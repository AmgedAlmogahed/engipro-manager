# ADR-0045: No cutover, no data migration

**Status:** Proposed
**Date:** 2026-08-02

## Context

Rebuild projects normally carry three expensive workstreams: a data migration from the old system, a cutover plan with a rollback path, and a decommission plan for the legacy system.

**None of them apply here.** `ABAK_ERP/` was built and deployed to an OCI ARM box but **never carried production data**. There is nothing to migrate, no live users to cut over, and no legacy system running in production to decommission.

This is worth an ADR precisely because it is unusual. A future reader — or a new team member — will reasonably assume a migration plan exists somewhere and go looking for it. Recording the absence as a deliberate finding prevents that search, and prevents someone building migration tooling for data that does not exist.

It also removes a common objection to rebuilding. The strongest argument against a rewrite is that it discards accumulated production behaviour. Here there is no production behaviour to discard — only design knowledge, which is mined deliberately (ADR-0003).

## Decision

- **No data migration.** There is no production data in `ABAK_ERP/`.
- **No cutover plan.** There are no live users to move.
- **No decommission plan.** Nothing is running in production to retire.
- `ABAK_ERP/` is **archived as reference material**, retained read-only for the mining protocol (ADR-0003).
- The frozen prototype is handled separately by ADR-0002; it also holds no production data (its data is mock data in `constants.ts`).
- **If this premise turns out to be wrong** — if any real client data exists anywhere in the old system — this ADR is superseded immediately and a migration ADR is written before any further work.

## Consequences

**Positive**
- Substantial workstreams are avoided, and the timeline reflects that honestly.
- The rebuild is free to choose different data shapes without migration compatibility constraints — schema-per-context (ADR-0013), UUIDv7 keys (ADR-0015), `numeric` money (ADR-0016), and `organization_id` (ADR-0017) can all be adopted cleanly.
- Removes the strongest general objection to rewriting.

**Negative / trade-offs**
- The new system starts with no real data, so performance characteristics under realistic volume are unknown until it is in use. Seed and load-test data must be generated deliberately (ADR-0009's fixtures).
- No production usage means no production-validated behaviour; the defect register and the prototype are the substitutes, which is why ADR-0003's mining is not optional.
- If the premise is wrong, discovering it late would be severe. Hence the explicit verification below.

## Rejected alternatives

| Alternative | Why rejected |
|---|---|
| **Build migration tooling anyway** | Tooling for data that does not exist. Pure waste. |
| **Run both systems in parallel (strangler)** | Correct when a live system serves real users. Here the old system serves nobody, so a routing layer would strangle an empty application. |
| **Leave this undocumented** | A future reader assumes a migration plan exists, searches for it, and may build one. The absence of a plan should be a finding, not a gap. |
| **Delete `ABAK_ERP/` entirely** | It holds the conflict register, the blueprint, the service catalogue, the flow documents, and the role matrix — the most valuable inputs to the rebuild (ADR-0003). |

## Enforcement

- **Verification before acceptance**: confirm that no production database, backup, or export from `ABAK_ERP/` contains real client data. This ADR moves from Proposed to Accepted only after that check, and the check is recorded here with a date. **This is the one thing in this ADR that must actually be done rather than assumed.**
- **Archive state**: `ABAK_ERP/` is retained read-only, outside the workspace, not in `pnpm-workspace.yaml` and not referenced by any tsconfig path (ADR-0003).
- **Seed data**: `packages/testing` provides realistic seed and volume-test fixtures, so the absence of production data does not mean the absence of realistic testing.
- **Supersession trigger**: if real data is found, work stops on new schema decisions until a migration ADR exists.
