# ADR-0004: Modular monolith behind a standalone API

**Status:** Accepted
**Date:** 2026-08-02
**Accepted:** 2026-08-08 — ratified as wave W2 (architecture shape).

## Context

The system must eventually serve an admin dashboard, a customer booking portal, a public site, mobile apps, a partner API, background workers, and scheduled jobs. It runs today on a single OCI Ampere ARM VM with roughly 6 GB of RAM, operated by a team of 2–5.

The business operations that matter are cross-aggregate and transactional: a won quotation issues a purchase order, which seeds a project with phases and payment milestones. These happen a few times a week, not thousands of times a second.

The predecessor's problem was never deployment topology. It was the absence of internal boundaries — no domain layer, and no event backbone, so "every cross-module effect is therefore an inline write" (C11, verbatim).

## Decision

We will build a **modular monolith** — one deployable API process, internally divided into domain modules — served by a **standalone API application** (`apps/api`), separate from the web frontend.

Deferred, with the seams built now:
- **BFFs** — introduced when the second client surface ships, not before.
- **Worker processes** — Phase 4, except the PDF/Chromium worker which ships with quotations (ADR-0032).
- **Service extraction** — only under a concrete forcing function: independent scaling need, a compliance boundary, or a second team blocked by our deploy cadence.

## Consequences

**Positive**
- One transaction spans a whole business operation. "Quote won → PO → project seeded → milestones created" is one commit, not a saga with compensating actions.
- One place to enforce authorization and audit.
- Refactoring across a module boundary is a type-check, not a coordinated multi-service release.
- One deployable fits the memory budget of a 6 GB box.

**Negative / trade-offs**
- All modules deploy together and fail together. Acceptable for an internal ERP; revisited if uptime requirements diverge per module.
- Scaling is all-or-nothing until workers are extracted.
- Internal boundaries are conventions unless enforced — which is exactly what happened before. ADR-0008 is the mitigation and is not optional.

## Rejected alternatives

| Alternative | Why rejected |
|---|---|
| **Microservices from day one** | Loses distributed transactions for the core business flow, turning a weekly event into a saga. Requires tracing, service discovery, and contract testing before there are users. Not viable on a 6 GB box. Fowler's *MonolithFirst*: service boundaries discovered early are almost always wrong, and refactoring across services is dramatically harder than within one deployment. |
| **Next.js API routes as the backend** | No natural home for cron, background workers, long-running PDF generation, or a partner API. Couples UI traffic to business logic scaling. Business rules end up next to React components. |
| **BaaS / platform-first** | Contradicts self-hosting outright, and moves business rules into database policies and vendor functions where they cannot be unit-tested or reviewed as code. |
| **Serverless functions** | Connection exhaustion against self-hosted Postgres, cold starts on low-traffic internal usage, and long-running jobs fighting execution limits. Wrong shape for a low-volume, high-complexity ERP. |
| **BFFs now** | Nothing to serve. Would be an empty indirection layer that accumulates business logic — the specific way BFFs fail. |

## Enforcement

- **dependency-cruiser** (ADR-0008): `no-app-to-app` prevents `apps/web` importing API internals, keeping the API a real network boundary rather than a shared library.
- **Deployment topology**: `docker-compose.prod.yml` runs the `api` container separately from the container serving the frontend, with separate memory limits; the boundary is physical, not aspirational. Since ADR-0050 the frontend is a static bundle served by Caddy rather than its own Node service (ADR-0032), which makes the boundary stronger rather than weaker — there is no frontend runtime that could import API internals even in principle.
- **Module structure**: enforced by ADR-0006 and ADR-0008 folder rules — this ADR is the intent; those are the mechanism.
