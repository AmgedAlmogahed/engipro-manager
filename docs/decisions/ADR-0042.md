# ADR-0042: Audit and financial record retention

**Status:** Accepted
**Date:** 2026-08-02
**Accepted:** 2026-08-08 — open question E answered: the proposed defaults are adopted. See the note on verification in Enforcement: the figures remain unconfirmed by a tax advisor and are adopted as **safe minimums**, on the reasoning that over-retention is correctable and under-retention is not.

## Context

ADR-0024 establishes an append-only audit log that is never deleted by the application. That is correct for integrity and unsustainable forever without a retention policy: the table grows monotonically, and a policy decided after ten years of data is a policy applied to data that may already have been kept too long or not long enough.

Two distinct retention questions:

1. **Financial and tax records.** Saudi tax regulations impose minimum retention periods on invoices, tax records, and supporting documents. ZATCA e-invoicing **does** apply (ADR-0039, accepted 2026-08-08), so its retention requirements apply to e-invoice data including the ICV and PIH chain — and a hash chain is only meaningful for as long as every link in it is retained. Commonly cited figures are **6 years** for tax records and longer for core accounting records, but the precise obligation for Abak's circumstances must be confirmed by whoever advises them on tax and corporate compliance — not inferred from a blog post or from this document.

2. **Operational audit entries.** Permission changes, status transitions, and access logs have no external mandate but do have practical value for dispute resolution.

## Decision

We will adopt the following retention periods:

| Category | Retention |
|---|---|
| Invoices, payments, tax records, e-invoice data | **10 years** |
| Financial audit entries (approvals, validations, PO issuance) | **10 years** |
| Operational audit entries (status transitions, permission changes) | **6 years** |
| Access and read audit entries | **2 years** |
| Notification delivery logs | **1 year** |
| Outbox rows | Deleted on success (ADR-0026) — not a retention category |
| Application logs | 30–90 days (ADR-0036) — not audit data |

**Hash chaining is deferred.** ADR-0024's schema reserves room for a `prev_hash` column so tamper-evidence can be added without redesign. It is warranted only if a legal or contractual requirement for tamper-evidence emerges; hash chaining serialises audit writes, which is acceptable at this scale but is a cost with no current justification.

**Deletion of audit data is a separate, audited administrative operation** performed by a distinct database role — never an application feature, consistent with ADR-0023.

## Consequences

**Positive**
- Retention becomes a deliberate, documented decision rather than "we kept everything and hoped."
- Tiering by category avoids applying the strictest requirement to the highest-volume data.
- Deferring hash chaining while preserving the schema shape keeps the option cheap.

**Negative / trade-offs**
- Holding the periods as configuration makes them editable, and an edit that *lowers* a figure is a deletion instruction wearing the clothes of a settings change. This is the sharpest edge in the ADR and is why the monotonicity checks in Enforcement exist; without them, configuration access would silently confer authority to destroy legally significant records.
- Multi-year retention on a single VM means the audit table becomes one of the largest objects in the database. Partitioning by month, and archiving cold partitions to object storage (ADR-0034), will be needed before the ten-year horizon.
- Any deletion of audit data is a sensitive operation and a plausible attack vector; the separate role and audited procedure are the mitigation.
- Retention periods stated here are **proposals from general knowledge and must be verified**. Acting on unverified compliance figures is itself a risk.

## Rejected alternatives

| Alternative | Why rejected |
|---|---|
| **Keep everything forever** | Simple and defensible for integrity, but unbounded growth on a single VM, and some regulations impose maximum retention on personal data as well as minimums. |
| **Uniform retention across all categories** | Either over-retains high-volume operational data or under-retains financial records. |
| **Delete audit entries from the application** | Contradicts ADR-0024's append-only guarantee and would require granting `DELETE` on the audit schema. |
| **Hash chaining now** | Serialises audit writes for a tamper-evidence property nobody has yet required. The schema keeps the option open. |

## Enforcement

- **Archival job**: a scheduled job moves partitions older than the retention period to object storage and records the operation in the audit log itself. Nothing is deleted outside this job.
- **Retention periods are configuration, not constants in code.** They are held in one place, per category, so a figure raised on advice is a config change rather than a code change. A hardcoded retention duration fails lint.
- **Retention configuration is monotonic-increasing, enforced mechanically.** Making the periods configuration created a hazard that constants did not have: lowering a value *causes deletion*. A config edit taking `financial_retention_years` from 10 to 3 would, on the archival job's next run, permanently destroy seven years of ZATCA-relevant records — with no migration, no review, and no second pair of eyes. Three checks, all failing closed:
  1. **Boot and CI assertion**: each retention value is compared against the last committed value. Any decrease fails the build and refuses production boot. This rides the same config-schema validation as ADR-0035's secret checks.
  2. **The archival job refuses to act** on any retention value that decreased since its previous run. It alerts and does nothing. A job that deletes more than it did last time, because configuration said so, must not be the thing that discovers the mistake.
  3. **Lowering a value is a deletion operation** and takes the same path as one: the separate audited administrative procedure and distinct database role required below. Lowering retention causes deletion, so it inherits deletion's controls rather than configuration's.
- Raising a value stays an ordinary config change requiring no ceremony, which keeps the common case — acting on advice — cheap.
- **Partitioning**: `audit.audit_log` is partitioned by month from the first migration, so archival later is a partition detach rather than a mass delete. **This is a now decision even though retention is blocked** — retrofitting partitioning to a large table is expensive.
- **Grants**: the application role holds `INSERT, SELECT` only; archival runs as a separate role (ADR-0024).
- **Verification remains an open action, and does not block acceptance.** The figures above are drawn from general knowledge, not from advice given to Abak. They are adopted because the archival job is the only thing that acts on them, it is not scheduled to run for years, and the asymmetry is one-directional: retaining a record too long is correctable at any time, while deleting one too early is not. Confirmation with a qualified tax or corporate-compliance advisor is therefore tracked as an outstanding item, and its only possible effect is to **raise** a figure. Advice that would *lower* one requires re-opening this ADR — and that is not left to good intentions: the monotonicity checks above make a lowered value fail the build, refuse boot, and halt the archival job.
