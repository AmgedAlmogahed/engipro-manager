Claim 4b was the one worth testing. A tool that generates additive migrations correctly and silently omits destructive ones leaves the schema drifting from the model on every green run. Drizzle emits both.

**Recorded caveat.** The PoC schema is throwaway, under `tools/poc/multischema/`, so a failed run left no residue in `packages/database`. The cost is that it does not exercise the real package layout — covered by a later gate rather than ignored: the first real migration is checked by the live-fired migration lint (ADR-0014 rider), which additionally verifies that any tooling regex touching Drizzle's generated migration paths holds under pnpm's layout. That last point exists because ADR-0008's vendor rule was written against npm's flat `node_modules` and never matched under pnpm.

**Rider — the multi-schema proof of concept is a W3 entry condition, not advice.** This ADR's own text says to validate the schema layout with a proof of concept before committing to it. That is elevated here to a **gate**: before the first real migration lands, a throwaway PoC must demonstrate Drizzle's multi-schema behaviour and cross-schema migration ordering — two schemas per ADR-0013, a foreign-key-by-identifier reference across them, and migration generation in both directions. The result is recorded in this ADR whether it passes or fails. **If it fails, the one-day Prisma bake-off triggers** rather than the schema layout being adjusted to suit the tool.

Run it in CI, not only locally, for the reason recorded in ADR-0010's rider.

## Context

The ORM sits behind repository ports (ADR-0006), so this is the most reversible decision in the set. It is still worth recording, because the choice interacts with three other decisions: domain purity (ADR-0006), money precision (ADR-0016), and migration safety (ADR-0014).

The predecessor used Prisma with a 2,700-line single-schema file, `Float` money columns, and no unique constraint on client phone or email despite a documented deduplication rule (C7).

## Decision

We will use **Drizzle**, narrowly, over Prisma.

Reasons, in order of weight:
1. **No generated client to leak.** Drizzle's schema *is* TypeScript. Prisma generates a client whose types are convenient to import into `domain/` — exactly the leak ADR-0008 rule 2 exists to prevent. Drizzle removes the temptation structurally rather than policing it.
2. **Explicit precision in the DDL.** `numeric('amount', { precision: 19, scale: 4 })` states exactly what lands in the database, which matters given ADR-0016.
3. **No data-destructive migration commands.** Prisma ships `migrate dev` and `migrate reset`, which must never touch production and have caused incidents elsewhere. Drizzle has no equivalent footgun.
4. **Pure TypeScript on ARM** — no native binary or engine to reconcile with arm64 builds.

**This decision is explicitly re-openable.** Prisma is defensible on team familiarity, ecosystem size, and TypedSQL ergonomics. If the team writes the same repository both ways behind the same port and prefers Prisma, accept it and supersede this ADR. Timebox that exercise to one day.

**Consequence to handle immediately:** Drizzle returns `numeric` columns as **strings**. `decimal.js` is standardised in `packages/domain` and is the only permitted way to perform monetary arithmetic.

## Consequences

**Positive**
- Nothing generated means nothing generated to import into the domain layer.
- SQL-first ergonomics suit an ERP, where reporting and cross-cutting queries need raw SQL more often than a typical CRUD app.
- No schema-generation step in the build.

**Negative / trade-offs**
- Thinner documentation on multi-schema edge cases than Prisma (relevant given ADR-0013). Validate with a proof of concept before committing the schema layout.
- Migration ordering across schemas when tables reference one another by ID is not well documented. Test it.
- Smaller ecosystem and fewer Stack Overflow answers than Prisma; the team absorbs more of the learning.
- String-returning numerics are a real bug source if `decimal.js` discipline slips — silent string concatenation instead of addition.

## Rejected alternatives

| Alternative | Why rejected |
|---|---|
| **Prisma** | Generated client invites domain-layer type leakage; two data-destructive CLI commands; a schema DSL requiring a generate step. **Not rejected on quality** — it is the runner-up and remains acceptable if the team prefers it after the one-day bake-off. |
| **Raw SQL only** | Hand-rolled migrations and result mapping. Raw SQL is still used *selectively inside repositories* for reporting, which captures most of the benefit. |
| **TypeORM / Sequelize** | Active-record patterns encourage entities that know how to persist themselves, which is the opposite of ADR-0006's separation. |

## Enforcement

- **dependency-cruiser** rule `no-vendor-in-domain-or-application` lists `drizzle-orm` explicitly, so the ORM cannot appear outside `infrastructure/` and `packages/database`.
- **Migration lint** (ADR-0014) inspects generated SQL for banned column types, so a misconfigured Drizzle column definition is caught at the DDL level rather than trusted.
- **Money arithmetic lint**: an ESLint rule forbids arithmetic operators (`+`, `-`, `*`, `/`) on values typed as `Money`; only `decimal.js` methods are permitted. Prevents the string-concatenation failure mode.
- **Enum parity test**: CI asserts that every enum in `packages/domain` matches the corresponding database enum or check constraint, so the domain remains the definition and the schema the mirror.
