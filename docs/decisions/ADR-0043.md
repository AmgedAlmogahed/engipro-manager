# ADR-0043: Multi-role conflict resolution

**Status:** Proposed — **BLOCKED** on open question C
**Date:** 2026-08-02

## Context

ADR-0021 allows a user to hold more than one role, and each role grants permission keys at a scope. When two roles grant the same key at different scopes, the effective scope must be determined by a rule.

Standard RBAC practice is **most-permissive wins**: effective permissions are the union of grants, and the widest scope applies. This matches user expectation — adding a role should not reduce access — and is what almost every RBAC implementation does.

There is a category where that default is arguably wrong: **financial approval gates**. If someone holds a role granting `quote:approve` at `DEPARTMENT` and another granting it at `ORGANIZATION`, most-permissive means they may approve any quotation in the company. Where approval thresholds exist for control purposes, the widest grant may defeat the control — this is adjacent to separation-of-duties, which NIST RBAC treats as a distinct component precisely because it is not automatic.

## Decision

**BLOCKED** on confirmation. Proposed rule, stated so it can be closed quickly:

1. **Default: most-permissive wins.** Effective permissions are the union of all role grants; where the same key appears at multiple scopes, the widest applies.
2. **Exception: financial approval keys use most-restrictive.** For a declared set of keys — `quote:approve`, `finance:validate_payment`, `finance:manage_invoice`, `project:licence_override` — the **narrowest** granted scope applies.
3. The exception set is **data**, held in `permission_definitions` as a `conflict_resolution` column (`permissive` | `restrictive`), not a hardcoded list. Adding a key to the exception set is a configuration change, consistent with ADR-0021's rejection of hardcoded authorization behaviour (C14).

## Consequences

**Positive**
- The common case behaves as users expect.
- Financial controls are not silently widened by an unrelated role assignment.
- Because the rule is per-key data, the policy is auditable and adjustable without a deploy.

**Negative / trade-offs**
- Two rules instead of one means the effective-permission calculation is harder to explain, and a user may find they *cannot* approve something despite holding a role that appears to permit it. The admin UI must show the effective scope and **why** it was narrowed, or this becomes a support burden.
- A per-key column adds a dimension to the permission catalogue.
- If the exception set grows, the mental model degrades. Keep it small and reviewed.

## Rejected alternatives

| Alternative | Why rejected |
|---|---|
| **Most-permissive everywhere** | Simplest and standard, but a role granted for an unrelated reason can silently widen financial approval authority. |
| **Most-restrictive everywhere** | Violates the expectation that adding a role adds capability; a user with a broad role and a narrow one would lose access, which is surprising and generates support load. |
| **Explicit deny to model the exception** | Requires the overrides table (ADR-0044) and makes every effective-permission calculation carry a deny pass. Heavier than a per-key resolution rule. |
| **Prevent users from holding multiple roles** | Real organisations have people who are both a department head and a project manager. Denying that pushes the problem into bespoke composite roles, which is role explosion. |

## Enforcement

- **Blocked**: while unresolved, the permission resolver implements most-permissive only, and the exception set is empty. That is the safe interim because it is the standard behaviour, and the financial keys are not yet in use.
- Once resolved: `permission_definitions.conflict_resolution` drives the resolver; no code branches on a key name.
- **Role-matrix suite** (ADR-0009) gains cases for a user holding two roles granting the same key at different scopes, asserting the resolved scope for both a permissive and a restrictive key.
- **Admin UI**: the effective-permissions view shows the resolved scope and the roles contributing to it. Without this, the rule is invisible to administrators.
- **Audit**: role assignment changes record the effective-scope delta, so a widened or narrowed authority is traceable.
