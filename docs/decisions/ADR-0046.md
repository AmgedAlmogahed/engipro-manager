# ADR-0046: Public endpoints and the inbound integration boundary

**Status:** Proposed
**Date:** 2026-08-02
**Added during the completeness check** — conflict register item **C6** (severity S1) had no home in the supplied decision set, and the Integrations context needed a defined inbound contract.

## Context

The conflict register records C6 as a severity-1 defect: `POST /api/v1/leads/chatbot` was marked `@Public` — *"an unauthenticated write into the primary business table with no specified secret, rate limit or duplicate suppression."*

That is not a coding slip. It is what happens when an external system needs to push data in and the quickest path is to open an endpoint. The same pressure will recur here: the AI chatbot, the website contact form, WhatsApp inbound messages, payment gateway webhooks, and eventually government tender portal callbacks all need an inbound path.

Without a defined pattern, each one becomes an ad-hoc public route, and each is a potential unauthenticated write into business data.

## Decision

**No unauthenticated write reaches a business use-case.** Inbound external traffic goes through an **anti-corruption layer** in the Integrations context:

```
external system → signed/authenticated inbound endpoint
                → verify signature or shared secret
                → rate limit + idempotency key
                → normalise to a domain-neutral inbound event
                → the SAME use-case any internal caller would invoke
```

Rules:
1. **Every `@Public` route requires an ADR.** There is no ambient permission to add one.
2. **Authentication for machine callers** is a signed request (HMAC over the body with a shared secret) or a scoped API key — never "public because it's a webhook."
3. **Rate limiting** is mandatory on every inbound integration endpoint.
4. **Idempotency** is mandatory: the caller supplies a key, or one is derived from the payload, and duplicate deliveries produce one effect. Payment gateway callbacks in particular are retried by design.
5. **Payload shapes never enter the domain.** A provider's JSON is normalised in the adapter; Meta's WhatsApp schema, a gateway's callback shape, and a chatbot's format are all vendor concerns confined to `infrastructure/` (ADR-0006).
6. **Never trust a client-side redirect** as proof of payment. Only a verified server-to-server callback, or an explicit status query against the provider, may change financial state.
7. Inbound writes create records in the **same** way as internal ones — same use-case, same state machine, same audit entry, same validation. There is no privileged side door.

## Consequences

**Positive**
- C6 becomes structurally impossible: an unauthenticated route cannot exist without a reviewed ADR, and even then it cannot bypass the use-case.
- Adding an integration is a known shape rather than an improvisation.
- Vendor payload changes are contained to one adapter.

**Negative / trade-offs**
- Slightly more work per integration than opening a route: signature verification, an idempotency store, and rate-limit configuration.
- Shared secrets must be provisioned and rotated per integration (ADR-0035).
- Some providers do not support signing; those require an alternative such as IP allow-listing plus a secret path segment, which is weaker and must be recorded in the integration's ADR.

## Rejected alternatives

| Alternative | Why rejected |
|---|---|
| **Public endpoints with validation only** | C6 exactly. Validation confirms the shape, not the sender; anyone can post a well-formed lead. |
| **A separate "integrations" service with its own database** | Premature; it would also duplicate the business rules the inbound data must satisfy. |
| **Writing inbound data to a staging table for later processing** | Defensible, and worth it for high-volume or untrusted sources. Rejected as the default because it creates a second, weaker validation path — the same duplicated-invariant problem as C12. |
| **Allowing integrations to write business tables directly** | Bypasses state machines, audit, and permissions — the C5 pattern. |

## Enforcement

- **Lint / CI**: any route decorated `@Public` fails the build unless its path is listed in an allow-list file, and each allow-list entry must reference an ADR number. Adding one is therefore a visible, reviewed decision.
- **Structural test**: inbound integration handlers are asserted to call the same use-case as the corresponding internal endpoint — no separate write path.
- **Signature test**: each integration's test suite includes a rejected-unsigned-request case and a replayed-request case asserting one effect.
- **Rate limit test**: an integration test asserts the limiter engages.
- **dependency-cruiser**: provider SDKs and payload types are confined to `modules/integrations/*/infrastructure/` (ADR-0008 rule 2).
- **Audit**: inbound-created records carry `actor_type = 'system'` with the integration identified, so their provenance is visible (ADR-0024).
