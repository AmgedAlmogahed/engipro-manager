# ADR-0029: Workflow, status, and state machines

**Status:** Proposed
**Date:** 2026-08-02

## Context

Status changes crossing module boundaries was the second of the five problems motivating this rebuild. The conflict register documents exactly how it went wrong:

- **C3** — `PipelineEntry.stage` had no transition table. Any stage could jump to any other, including backwards out of `WON`. `opportunity.update` could write `stage` directly, bypassing the field gates that did exist.
- **C4** — `Client.status` and `Client.classification` were free-form writes: the update DTO passed both straight through, with any value, no reason, no guard, and no audit. Four separate call sites wrote classification.
- **C12** — `leads.requestRfq` created an opportunity directly at `READY_FOR_RFQ`, bypassing the five-field qualification gate that `pipeline.moveStage` enforced. The same invariant was enforced on one path and skipped on another.
- **C16** — RFQ terminal outcomes were not RFQ states at all; they were read off the linked Quote at render time. Two sources of truth.

The common cause: status was an ordinary writable field, and the rules about changing it lived in service methods rather than in the entity.

## Decision

**Status is never a writable field.**

1. **No `status`, `stage`, or `classification` in any update contract.** The field does not exist in the Zod schema, so it cannot be sent.
2. **State moves only through `aggregate.transition(to, actor, reason?)`**, a method on the domain entity that validates the current state, the actor's permission, and any guards. A service cannot bypass it, because the setter does not exist.
3. **Required reasons are `NOT NULL`** on the transition record — disqualification, loss, rejection, cancellation, licence override. Not "validated in the service"; a database constraint.
4. **Each aggregate owns its own status.** No aggregate derives its terminal state from another at render time (C16). Cross-aggregate facts arrive as events.
5. **Every transition writes an audit entry in the same transaction** (ADR-0024) and emits a domain event to the outbox (ADR-0026).

**Cross-module orchestration — two mechanisms, chosen by shape:**

| Shape | Mechanism |
|---|---|
| One-to-one reaction, no compensation | **Domain event** via the outbox |
| Multi-step chain (5+) with rollback semantics | **Explicit workflow / process-manager object** |

The commercial chain — enquiry → client → opportunity → RFQ → quotation → won → PO → project — is the workflow case. It is a named object that calls module use-cases in sequence and handles compensation, rather than orchestration buried inside any one module.

The canonical flow:

```
Sales.markWon()  ── one transaction ──▶ quotation.status = Won
                                        outbox: QuotationWon
                                        audit entry
       ├─▶ Finance      consumes QuotationWon → validates → issues PO → emits PurchaseOrderIssued
       │        ├─▶ Delivery   creates project, phases, payment milestones
       │        ├─▶ CRM        increments lifetime value
       │        └─▶ Notifications  informs owner and finance
       └─▶ Audit        every step, in the transaction that caused it
```

Sales knows nothing about projects. Delivery knows nothing about quotations.

## Consequences

**Positive**
- C3, C4, C12, and C16 lose their mechanisms entirely rather than being guarded against.
- An invariant lives in exactly one place, so it cannot be enforced on one path and skipped on another.
- Every state change is auditable and produces a durable event.
- Modules stop writing each other's tables.

**Negative / trade-offs**
- Cross-module effects are eventually consistent (ADR-0026's trade-off). The user does not see the project on the quotation screen.
- Correcting bad data requires a legitimate transition or an explicit, audited administrative operation — there is no `UPDATE … SET status`.
- Workflow objects are harder to unit test than a single service method, since they orchestrate several module APIs.
- More ceremony for simple status changes on Medium-tier modules. Thin-tier modules (ADR-0007) have no state machines at all.

## Rejected alternatives

| Alternative | Why rejected |
|---|---|
| **Status as a normal field with service-layer validation** | The predecessor. Validation is bypassable by any other code path that also writes the field — C4 and C12 exactly. |
| **A state machine library (XState)** | A dependency and a modelling paradigm for what is, in each aggregate, a 5–8 state transition map. A hand-rolled map in the entity is simpler and has no runtime cost. Revisit if a workflow needs parallel states or history. |
| **Database triggers enforcing transitions** | Cannot express actor permissions or produce good error messages, and the rules become invisible to developers reading the module. |
| **Deriving status from related aggregates** | C16. Two sources of truth that disagree at render time. |
| **A workflow engine (Temporal, Camunda)** | Disproportionate for a single-server ERP; introduces a second stateful system. Revisit only if long-running human-in-the-loop workflows with timers become central. |

## Enforcement

- **Contract-level**: `status`/`stage`/`classification` are absent from every update schema in `packages/contracts`. A CI test asserts no update schema contains these keys — the structural fix for C3 and C4.
- **Domain-level**: entities expose no status setter. A structural test asserts the only mutation path is `transition()`.
- **Database-level**: reason columns are `NOT NULL` on transitions that require them; an integration test attempts a reasonless disqualification and expects a constraint violation.
- **State-machine suite** (ADR-0009): for every aggregate, every legal transition succeeds, every illegal transition throws — including backwards out of terminal states, which is C3 verbatim — and every reason-requiring transition rejects a null reason.
- **Single-path test**: for each invariant that has more than one entry point, a test exercises **both** and asserts identical enforcement. This is C12's specific regression test.
- **dependency-cruiser**: `no-cross-module-internals` prevents a module writing another's tables, so orchestration must go through events or the workflow object.
- **Audit coverage**: the state-machine suite asserts an audit row after every transition (ADR-0024).
