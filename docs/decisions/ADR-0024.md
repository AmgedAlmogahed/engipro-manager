# ADR-0024: Audit log

**Status:** Accepted
**Date:** 2026-08-02
**Accepted:** 2026-08-08 — ratified as wave W5 (platform mechanics).

**Rider — the discrepancy check needs a nonzero baseline.** The nightly check comparing state transitions against audit rows passes trivially when *both* queries are broken: `0 == 0` is green. That is the same class of defect this branch has hit nine times, and it is worse here than elsewhere, because a silently-passing audit-completeness check is indistinguishable from a complete audit trail.

The check must therefore assert that **business activity exists in the window** before comparing counts, and report "no data in window" as a **distinct third state** — never as success. A weekend with no transitions is a legitimate no-data result; a broken query is not, and the two must not render identically.

Generalised in ADR-0048: any check deriving rules from data fails when it parses zero rules, and any check comparing two counts asserts its baseline is nonzero.

## Context

The ERP records commercially and legally consequential decisions: quotation approvals, purchase orders, payment validations, licence overrides, permission grants. When a dispute arises about who changed what and when, the audit trail is the answer.

The predecessor's audit was partial and unreliable. C10 records that only lead status transitions were audited, while RFQ decline, cancel, and start-pricing, every pipeline stage move, the bulk SLA recompute, and the cron reclassifier all mutated state silently — and that audit write failures were **swallowed** (`audit.service.ts:40`). An audit trail with silent gaps is worse than none, because it is trusted.

## Decision

We will write audit entries **in the same transaction as the change they describe**. If the audit write fails, the business operation fails.

```sql
audit.audit_log (
  id uuid PRIMARY KEY,
  organization_id uuid NOT NULL,
  occurred_at timestamptz NOT NULL DEFAULT now(),
  actor_id uuid,                    -- null only for system actors
  actor_type text NOT NULL,         -- staff | customer | partner | system
  actor_roles text[],               -- roles held at the time of the action
  entity_schema text NOT NULL,
  entity_type text NOT NULL,
  entity_id text NOT NULL,
  action text NOT NULL,
  old_value jsonb,
  new_value jsonb,
  reason text,                      -- required for transitions that require one
  correlation_id uuid,              -- ties to the request and its events
  ip_address inet,
  user_agent text
)
```

**Append-only, enforced by the database:** a `BEFORE UPDATE OR DELETE` trigger raises an exception, and the application role holds only `INSERT` and `SELECT`.

**What must be audited:** every status transition in every module; every approval, rejection, decline, and cancellation with its reason; every permission, role, and scope change; every financial validation and payment record; every data export; every licence override.

**Reading the audit log is itself a permission** (`audit:view`), and reads are audited.

Hash chaining is **deferred** (ADR-0042) — the schema reserves room for a `prev_hash` column so it can be added without redesign.

## Consequences

**Positive**
- No silent gaps. C10 cannot recur, because a swallowed failure is impossible when the write shares the transaction.
- A disputed status change is resolved by one query rather than by reconstructing intent from logs.
- `correlation_id` links an audit entry to the request that caused it and to every event it emitted (ADR-0036).

**Negative / trade-offs**
- Every state-changing operation carries an extra insert, and an audit failure now fails the business operation. That is the intended trade — availability sacrificed for integrity — but it must be understood.
- The table grows without bound; retention is ADR-0042 and is currently unresolved.
- `jsonb` before/after values are verbose. Storing whole entities is simpler than diffing and is preferred for evidentiary clarity.
- Audit is **not** the event log. The outbox (ADR-0026) is for triggering work; audit is for recording history. Two tables, deliberately.

## Rejected alternatives

| Alternative | Why rejected |
|---|---|
| **Audit written asynchronously (fire-and-forget)** | Exactly the predecessor's C10: failures swallowed, gaps invisible, and the record trusted anyway. |
| **Database triggers capturing all writes** | Catch writes from migrations and scripts too, which is an advantage, but cannot capture application context — actor, reason, correlation identifier — without session variables, and those break under transaction pooling (ADR-0022). Used only as a supplementary net on tables writable outside the application. |
| **Deriving audit from the outbox** | Conflates two purposes with different retention, different access control, and different failure semantics. Outbox rows are deleted on success (ADR-0026); audit rows are never deleted. |
| **Application logs as the audit trail** | Logs are sampled, rotated, and mutable. They carry no legal weight and are not queryable per entity. |

## Enforcement

- **Database trigger**: `BEFORE UPDATE OR DELETE ON audit.audit_log` raises an exception. Verified by an integration test that attempts both and expects failure.
- **Grants**: the application role has `INSERT, SELECT` only on `audit.*`.
- **Same-transaction guarantee**: the audit write is issued through the same unit of work as the change; a use-case that commits without an audit entry for a state transition fails a structural test.
- **Coverage test**: for every aggregate with a state machine (ADR-0029), the state-machine suite asserts an audit row exists after each transition, with a non-null reason where the transition requires one.
- **Permission**: `audit:view` is required to read; reads are themselves audited, asserted by test.
- **Nightly check**: count of transitions in business tables versus audit rows for the same period; a discrepancy raises an alert.
