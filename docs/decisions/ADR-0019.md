# ADR-0019: Bilingual content model

**Status:** Proposed
**Date:** 2026-08-02
**Added beyond the supplied decision set** — how bilingual content is stored propagates into every table, every contract, and every query, and it is expensive to change once data exists. Arabic is the primary interface language, so this cannot be treated as an afterthought.

## Context

Two different bilingual problems are commonly conflated:

1. **Interface strings** — button labels, column headings, validation messages. These are compile-time assets belonging to the application, not the database. The frozen prototype already contains roughly 1,000 lines of validated Arabic/English translations that should be reused.
2. **Content data** — a service catalogue entry, a department name, a quotation's scope narrative, a PDF's greeting and conclusion. These are rows in the database, they are edited by users, and some of them appear in client-facing documents where both languages may be needed.

Additionally, the system is **RTL-primary**: Arabic is the default interface language. Layout that hardcodes `left`/`right` breaks; the prototype already demonstrated that logical CSS properties (`ps-*`, `pe-*`, `ms-*`, `me-*`, `start-*`, `end-*`) work and should be the standard.

The old system used `nameAr`/`nameEn` column pairs in places, which is workable but inconsistent, and its screen specifications carried Arabic labels that were never centralised.

## Decision

- **Interface strings** live in `packages/i18n` (extracted from `apps/web` when a second consumer appears, per ADR-0001), keyed and typed. The prototype's existing `translations.ts` is mined and reused rather than re-translated.
- **Content data** uses **explicit paired columns** — `name_ar text`, `name_en text` — not JSON, not a translations table. A `LocalizedText { ar, en }` value object in `packages/domain` wraps the pair.
- **Which language is required** is a per-field domain decision recorded in the module's mining document. Client-facing document fields generally require Arabic; internal notes generally do not.
- **Resolution** happens at the presentation edge with an explicit fallback order (requested locale → Arabic → English → empty), never silently in the repository.
- **RTL**: logical CSS properties only. `left`/`right`/`ml-`/`mr-`/`pl-`/`pr-` are forbidden in application styles.
- **Documents (PDF)**: locale is an explicit parameter of the render contract, not inferred from the request.
- Only two languages are supported. If a third is ever required, this ADR is superseded by one introducing a translations table.

## Consequences

**Positive**
- Both languages are queryable and indexable — `WHERE name_ar ILIKE …` works, which a JSON blob makes awkward and a translations table makes a join.
- Constraints can require Arabic where the business requires it, per column.
- Reuses translation work already done and validated in the prototype.
- Contract schemas express the pair explicitly, so the frontend cannot forget a language exists.

**Negative / trade-offs**
- Two columns per translatable field; the schema is wider and slightly repetitive.
- Adding a third language is a schema migration across many tables. Accepted deliberately — two languages is the requirement, and a translations table is materially more complex for a case that may never arrive.
- Sorting differs by language; a list sorted by `name_ar` and one sorted by `name_en` are in different orders. Sort key must follow the requested locale.

## Rejected alternatives

| Alternative | Why rejected |
|---|---|
| **JSONB `{ "ar": …, "en": … }`** | Harder to index and constrain per language; type safety depends on discipline rather than the schema. |
| **Separate `translations` table** | Correct for many languages, disproportionate for two — every read becomes a join or a second query, for a case with a fixed, small language set. |
| **Single column plus a locale column (row per language)** | Doubles row counts on catalogue tables and complicates every unique constraint and foreign key. |
| **Arabic only** | The system already has English users and English-language documents. |
| **Application-side translation of user content** | Machine translation of contractual language is unacceptable in client-facing documents. |

## Enforcement

- **Migration lint** (ADR-0014): a text column whose name ends `_ar` must have an `_en` sibling and vice versa. Client-facing document fields listed in the lint configuration require `NOT NULL` on `_ar`.
- **ESLint rule**: `left`/`right` directional Tailwind utilities (`ml-`, `mr-`, `pl-`, `pr-`, `left-`, `right-`, `text-left`, `text-right`) are errors in `apps/web` and `packages/ui`; logical equivalents are required. The path matters: a rule scoped to a directory that does not exist never fires, and reports as passing.
- **Contract schemas**: `LocalizedText` is a shared Zod schema, so an endpoint returning only one language fails contract conformance tests.
- **i18n key check**: CI asserts every key present in the English dictionary exists in Arabic and vice versa; a missing translation fails the build rather than rendering a raw key.
- **Visual check**: `apps/web`'s default test locale is Arabic, so RTL breakage surfaces in normal test runs rather than only when someone switches language.
