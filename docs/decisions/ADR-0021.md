# ADR-0021: Hand-rolled permission model

**Status:** Proposed
**Date:** 2026-08-02

## Context

Permission rigidity was the first of the five problems that motivated this rebuild. The requirement is granularity along four axes — module, action, record scope, and selected field visibility — with roles composable by an administrator at runtime and no role names in code.

The predecessor's failures here are precisely documented:
- **C1** — two authorization models coexisted and disagreed: hardcoded `UserRole` checks living beside a permission engine.
- **C2, C23** — permission keys guarding a different capability than their name implied, and orphan keys defined but wired to no route.
- **C14** — manager designation was a hardcoded `Set` in a guard, so promoting someone required a code change and a deploy.
- **C21** — record lookups with no scope assertion, producing IDOR: any holder of `comms:log` could act on any client's records.

Zanzibar-style systems (OpenFGA, SpiceDB, Ory Keto) target billions of relationships and require a second stateful service. Decisively for this system: **they return a boolean allow/deny — they do not produce the SQL predicate a list endpoint needs.** The scope resolver would still have to be written.

## Decision

We will **hand-roll** a hybrid model: RBAC core, plus a scope dimension, plus opt-in field keys.

**Five tables**

```sql
permission_definitions(key PK, module, action, description, is_scopeable)
roles(id, organization_id, name, is_system_role)
role_permissions(role_id, permission_key, scope)   -- scope lives on the GRANT
user_roles(user_id, role_id, organization_id, granted_by, granted_at, expires_at)
user_permission_overrides(...)                     -- see ADR-0044; dropped unless required
```

**Two functions, and nothing else decides access**

```ts
authorize(actor, 'quote:approve', resource?)   // throws 403
scopeFilter(actor, 'clients:view')             // returns a WHERE fragment
```

**Four granularity levels**

| Level | Mechanism | Example |
|---|---|---|
| Module | key prefix | `quote:*` |
| Action | full key | `quote:approve` |
| Record | `scope` on the grant | `OWN ⊂ TEAM ⊂ DEPARTMENT ⊂ BRANCH ⊂ ORGANIZATION ⊂ PLATFORM` |
| Field | opt-in key + DTO serializer | `client:credit_limit:read` |

Field permissions are **opt-in**: a field is readable if the row is, unless it has its own key. Opt-out would explode the catalogue.

**Scope is compiled to SQL inside the repository, never applied after fetch.** `departmentDescendantIds` is resolved **once per request** via `WITH RECURSIVE` into the request context.

**Manager designation is data** — being `department.manager_id` unlocks a configured set of keys at `DEPARTMENT` scope, read from Settings.

**Eight seed roles** ship as system roles covering roughly 90% of assignments: Sales Rep, Sales Manager, RFQ Engineer, Department Head, Project Manager, Finance, Viewer, System Admin. Raw role composition is restricted to System Admin.

## Consequences

**Positive**
- Organisational change becomes configuration, not a deploy — the direct fix for C14.
- One authorization model, so C1 cannot recur.
- Scope in the query fixes C21 and keeps pagination counts correct.
- Seed roles keep granularity from becoming an administrative burden.

**Negative / trade-offs**
- We own the implementation: roughly 500 lines plus the scope resolver, and its correctness is on us.
- Permission keys are effectively permanent; a rename orphans existing grants (ADR-0014's expand-contract applies).
- The `DEPARTMENT`-with-descendants scope needs a recursive query per request. At ~50 users and a shallow tree this is microseconds; cached in request context.
- Field-level keys grow the catalogue; kept small by being opt-in.

## Rejected alternatives

| Alternative | Why rejected |
|---|---|
| **OpenFGA / SpiceDB / Ory Keto** | Return boolean allow/deny, not a SQL predicate — the scope resolver would still be hand-written. Require a second stateful service and a relationship-sync pipeline. Designed for Google-scale relationship graphs, not a ~50-user single-organisation ERP. |
| **Cerbos** | Stateless and NestJS-friendly, but still a sidecar plus policy in YAML outside the codebase — the same objection at smaller scale. Reconsider only if non-engineers must author policy. |
| **Casbin** | Policy in CONF files, harder to audit and test than TypeScript plus data. |
| **CASL alone** | Ability rules live in application code, so roles would not be admin-composable at runtime. Acceptable as an *enforcement helper* that translates abilities to predicates; not as the source of truth. |
| **Role enum in code** | The predecessor. Every organisational change becomes a deploy; produced C1 and C14. |
| **PostgreSQL RLS for all scopes** | See ADR-0022 — recursive scope in an RLS `USING` clause is evaluated per candidate row. |

## Enforcement

- **ESLint rule**: a string literal matching a known role name inside a conditional is an error. This is the specific control for C1 and C14.
- **CI catalogue check**: every key in `permission_definitions` is referenced by at least one guarded route, and every guarded route references a key that exists. Fixes C2 and C23 by making orphans and mismatches build failures.
- **Compile-time scope**: repository methods take a required `ScopeContext` parameter; omitting it does not compile. This is the structural fix for C21.
- **Role-matrix suite** (ADR-0009): asserts allow/deny for every (role × endpoint × scope) triple, including IDOR probes with a foreign owner and a foreign `organization_id`.
- **Lint**: post-fetch filtering — `.filter(` applied to a repository result on an authorization attribute — is flagged for review.
- **Audit**: every permission, role, grant, and scope change writes an audit entry in the same transaction (ADR-0024).
