# ADR-0028: Internal notification model

**Status:** Accepted
**Date:** 2026-08-02
**Accepted:** 2026-08-08 — ratified as wave W5 (platform mechanics).

## Context

Notification unreliability is the third of the five problems motivating the rebuild. In the predecessor, notifications were fire-and-forget with swallowed failures (C11) and were called inline from business services, which coupled the notification concern to every module that needed to tell someone something.

The stated requirements are: notifications must react reliably to domain events, support retries, be auditable, support targeting, and support multiple channels over time — starting with in-app, adding email and WhatsApp later.

Off-the-shelf notification infrastructure exists (Novu, Knock, Courier). Self-hosting Novu brings Redis and MongoDB, which conflicts directly with ADR-0012 and the memory budget in ADR-0032. Its *data model*, however, is a well-considered reference.

## Decision

We will build a **lightweight internal notification module** in PostgreSQL, following Novu's data shape without running Novu.

```sql
notifications.subscribers        (user_id, channel_preferences jsonb, locale, quiet_hours)
notifications.templates          (key, channel, locale, subject, body, variables)
notifications.workflows          (key, trigger_event_type, channels[], digest_rule)
notifications.executions         (id, workflow_key, event_id, subscriber_id, status, created_at)
notifications.messages           (execution_id, channel, provider, status, attempts,
                                  provider_ref, error, sent_at)
```

The load-bearing insight: **a notification is not one row.** It is a workflow execution that may produce three channel attempts, each with its own status and retry count. That is what makes delivery auditable rather than merely attempted.

Rules:
- The notifications module is a **pure consumer of the outbox** (ADR-0026). No use-case anywhere calls a notification service directly.
- **Channel order**: in-app first (no external dependency, ships in Phase 2), then email, then WhatsApp — each behind a `MessagingProvider` port (ADR-0006).
- **Idempotency**: unique on `(event_id, subscriber_id, channel)`, so a redelivered event cannot double-notify.
- **Retries and dead-lettering** come from graphile-worker (ADR-0027).
- **`digest_rule` exists as a column and is unused.** Batching is deferred; the column is present so adding it later is not a migration of the workflow table.
- **Recipient resolution** derives from the event plus organisational structure plus subscriber preferences — never a hardcoded recipient list.
- Provider credentials are secrets (ADR-0035), never stored in plain columns.

## Consequences

**Positive**
- Notifications become reliable by construction: durable events in, retried per-channel deliveries out, with a delivery log.
- Business modules stop knowing that notifications exist, which removes an entire class of coupling.
- Adding a channel is an adapter plus a template, not a change to any business module.
- Delivery status is queryable per message — "did the client actually receive the quotation?" has an answer.

**Negative / trade-offs**
- We write the dispatcher, template rendering, and preference resolution ourselves — roughly two weeks of work that a hosted product would provide.
- Template management has no UI initially; templates are seeded and edited as data.
- Multi-channel fan-out semantics (does an in-app read suppress the email?) must be decided per workflow. Initially: no suppression, simplest behaviour.
- The `executions` and `messages` tables grow; retention is a Phase 4 concern.

## Rejected alternatives

| Alternative | Why rejected |
|---|---|
| **Novu self-hosted** | Requires Redis and MongoDB, contradicting ADR-0012 and consuming a large share of a 6 GB budget. Its data model is adopted; its runtime is not. |
| **Knock / Courier (hosted SaaS)** | External dependency for a core workflow component, per-notification cost, and subscriber data leaving the estate. Revisit if volume and complexity grow substantially. |
| **Inline calls from business services** | The predecessor. Produces C11, couples every module to the notification concern, and provides no retries or delivery record. |
| **A single `notifications` table** | Cannot represent per-channel delivery status or retry counts, which is precisely what makes the record auditable. |
| **Email first instead of in-app** | Requires provider credentials, deliverability configuration, and DNS work before anything is demonstrable. In-app needs none of that. |

## Enforcement

- **dependency-cruiser**: no module outside `notifications/` may import the notification service; business modules emit events instead. Enforced by rule `no-cross-module-internals` (ADR-0008).
- **Consumer-only test**: a structural test asserts the notifications module exposes no synchronous API to other modules — only event handlers.
- **Idempotency constraint**: `UNIQUE (event_id, subscriber_id, channel)` in the database, plus a double-delivery test.
- **Delivery-log completeness**: an integration test asserts that a failing provider produces a `messages` row with `status = 'failed'` and an error, rather than silence.
- **Provider port**: adding a channel requires implementing `MessagingProvider`; the interface is the contract, and a provider SDK imported outside `infrastructure/` fails lint.
- **Alert**: failed-message count above threshold raises an alert (ADR-0036).
