# ADR-0036: Observability

**Status:** Accepted
**Date:** 2026-08-02
**Accepted:** 2026-08-08 — ratified as wave W6 (infrastructure).

## Context

The most legitimate criticism of event-driven architecture is that failures surface asynchronously — sometimes long after the request that caused them. Since ADR-0026 commits to a transactional outbox and ADR-0027 to background jobs, an observability floor is not optional; it is the compensating control for that trade-off.

The predecessor's opposite failure is instructive: notification failures were swallowed (C11) and audit failures were swallowed (C10). Nothing surfaced, so nothing was fixed.

The deployment is a single VM. The most likely causes of an outage are, in rough order: a full disk, a memory exhaustion event (Chromium is the prime suspect, per ADR-0032), a failing `archive_command` silently stopping backups, and a stuck outbox relay.

## Decision

**Immediately (Phase 1):**

| Control | Detail |
|---|---|
| Structured logs | JSON, one line per event, with `request_id`, `correlation_id`, `organization_id`, `actor_id`, `route`, `status`, `duration_ms` |
| **Correlation propagation** | `correlation_id` is generated at the HTTP edge and written onto **every outbox event** and every downstream log line, so an asynchronous failure traces back to the request that caused it |
| Health endpoints | `/health` (process alive) and `/ready` (database reachable, migrations applied), wired to Docker health checks |
| External uptime check | Third-party, off-box, alerting on failure |
| **Disk-space alert** | The single most likely cause of death for a single-VM ERP |
| Error tracking | Sentry (self-hosted or free tier), with `correlation_id` attached |

**Phase 4:**

| Control | Trigger |
|---|---|
| **Dead-letter depth > 0 alert** | Non-negotiable once the relay moves out of the API process (ADR-0026) |
| **Outbox lag alert** | Age of the oldest `pending` row above threshold |
| **Backup-verification alert** | No successful restore drill result within N days (ADR-0031) |
| Failed-job and failed-message alerts | graphile-worker failures, notification delivery failures (ADR-0027, ADR-0028) |
| PostgreSQL metrics | Connections, slow queries, table and index bloat, autovacuum health, replication lag if applicable |
| Nightly consistency check alert | Cross-context orphaned identifiers (ADR-0013) |

**Deferred:** OpenTelemetry distributed tracing — introduced only once a second process exists to trace between, which is Phase 4 at the earliest. Also deferred: APM, real user monitoring, log aggregation beyond the host.

**Audit logs are not application logs.** Audit (ADR-0024) is a business record: append-only, permissioned, retained for years, written in-transaction. Logs are operational: sampled, rotated, mutable, no evidentiary weight. Never conflated.

## Consequences

**Positive**
- An asynchronous failure is traceable to its originating request via `correlation_id`, which is the specific mitigation for the EDA debuggability objection.
- The failure modes most likely to end the system (disk, backups) alert before they are fatal.
- Swallowed failures become impossible to sustain, because dead-letter depth is monitored.

**Negative / trade-offs**
- Structured logs are less pleasant to read directly than plain text; `jq` becomes part of the operational toolkit.
- Alerting requires somewhere to send alerts and someone to receive them. An alert nobody reads is worse than none, because it creates false confidence.
- Deferring tracing means cross-process debugging in Phase 4 relies on correlation identifiers in logs rather than spans. Accepted; the correlation identifier is the 80% solution.
- Self-hosted error tracking adds a service; the hosted free tier is preferred initially.

## Rejected alternatives

| Alternative | Why rejected |
|---|---|
| **Plain text logs** | Not queryable; correlating a request across API, worker, and notification delivery becomes manual reading. |
| **Full OpenTelemetry now** | Instrumentation cost with one process to trace. The correlation identifier gives most of the value at a fraction of the effort until a second process exists. |
| **A hosted APM suite from day one** | Cost and complexity disproportionate to a single-VM internal ERP. |
| **No alerting; check dashboards manually** | The predecessor's effective posture. Failures went unnoticed because nothing demanded attention. |
| **Logging to the database** | Couples observability to the component most likely to be the subject of an incident. |

## Enforcement

- **Logging middleware**: a request-scoped logger carries `request_id` and `correlation_id`; a log call outside that context is a lint error, so unstructured `console.log` cannot survive review.
- **Correlation propagation test**: an integration test asserts that a `correlation_id` set on an inbound request appears on the resulting outbox row and on the consumer's log line.
- **Health-check wiring**: `docker compose config` validation asserts every service declares a `healthcheck` (ADR-0032).
- **Alert-as-code**: alert definitions live in `infra/` and are reviewed as code, not configured by hand in a console.
- **Alert liveness**: a deliberately failing synthetic check runs monthly to confirm alerts actually reach a human — an untested alert is not an alert.
- **Backup alert**: driven by the restore-drill result row (ADR-0031), so an unverified backup raises an alert rather than being assumed good.
