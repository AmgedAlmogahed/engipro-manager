# ADR-0050: Frontend application stack for `apps/web`

**Status:** Accepted
**Date:** 2026-08-08

## Context

**No ADR in this set ever decided the frontend framework.** Forty-eight decisions were written covering the monorepo, the API, the data layer, authorization, workflow, deployment, and UI component standards — and the framework that renders all of it was never one of them.

It was nonetheless present in the repository, as an assumption inside an infrastructure document:

- `ADR-0032` specified `Dockerfile.admin` as `Next.js output:'standalone'`, configured `outputFileTracingRoot`, described copying `.next/static` and `public/` in the Dockerfile, and cited the Next.js standalone documentation.
- `ADR-0033` phrased a rejected alternative as "API mounted inside the Next.js app."

Neither statement was a decision. Both read as one to anybody who opened those files, and neither would ever be opened by somebody reviewing authorization or data.

**The evidence that it was inherited rather than chosen is the memory budget.** ADR-0032 allocated `admin | 512 MB` on a 6 GB box. Vercel's own self-hosting guidance for a production Next.js standalone server is 2–4 GB — between four and eight times the figure budgeted — on a box already committing 2 GB plus `shm_size: 2gb` to Chromium for PDF rendering. A framework that had actually been chosen would have had its footprint costed. This one was carried over from the predecessor, which used Next.js, and the number was never questioned.

Two further points of prior reasoning are relevant:

- `ADR-0004:41` already **rejected** Next.js in the backend role — "no natural home for cron, background workers, long-running PDF generation, or a partner API" — so the ADR set had reasoned against the framework in one role while silently assuming it in another.
- `ADR-0010:21` already specifies `orval` generating a **typed React Query client** from the OpenAPI contract, so the data-fetching layer was decided independently of the framework and constrains this choice.

The frozen prototype (ADR-0002) is a Vite SPA, but not one whose setup should be inherited: it uses `HashRouter`, Tailwind from a CDN `<script>`, and React imported from esm.sh through an import map. Those are prototype shortcuts, not a stack.

Under ADR-0004 the API is standalone and the frontend consumes it over HTTP; under ADR-0033 both are served from a single domain with no CORS. Nothing in the architecture requires the frontend to run a server.

## Decision

We will build `apps/web` as a **client-rendered single-page application**:

| Concern | Choice |
|---|---|
| Build tool | **Vite** |
| Routing | **React Router v7**, in declarative mode — browser history, not hash |
| Server data | **TanStack Query**, via the `orval`-generated client (ADR-0010) |
| Styling | **Tailwind CSS as a build-time dependency**, compiled by PostCSS in the Vite pipeline |
| Components | `packages/ui`, which owns `DataState` and status colour (ADR-0047) |
| Output | A static `dist/` directory — no Node server, no SSR, no server components |

Because the build output is static, the frontend is not a runtime service. ADR-0032 is amended accordingly: `Dockerfile.admin` becomes `Dockerfile.web` with the built `dist/` baked into the Caddy image, the `admin` service is removed from `docker-compose.prod.yml`, and roughly 450 MB returns to the memory budget.

**Server-side rendering is not required for this application.** `apps/web` is an authenticated internal ERP: every meaningful route sits behind a login, there is no crawler to serve, and no route benefits from being indexable. SSR's costs — a Node process to supervise and cap, a server/client execution boundary in every component, and a second place where authorization can be evaluated — are real, and its benefits do not apply here.

### Scope: this decision covers `apps/web` only

ADR-0001 anticipates a **customer portal**, a partner API, and a mobile app. A public-facing portal is exactly the case where SSR and a framework like Next.js are the right tool — public content, SEO, social previews, first-paint on unreliable mobile connections. This ADR takes **no position** on that application and must not be cited to reject Next.js for it. The shared contract types and `packages/ui` primitives cross that boundary; the rendering strategy does not have to.

## Consequences

**Positive**
- The deployment topology loses a supervised Node process, and the memory budget improves from roughly 1.5 GB to 1.95 GB of headroom — the only quantified benefit of this decision.
- No server/client boundary to reason about, so authorization is evaluated in exactly one place: the API. A second evaluation point is how the two authorization models in the predecessor's C1 came to disagree.
- Static assets are immutable and cacheable, and a rollback is an image tag.
- Build tooling stays simple for a 2–5 developer team, which ADR-0001 identifies as a real cost constraint.

**Negative / trade-offs**
- No SSR, so if a public surface is later added to *this* application rather than a separate one, it would need SSR retrofitted or a separate app. Accepted: ADR-0001 already anticipates the portal as its own deployable.
- First paint requires the JS bundle. Mitigated by code splitting per route and by this being an internal tool on known networks, but it is a real cost on a poor mobile connection.
- No streaming or server components, so a genuinely large table renders client-side. Pagination is already required by ADR-0021's scope-in-query rule.
- The team owns the routing and data-loading conventions that a full framework would have supplied.

## Rejected alternatives

| Alternative | Why rejected |
|---|---|
| **Next.js (the inherited assumption)** | Its memory footprint is 4–8× what ADR-0032 budgeted, on a 6 GB box already dominated by Chromium. It adds a server process with nothing to do — the API is standalone per ADR-0004, whose own rejection of Next.js API routes still applies. Server components introduce a second place authorization could be evaluated. For an entirely authenticated internal ERP, SSR's benefits do not apply. |
| **Remix / React Router in framework mode** | Same objection at smaller scale: it wants a server for loaders and actions, and there is no work for that server to do when a standalone API already owns the contract. Using React Router in declarative mode keeps the routing library without adopting a server runtime. |
| **Keep the prototype's setup and grow it** | `HashRouter` produces unshareable URLs and breaks server-side route matching; CDN Tailwind ships an unpurged runtime compiler; the esm.sh import map means dependencies are resolved at request time, which is the exact class of failure ADR-0032 exists to eliminate. The screens are worth mining; the setup is not. |
| **Tailwind via CDN, as in the prototype** | Unpurged, unversioned, and a network dependency at page load. Tailwind is a build dependency so the output is purged and pinned by the lockfile. |
| **A separate SPA per persona (sales, finance, admin)** | Three deployables and three auth sessions for one internal tool. Personas differ by permissions, which ADR-0021 already resolves at runtime; they do not need separate applications. |
| **Deciding this implicitly, as before** | The status quo. It produced a framework nobody chose, a memory budget off by up to 8×, and an assumption living where no reviewer of authorization or data would encounter it. |

## Enforcement

- **No-CDN build assertion**: the built `index.html` must contain no `<script src="http…` and no `<script type="importmap">`. Fails the build. This mechanically prevents the prototype's CDN-Tailwind and esm.sh shortcuts from reaching `apps/web`, and is asserted in ADR-0032's image build as well, since that is what produces the artefact.
- **Router pinned**: a lint rule bans importing `HashRouter`, so shareable URLs cannot silently regress. Browser history is the only routing mode.
- **No server runtime**: `apps/web`'s `package.json` declares no `start` script and no server framework dependency. A dependency-cruiser rule (ADR-0008) fails on any server-side framework import from `apps/web`.
- **Tailwind is a build dependency**: present in `devDependencies` with a PostCSS config; a lint rule fails on a Tailwind `<script>` or `<link>` to an external host in any HTML entry point.
- **Bundle budget in CI**: an initial-route JS budget is asserted, failing the build when exceeded, so the absence of SSR does not quietly become a slow first paint.
- **Generated client only**: hand-written `fetch` calls to `/api/*` from component code fail lint. All server access goes through the `orval`-generated TanStack Query client (ADR-0010), so contract drift is a codegen diff rather than a runtime surprise.
- **`DataState` compliance** (ADR-0047): a data-bearing view that does not use the `DataState` primitive fails lint — the mechanism that keeps C8 from recurring.
- **This ADR is the citation for the framework.** ADR-0032 and ADR-0033 now reference it rather than naming a framework themselves, so the decision lives in exactly one place.
