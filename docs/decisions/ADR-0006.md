# ADR-0006: Hexagonal architecture — outbound ports only

**Status:** Accepted
**Date:** 2026-08-02
**Accepted:** 2026-08-08 — ratified as wave W2 (architecture shape).

## Context

Cockburn's original intent for hexagonal architecture was to let the application be driven by tests, scripts, or a UI interchangeably, and to stop the database bleeding into business logic. In practice, teams applying it uniformly report file-count multiplication of 4–6× for CRUD operations, with inbound port interfaces that have exactly one implementation, per-layer DTO duplication, and separate persistence models.

The practical decision rule that emerges from the critiques: hexagonal pays when **outbound** targets are multiple and volatile; layered is cheaper when there is one inbound protocol and one outbound technology.

Our outbound list is long and volatile: PostgreSQL, object storage, WhatsApp, PDF/Chromium rendering, email, payment gateways, accounting systems, and government tender portals (Etimad/Fursa). Our inbound list is one item: HTTP.

## Decision

We will apply hexagonal architecture **on the outbound side only**.

```
apps/api/src/modules/<module>/
├─ domain/          entities, value objects, policies, state machines, events — plain TS
├─ application/     use-cases + OUTBOUND ports (repository, storage, pdf, publisher, notifier)
├─ infrastructure/  adapters — the only place vendor SDKs are legal
└─ interface/http/  controller: authorize → call use-case → map response
```

Controllers call use-cases **directly**. There are no inbound port interfaces.

## Consequences

**Positive**
- Every vendor is swappable by writing one adapter and changing one line in the module's composition file. This is what makes ADR-0032's "portable deployment" claim true rather than aspirational.
- Domain logic is testable with no database, no HTTP, and no container (ADR-0009).
- Roughly half the ceremony of full hexagonal, with the protection concentrated where volatility actually is.

**Negative / trade-offs**
- If a second inbound protocol appears (a batch importer, a WebSocket surface, a message-driven entry point), controllers and that new driver will both call use-cases directly, duplicating a little orchestration. Acceptable; introduce inbound ports at that point, not before.
- Still adds files relative to controller→service→ORM: a port interface and an adapter per outbound dependency. Mitigated by ADR-0007, which exempts Thin-tier modules entirely.

## Rejected alternatives

| Alternative | Why rejected |
|---|---|
| **Full hexagonal (inbound + outbound ports)** | Inbound ports with a single implementation are the primary documented over-engineering pattern. One HTTP protocol does not justify the indirection. |
| **No ports at all (service calls ORM directly)** | This is the predecessor's structure. It leaves no place for business rules other than inside services that also perform I/O, which is the root cause of C3, C4, C5, and C12, and makes vendor changes a codebase-wide edit. |
| **Ports only around the database** | Under-protects. WhatsApp providers, payment gateways, and accounting integrations are the ones most likely to change, and they are exactly where vendor shapes leak into domain types. |

## Enforcement

- **dependency-cruiser** rule `no-vendor-in-domain-or-application`: `domain/` and `application/` may not import `@nestjs/*`, `drizzle-orm`, `@prisma/*`, `@aws-sdk/*`, `playwright`, or any other vendor SDK. Blocking in CI.
- **Purity check in CI**: `packages/domain` must typecheck with only TypeScript present. A job removes all other `node_modules` entries and runs `tsc --noEmit` on it.
- **Test-shape check**: domain unit tests declare no test container and no database fixture (ADR-0009). A test under `domain/` that imports the DB harness fails lint.
- **Convention**: every port interface lives in `application/ports/` and its adapter in `infrastructure/`; a dependency-cruiser rule forbids `application/` from importing anything under `infrastructure/`.
