# ADR-0014: Standard table conventions and migration lint

**Status:** Proposed
**Date:** 2026-08-02
**Added beyond the supplied decision set** — several other ADRs (money, tenancy, soft delete, audit, primary keys) state "migration lint enforces this." That lint needs one definition and one home rather than being asserted five times.

## Context

Multiple decisions in this set are only real if they are applied to **every** table, including tables added months from now by someone who has not read the ADRs. The predecessor demonstrates the failure: its documented deduplication rule was never expressed as a unique constraint (C7), and its stated no-deletion policy coexisted with hard-delete endpoints (C22). Both were policies without mechanisms.

A convention that is checked by a human at review time is a convention that will eventually be missed.

## Decision

Every table in a business schema will carry these columns:

```sql
id              uuid        PRIMARY KEY,        -- UUIDv7 (ADR-0015)
organization_id uuid        NOT NULL,           -- tenancy (ADR-0017)
created_at      timestamptz NOT NULL DEFAULT now(),
updated_at      timestamptz NOT NULL DEFAULT now(),
created_by      uuid,                           -- null only for system-created rows
deleted_at      timestamptz                     -- soft delete (ADR-0023)
```

Exempt by declaration: `platform.outbox_events`, `audit.*`, `platform.business_counters`, and graphile-worker's own tables. Exemptions live in an explicit allow-list in the lint configuration, not in reviewers' heads.

We will write a **migration lint** that runs against generated SQL in CI and fails on:

| Rule | Rationale |
|---|---|
| `CREATE TABLE` in a business schema without the six base columns | ADR-0015, 0017, 0023 |
| Any `float`, `double precision`, or `money` column | ADR-0016 |
| A monetary column not `numeric(19,4)`, or a rate column not `numeric(5,4)` | ADR-0016 |
| A `REFERENCES` crossing schemas (except `organization_id`) | ADR-0013 |
| A new table without an index on `organization_id` | ADR-0017 |
| A unique constraint on a soft-deletable table that is not a partial index `WHERE deleted_at IS NULL` | ADR-0023 |
| `DROP COLUMN`, `DROP TABLE`, or a type narrowing without an `expand-contract` label on the PR | ADR-0014 (below) |
| `CREATE SEQUENCE` used for a business number | ADR-0025 |

Destructive schema changes follow **expand → migrate → contract** (Fowler's Parallel Change): add the new shape, backfill, dual-write, switch reads, drop the old shape. Four PRs, zero downtime.

## Consequences

**Positive**
- Every other data ADR gains a real enforcement point instead of an intention.
- A new table cannot silently miss tenancy, soft delete, or audit columns.
- Destructive migrations become deliberate and labelled rather than accidental.

**Negative / trade-offs**
- Six columns on every table costs storage and index space. Negligible at this scale; recorded for honesty.
- The lint needs maintenance as conventions evolve, and a badly written rule blocks legitimate work. Rules must be specific and their allow-lists explicit.
- Expand-contract turns a one-line column rename into four deployments. That is the point, but it is real friction.

## Rejected alternatives

| Alternative | Why rejected |
|---|---|
| **Code review as the check** | Demonstrably insufficient — C7 and C22 are both "the policy was written down and not applied." |
| **Base entity class in the ORM only** | Catches tables created through the ORM, misses raw SQL migrations, and does not catch column *types*. |
| **Database event triggers enforcing DDL policy** | Powerful but opaque; failures appear at migration time with poor messages, and the rules become invisible to developers reading the repository. |
| **No conventions; decide per table** | Guarantees inconsistency, and makes tenancy and soft-delete filters unreliable across the codebase. |

## Enforcement

This ADR **is** an enforcement mechanism. Its own enforcement:

- **CI job `migration-lint`**, blocking, run against every new migration file in a PR's diff.
- **Test**: the lint has its own unit tests containing deliberately non-compliant DDL fixtures, so a regression in the linter is caught.
- **PR label gate**: `DROP`/narrowing statements require an `expand-contract` label; the CI job checks the label via the API and fails without it.
- **Drift check**: a nightly job introspects the live schema and asserts every business table matches the convention, catching anything applied outside the migration pipeline.
