# ADR-0037: CI/CD pipelines

**Status:** Accepted
**Date:** 2026-08-02
**Accepted:** 2026-08-08 — ratified as wave W1b (machinery).

**Rider — staged activation.** Most stages above have no subject yet: there are no migrations, no test suites, no permission model, no Dockerfiles, no eslint config. Those stages are declared in `.github/workflows/pr.yml` as **commented-out stages carrying their ADR reference**, and the rule is:

> **The PR that lands a subject activates its stage.**

**No stage may sit green against a nonexistent target.** A check that passes because it matched nothing is indistinguishable from a check that passes because the code is correct. This is not hypothetical — ADR-0019 and ADR-0047 had scoped the RTL directional-utility lint to `apps/admin`, a directory that will never exist, so that rule would have matched nothing and reported green while Arabic-first layouts broke. Two consequences of the rider:

- The `workspace` job is **active and red** until the lockfile exists, failing with a message that names the cause, rather than being skipped and looking green. *(Resolved 2026-08-08: lockfile committed, pnpm 10.0.0 via corepack.)*
- `tools/dependency-cruiser.test.sh` asserts the real cruise examines **more than zero modules** once a subject exists, because `0 modules cruised` also exits 0.

**Rider — branch protection grows in lockstep.** Required status checks cannot reference a check that has never reported. `main` is protected first with PR-required, direct pushes disabled and force-pushes blocked; individual checks join the required list as they come online. The ruleset is exported to `.github/rulesets/main.json` so protection is reviewable as code, consistent with this ADR's own "pipeline definitions in version control".

## Context

Nearly every other ADR in this set names a CI check as its enforcement mechanism. Without a defined pipeline, those enforcement claims have no implementation.

The predecessor's deployment was a manual runbook (ADR-0032), so there was no gate between a developer's intent and production. The first production PDF request failed because no smoke test existed.

## Decision

Three pipelines.

### PR pipeline (blocking)

```
install            pnpm --frozen-lockfile, cached
lint               eslint (incl. boundaries, role-literal, money-arithmetic, RTL rules)
typecheck          tsc --noEmit across the workspace
boundaries         depcruise apps packages --config tools/.dependency-cruiser.js
contract codegen   regenerate client + OpenAPI, then git diff --exit-code
openapi diff       vs main; breaking changes posted as a PR comment
migration lint     base columns, money types, cross-schema FKs, RLS policy, sequences
domain purity      packages/domain typechecks with only TypeScript present
unit + use-case    no database
integration        real PostgreSQL service container
role-matrix suite  every (role × endpoint × scope), incl. IDOR probes
state-machine suite every legal/illegal transition, reason requirements
c-number coverage  every C-number claimed "prevented" has a matching test
docker build       --platform linux/arm64, no push
trivy              container and dependency scan
gitleaks           secret scan
```

### `main` pipeline

```
… all PR checks …
docker buildx build --platform linux/arm64 --push
deploy: docker compose pull && up -d
health-check loop  wait for /ready on every service
post-deploy smoke  authenticate, then issue one quotation PDF and assert a valid PDF
rollback           on any failure, redeploy the previous image tag
```

### Nightly pipeline

```
restore drill            restore latest backup into a throwaway container, run integration
                         suite, record duration and outcome (ADR-0031)
consistency check        cross-context orphaned identifiers (ADR-0013)
schema drift check       live schema matches conventions (ADR-0014)
dependency audit         pnpm audit
```

**CI runs on native ARM runners** where available; arm64 Chromium layers under QEMU emulation are prohibitively slow (ADR-0032).

## Consequences

**Positive**
- Every architectural rule has a place to be checked, so ADRs stop being advisory.
- The post-deploy smoke test is precisely the control whose absence produced the predecessor's first-request PDF failure.
- Rollback is automatic on health-check failure rather than a manual scramble.
- The nightly restore drill makes an untested backup impossible to sustain.

**Negative / trade-offs**
- The PR pipeline is long. Mitigated by Turborepo caching and by running fast checks first so failures surface early, but a full run will take minutes.
- A flaky integration test blocks all merges; flakes must be fixed or quarantined immediately, not tolerated.
- Committed generated artefacts (client, OpenAPI) create merge conflicts on concurrent contract changes. Accepted — the `git diff --exit-code` check is what prevents drift (ADR-0010).
- Native ARM runners may cost more or be less available than x86.

## Rejected alternatives

| Alternative | Why rejected |
|---|---|
| **Manual deployment** | The predecessor. Produces snowflakes and skips every gate. |
| **Deploy on every merge without a smoke test** | Health checks confirm the process is alive, not that it works. Chromium was installed but unusable in the predecessor; only an end-to-end PDF request would have caught it. |
| **Warning-only lint and boundary checks** | Warnings accumulate and are ignored. C1–C23 is what a codebase of ignored warnings looks like. |
| **x86 CI with QEMU for arm64** | Emulated Chromium download and extraction makes build times unacceptable. Acceptable only as a fallback. |
| **Blue-green or canary deployment now** | Docker Compose does not provide it natively; Kamal is the escalation path when zero-downtime becomes a requirement (ADR-0032). |

## Enforcement

This ADR **is** the enforcement layer. Its own enforcement:

- **Branch protection** on `main`: every check above is a required status check; direct pushes are disabled.
- **Pipeline definitions in version control** under `.github/workflows/`, reviewed as code.
- **Self-test**: the migration lint and the boundary configuration have their own unit tests with deliberately non-compliant fixtures, so a broken checker is caught rather than silently passing everything.
- **Phase 1 exit criterion**: a deliberately introduced boundary violation must fail the PR pipeline. Until demonstrated, the pipeline is unverified (ADR-0008).
- **Drill result**: the nightly restore drill writes a result row; its absence raises an alert (ADR-0036), so a silently broken pipeline is visible.
