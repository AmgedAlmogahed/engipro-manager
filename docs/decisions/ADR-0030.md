# ADR-0030: Reporting strategy

**Status:** Proposed
**Date:** 2026-08-02

## Context

The ERP will need reporting: lead source performance by channel, pipeline funnel and conversion rates, rep targets versus actuals, win/loss analysis with reasons, quotation turnaround by department, project progress against plan, government transaction ageing, licence status across projects, revenue recognised and invoiced, collections and overdue ageing, commission payouts.

Two risks pull in opposite directions:

1. **Reports hammering operational tables.** A CSV export that scans the whole quotations table can lock or starve user-facing queries on a shared single-instance PostgreSQL (ADR-0012).
2. **Premature CQRS.** Building separate read models, projections, and rebuild logic before any query is measurably slow adds months of work and permanent complexity for no measured benefit.

Schema-per-context (ADR-0013) adds a specific constraint: a report spanning CRM, Sales, and Finance cannot be a simple join, because cross-context joins are forbidden.

## Decision

We will adopt reporting **incrementally, by measured need**:

1. **Now (Phase 1–3):** reports query operational tables directly through a **Reporting module** that owns them. Reporting is read-only and never writes.
2. **Phase 5:** **materialized views** owned by the `reporting` schema, refreshed on a schedule via graphile-worker. This is the default answer for anything expensive.
3. **Deferred:** full CQRS with event-sourced read models, introduced **only** when a specific query exceeds roughly 200 ms under real load and a materialized view cannot solve it.
4. **Deferred:** a read replica, introduced when reporting load measurably affects operational latency.

**The permanent rule** — reporting is the *only* module permitted to read across context boundaries, and it does so through views it owns in the `reporting` schema, never by joining another module's tables directly from application code. Scope applies: a user sees reports over the rows they are permitted to see (ADR-0021).

## Consequences

**Positive**
- No speculative infrastructure. The first reports ship in days rather than after a projection framework exists.
- Materialized views are a small, well-understood step that solves most ERP reporting without a paradigm change.
- Because events accumulate from day one (ADR-0026), event-sourced read models remain available later without needing history to be reconstructed.

**Negative / trade-offs**
- Phase 1–3 reports do query operational tables, which is the risk named above. Mitigated by the SLO measurement loop (ADR-0041) making the moment to escalate visible rather than a matter of opinion.
- Materialized views are stale between refreshes. For daily, weekly, and monthly reporting cadences this is acceptable; it must be shown in the UI as "as of <timestamp>".
- The reporting module's cross-context read privilege is a deliberate exception to ADR-0013 and must be visibly bounded, or it becomes the hole through which the boundary rules erode.

## Rejected alternatives

| Alternative | Why rejected |
|---|---|
| **Full CQRS with event-sourced read models from day one** | The literature is close to unanimous that this is premature for MVPs and internal tools: an event store, projection rebuild logic, eventual consistency everywhere, and specialised debugging, for no measured benefit. |
| **A BI tool (Metabase, Superset) pointed at the operational database** | Puts arbitrary unreviewed queries against production tables with no scope enforcement — an authorization hole and a performance risk simultaneously. Revisit against a read replica with row-level scope applied. |
| **A data warehouse** | Disproportionate before there is stable data or a stakeholder asking questions the ERP cannot answer. |
| **Letting each module build its own reports** | Produces N inconsistent definitions of "conversion rate" and pushes cross-context joins into business modules. |
| **Permanently allowing reports on operational tables** | The failure mode named in the problem statement; acceptable as a starting point, unacceptable as the end state. |

## Enforcement

- **Module ownership**: only `apps/api/src/modules/reporting/` may declare cross-context read access; dependency-cruiser has an explicit, narrow exception for it, so the exception is visible in configuration rather than implicit.
- **Read-only guarantee**: the reporting module's database role has `SELECT` only. A write attempt fails at the database, asserted by an integration test.
- **Scope**: report queries take the same `ScopeContext` as any other repository call (ADR-0021); the role-matrix suite includes report endpoints.
- **Escalation trigger**: the SLO dashboard (ADR-0041) tracks p95 duration per report endpoint. Crossing the threshold opens the decision to introduce a materialized view — the trigger is measured, not argued.
- **Staleness disclosure**: a contract test asserts every materialized-view-backed response includes an `as_of` timestamp.
- **Traceability**: every report figure must link to the records it aggregates; a review checklist item, with **no mechanical enforcement** — recorded honestly as a gap.
