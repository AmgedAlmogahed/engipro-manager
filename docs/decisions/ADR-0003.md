# ADR-0003: Prior-art mining protocol

**Status:** Accepted
**Date:** 2026-08-02
**Accepted:** 2026-08-08 — ratified as wave W1b (machinery). Both enforcement scripts are landed and running in CI: `tools/check-mining-docs.sh` (clause 1, the changed-file gate) and `tools/check-cnumber-coverage.sh` (clause 4, the `c<NN>-*.spec.ts` naming check). `docs/mined/TEMPLATE.md` carries the fixed sections required by clause 3.

**Note on the deliverable.** The client intends to extend this system with their own modules (HR and accounting are expected), so the module-structure material derived from this protocol is **deliverable-facing documentation, not internal-only**. A mining document written for our own benefit and a mining document a third-party developer can follow are the same artifact; write them as the latter.

## Context

We have two prior-art systems and no foundation:

- `ABAK_ERP/` — a NestJS + Prisma + Next.js ERP that was built and deployed to an OCI ARM box but never carried production data. It contains real business knowledge: a machine-readable blueprint (`blueprint/abak/*.json`), workflow documents (`docs/flows/`), a service catalogue with required client documents per service, persona and role-matrix documents, and — most valuably — a **diagnosed defect register** (`blueprint/abak/99-conflicts.md`, C1–C23) with severities and `file:line` references.
- The frozen prototype (ADR-0002) — validated workflow and UX behaviour.

Spolsky's argument against rewrites is that they discard knowledge accumulated in the old code. That argument applies to "start fresh and ignore the old system." It does not apply to "extract the knowledge into artifacts first, then build from the artifacts" — provided the extraction actually happens.

The failure mode we are guarding against is the old repository becoming a *hidden source of truth*: a developer with it open in a second window, copying structure by osmosis while believing they are designing fresh.

## Decision

We will mine both prior-art systems into written artifacts **before** writing domain code, using this protocol:

1. **No new domain code for a module until `docs/mined/<module>.md` exists.**
2. Neither old repository is a workspace member. No path aliases, no imports, not in `pnpm-workspace.yaml`. They are read as files, never linked.
3. Each mining document uses a fixed template capturing: observed behaviour in both systems; a verdict table (Keep / Modify / Reject with reasons); the module's C-numbers from the conflict register quoted verbatim; the new Zod contract; the new state machine; and **the tests that prevent each old failure**.
4. **Characterization tests** are written against known-good workflows of the old system, each **tagged with its C-number status**, so that known defects are not faithfully re-encoded as "correct" behaviour.
5. Every `Reject` verdict gets a line in an ADR, so that "why is there no Lead table?" is answerable in eighteen months.

Mining order follows dependencies: Identity/Access/Org → CRM → Sales → Delivery → Finance.

Initial documents: `docs/mined/{identity,clients,quotations,rfq,deployment}.md`. `deployment.md` is unusual — every manual step in the old `DEPLOY.md` is recorded as an *anti-requirement* whose answer is a Dockerfile line (ADR-0032).

## Consequences

**Positive**
- Business knowledge survives the rebuild in a reviewable form rather than in one person's memory.
- The defect register becomes a test suite instead of a document, which is the whole value of having it.
- The "why did we do it this way" question has a written answer for every module.

**Negative / trade-offs**
- Slower start per module — roughly a day of mining before implementation begins.
- Mining documents can go stale after implementation. Mitigated by treating them as historical records of a decision point, not living documentation.
- Characterization tests capture bugs as faithfully as correct behaviour; the C-number tagging is mandatory, not optional, or this step actively harms.

## Rejected alternatives

| Alternative | Why rejected |
|---|---|
| **Read the old code while writing new code** | The precise mechanism by which prior art becomes a hidden source of truth. Structure gets copied unconsciously. |
| **Port the old code module by module** | Inherits the flat controller→service→Prisma structure that has no place for business rules, which is the root cause of C3, C4, C5, and C12. |
| **Skip mining, design purely from the flowchart** | Discards the defect register, the service catalogue, the role matrix, and the validated prototype behaviour — the most expensive knowledge in the project. |
| **Import the old repo as a workspace package for reference** | Makes accidental imports possible and puts old types in scope for autocomplete. |

## Enforcement

- **CI check**: a PR that adds or modifies files under `apps/api/src/modules/<x>/domain/` fails if `docs/mined/<x>.md` does not exist. Implemented as a script over the PR's changed-file list.
- **PR template**: a required checkbox — "mining doc exists and its C-numbers have tests."
- **Workspace exclusion**: neither old repo appears in `pnpm-workspace.yaml` or any `tsconfig` `paths` entry, so imports do not resolve.
- **Test naming convention**: characterization tests are named `c<NN>-<description>.spec.ts`; a CI script asserts that every C-number marked "prevented" in a mining doc has at least one matching test file.
