# ADR-0020: Identity owned in-house

**Status:** Proposed
**Date:** 2026-08-02

## Context

The system will authenticate four distinct actor types: staff users, customer users (a future booking portal), partner API clients, and system/service actors such as the worker.

Delegating identity to a hosted provider is fast to start. The cost is that **your user identifiers become the vendor's identifiers**, and every foreign key in the system then points at a value you do not control. Migrating away later means remapping identity across every table — among the most expensive migrations that exists.

The predecessor already owned its identity (JWT access tokens with refresh tokens in a `refresh_tokens` table, bcrypt hashing). That part was sound and is retained by re-derivation rather than inheritance.

Note on hashing: bcrypt is a native module, which adds an arm64 build consideration (ADR-0032). Argon2id is both the stronger algorithm and avoids that concern.

## Decision

We will **own identity**. Our user identifiers are ours.

- **Access token**: JWT, ~15 minutes, carrying `sub`, `organization_id`, `actor_type`, `session_id`, `permissions_version`. It does **not** carry the permission list — that grows past sensible header sizes and goes stale the moment an administrator revokes a grant.
- **Refresh token**: opaque, rotating, stored server-side, revocable. Reuse of a rotated token invalidates the whole family (theft detection).
- **Transport**: httpOnly + Secure + SameSite=Lax cookies for the web (ADR-0033 makes this simple by keeping one domain); secure device storage for mobile; no refresh tokens for partner clients, which use client credentials.
- **Password hashing**: **argon2id** with parameters recorded in configuration.
- **Permissions** are resolved server-side per request from a cache keyed by `(userId, permissions_version)`; bumping the version invalidates immediately.
- If a hosted identity provider is ever adopted, it goes behind an `IdentityProvider` **port** with our own `identity.users` row keyed by the external subject identifier. The external identifier is an attribute, never a primary key.

## Consequences

**Positive**
- No vendor owns the identifier that every foreign key in the system depends on.
- Actor types, `permissions_version`, and partner API keys fit the model naturally rather than being bent around a provider's schema.
- Session revocation is immediate and under our control.
- Argon2id removes a native-module dependency from the arm64 build.

**Negative / trade-offs**
- We build and maintain password reset, email verification, MFA, session management, and lockout. That is real work, and getting it wrong is a security incident.
- No free social login, SSO, or SCIM. Those become projects if required.
- Token rotation and family invalidation need careful implementation and testing.

## Rejected alternatives

| Alternative | Why rejected |
|---|---|
| **Hosted identity provider as source of truth** (Auth0, Clerk, Supabase Auth, Cognito) | User identifiers become the vendor's, making later migration a remap of every foreign key. Also awkward to express `actor_type`, `permissions_version`, and partner keys. |
| **Permission list inside the JWT** | Grows unboundedly, and stale until expiry — an administrator revoking access would not take effect for up to the token lifetime. `permissions_version` gives immediate invalidation instead. |
| **Long-lived access tokens without refresh** | No revocation path short of a denylist, which reintroduces server state anyway. |
| **bcrypt** | Weaker than argon2id and a native module that complicates arm64 builds. Not wrong, just second-best on both axes. |
| **Session cookies with server-side sessions only** | Workable, but a stateful lookup on every request and awkward for the future mobile and partner surfaces. |

## Enforcement

- **Startup validation**: the API refuses to boot in production without a strong `JWT_SECRET` (minimum length enforced, dev fallback value explicitly rejected). This behaviour is inherited deliberately from the predecessor's `env.validation.ts`, which got it right.
- **Test suite**: refresh-token rotation tests assert that reusing a rotated token invalidates the family; access-token tests assert `permissions_version` mismatch forces re-resolution.
- **Lint**: `@nestjs/jwt` and any auth library are permitted only in the identity module's `infrastructure/` (ADR-0008 rule 2).
- **Contract**: `actor_type` is a required claim; a token missing it fails validation rather than defaulting to staff.
- **Secrets**: `JWT_SECRET` and the argon2 parameters are managed per ADR-0035; a secret in a committed file fails the secret-scanning CI step.
