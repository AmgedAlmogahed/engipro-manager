# ADR-0023: Soft deletes

**Status:** Proposed
**Date:** 2026-08-02

## Context

The business process explicitly requires records not to be destroyed: a project is never deleted, only cancelled with a reason; a disqualified lead keeps its full history; a quotation cannot be deleted, only moved to Won, Lost, or Postponed.

The predecessor stated this policy and violated it — C22 records hard-delete endpoints for interactions, opportunities, and client notes, directly contradicting the documented no-deletion rule. It also failed to enforce deduplication (C7) because a plain unique index would have collided with archived rows, and the constraint was simply never added.

Soft deletion has real, well-argued costs: the `deleted_at IS NULL` predicate leaks into every query, foreign keys still resolve to soft-deleted rows, and it does not simplify a right-to-erasure request.

## Decision

We will use **soft deletes everywhere in business schemas**.

- `deleted_at timestamptz` on every business table (ADR-0014).
- A **default query filter** in the repository base applies `deleted_at IS NULL`; including archived rows requires an explicit, named method (`…IncludingArchived`).
- **All unique constraints are partial indexes**:
  ```sql
  CREATE UNIQUE INDEX clients_phone_active
    ON crm.clients (organization_id, normalized_phone)
    WHERE deleted_at IS NULL;
  ```
  This is simultaneously the fix for C7 (deduplication was never enforced) and the reason a plain unique index would not have worked.
- **The application database role has no `DELETE` grant** on business tables. A hard delete is not possible through the application, regardless of code.
- Erasure for a legal right-to-be-forgotten request is a separate, deliberate, audited administrative operation performed by a different role — not an application feature.

## Consequences

**Positive**
- The no-deletion business rule is enforced by database privileges rather than by developer discipline. C22 cannot recur.
- Deduplication is enforced at the database level and coexists with archived records — C7 is fixed by the same mechanism.
- History for audit and dispute resolution is intact.

**Negative / trade-offs**
- The filter must be applied everywhere. A default in the repository base hides it from the reader — a genuine criticism — but omitting the default guarantees eventual leakage of archived rows. The default is chosen as the lesser risk, with the explicit `…IncludingArchived` naming making the exception visible.
- Cross-context identifiers can point at soft-deleted rows; the nightly consistency check (ADR-0013) reports these.
- Tables accumulate rows. On a CRM with dormant leads this degrades index scans over time; revisited if measured.
- Right-to-erasure is *more* complex, not less, because deletion is deliberately hard.

## Rejected alternatives

| Alternative | Why rejected |
|---|---|
| **Hard deletes** | Contradicts a stated business rule and destroys the audit trail the ERP exists to provide. |
| **Archive table (move rows on delete)** | Cleaner steady-state, but every "restore" and every historical query becomes a union across two tables, and foreign keys break at the moment of the move. |
| **`deleted_records` side table holding JSONB copies** | A defensible alternative that keeps main tables clean. Rejected for now because undo and "show archived" are ordinary product features here, and querying them from JSONB is worse. Revisit if table growth becomes a measured problem. |
| **A `status = 'ARCHIVED'` value instead of `deleted_at`** | Conflates lifecycle status with existence, which is the same category error as C20 (VIP as a lifecycle status). Archival must be orthogonal to business status. |

## Enforcement

- **Database grant**: the application role receives `SELECT, INSERT, UPDATE` on business tables and **not** `DELETE`. Asserted by a startup check and by an integration test that attempts a delete and expects a privilege error.
- **Migration lint** (ADR-0014): a unique constraint on a soft-deletable table that is not a partial index `WHERE deleted_at IS NULL` fails CI. A business table without `deleted_at` fails CI.
- **Repository base**: the default filter is implemented once; a repository that bypasses the base helper fails a structural test.
- **Dedupe test**: an integration test creates, archives, and recreates a client with the same phone number, asserting the archived row does not block the new one and a second *active* row does.
- **Erasure runbook**: documented, uses a separate role, and writes an audit entry (ADR-0024).
