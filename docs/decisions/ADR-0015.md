# ADR-0015: Primary keys — UUIDv7

**Status:** Proposed
**Date:** 2026-08-02
**Added beyond the supplied decision set** — primary key type is among the most expensive decisions to retrofit (it propagates to every foreign key, index, and API response), and it was not covered. ADR-0025 covers human-facing business numbers, which are a separate concern.

## Context

Three properties matter for this system:

1. **Cross-context references without foreign keys** (ADR-0013) means identifiers travel between schemas and, later, potentially between services. They must be globally unique, not per-table sequences.
2. **Identifiers appear in URLs and API responses.** Sequential integers leak row counts and invite enumeration — a direct enabler of the IDOR class of bug the predecessor exhibited (C21).
3. **Index locality matters.** Random UUIDv4 primary keys cause B-tree page splits and index fragmentation on insert-heavy tables.

UUIDv7 is time-ordered in its high bits, which restores insert locality while keeping global uniqueness and non-enumerability.

## Decision

We will use **UUIDv7 for all primary keys**, generated in the application layer, stored as PostgreSQL `uuid`.

- Generated by the application, not the database, so an entity has its identity before it is persisted — required for aggregates that emit events referencing themselves before commit (ADR-0026).
- Business numbers (`CLIENT-2026-0042`) are a **separate, additional** human-facing identifier with different rules (ADR-0025). Primary keys are never shown as the primary reference in the UI.
- Foreign keys and cross-context identifier columns are `uuid`.

## Consequences

**Positive**
- Identity exists before persistence, which simplifies event emission and aggregate construction.
- No enumeration risk in URLs; combined with ADR-0021's scope checks, IDOR requires guessing a 128-bit value *and* passing authorization.
- Time-ordering keeps index insert locality close to a sequential key, avoiding UUIDv4's fragmentation.
- Merging data from another environment or a future service cannot collide.

**Negative / trade-offs**
- 16 bytes versus 8 for `bigint`, on every primary key, foreign key, and index. Immaterial at this scale.
- UUIDv7 creation timestamps are weakly inferable from the identifier. Acceptable — `created_at` is already on every row (ADR-0014).
- Requires a UUIDv7 library until PostgreSQL's native `uuidv7()` is universally available in the deployed version; generating in the application sidesteps the version dependency entirely.
- Less readable in logs and psql than integers. Mitigated by business numbers for anything a human discusses.

## Rejected alternatives

| Alternative | Why rejected |
|---|---|
| **`bigserial` / sequential integers** | Enumerable in URLs, leaks volume, collides across contexts and environments, and requires a round trip to the database to learn an entity's identity. |
| **UUIDv4** | Loses insert locality; measurable index fragmentation and page splits on write-heavy tables over time. |
| **`cuid` / `nanoid` (text)** | Text primary keys are larger in indexes and lose native `uuid` type checking. `cuid2` explicitly does not guarantee sortability. |
| **Composite `(organization_id, id)` primary keys** | Complicates every foreign key and ORM mapping for a benefit already provided by the tenancy predicate and RLS (ADR-0017, ADR-0022). |
| **Business number as primary key** | Couples the physical key to a business format that may change, and business numbers are allocated transactionally (ADR-0025), which would serialise all inserts. |

## Enforcement

- **Migration lint** (ADR-0014): `CREATE TABLE` in a business schema whose `id` column is not `uuid PRIMARY KEY` fails.
- **Base table helper** in `packages/database` supplies the standard column set, so the correct type is the default path.
- **Domain type**: `packages/domain` exports branded identifier types (`ClientId`, `QuotationId`) so an identifier from one context cannot be passed where another is expected — a compile error rather than a runtime mismatch.
- **Generation location test**: a unit test asserts entities can be constructed with a valid identity without any database, proving generation is in the application layer.
