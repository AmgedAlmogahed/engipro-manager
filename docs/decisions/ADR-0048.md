# ADR-0048: Ubiquitous language and naming

**Status:** Accepted
**Date:** 2026-08-02
**Accepted:** 2026-08-08 — pulled forward from W7 and ratified at the domain-code threshold, which is the trigger this ADR sets for itself.

**Installed and live-fired.** `docs/glossary.md` is mined from `ABAK_ERP/blueprint/abak/00-glossary.md` and resolves the drift that document recorded against itself: the predecessor's glossary carried a `DRIFT:` column noting three names for one concept and a model called `ServiceCategory` used as a Department everywhere — *including in authorization*, where `Department.managerId` decided who could act. C13 is that drift.

`tools/check-glossary.mjs` parses the rejected synonyms out of the glossary rather than duplicating them, so the document and the check cannot disagree. 19 rejected synonyms across 20 canonical terms. Verified in both directions before being trusted: it passes a clean tree and rejects `PipelineEntry`, `ServiceCategory` and `isLeadPricer` with the canonical replacement named.

There is deliberately **no inline suppression** — ADR-0008's policy applies: an exception is a reviewed glossary change, never a comment no reviewer sees again.

**One finding from building it, worth recording.** The parser initially indexed the rejected-synonyms column by a fixed position and returned zero terms after the table gained a column. A lint with zero terms passes everything. It was caught only by an explicit guard that fails when zero terms parse — the ninth instance in this branch of a check that would have reported green while enforcing nothing. Any lint that derives its rules from data needs that guard.
**Added during the completeness check** — conflict register item **C13** had no home in the supplied decision set. Renaming a concept across code, database, API contracts, and authorization keys after data exists is genuinely expensive, which qualifies it for an ADR.

## Context

The register records C13: *"Naming drift: `PipelineEntry` / `pipeline_entries` / 'Opportunity' / 'Pipeline' are one concept. `ServiceCategory` is used everywhere as Department, including in authorization."*

Both halves are harmful in different ways.

**One concept with four names** means developers cannot search for it reliably, documentation and code disagree, and new contributors must learn a translation table before they can read anything.

**`ServiceCategory` used as Department is worse**, because it reached *authorization*. A permission scoped to a "department" was actually scoped to a service category. When the name lies about the concept, the security model becomes hard to reason about — and the register elsewhere shows keys guarding the wrong capability (C2, C23), which is the same failure at a different layer.

DDD calls the countermeasure ubiquitous language: one term per concept, used identically by the business, the code, the database, and the API.

## Decision

**One name per concept, everywhere.**

- A **glossary** at `docs/glossary.md` is the authority. Each entry gives the canonical term, its Arabic equivalent (ADR-0019), a one-line definition, the owning bounded context, and explicitly **rejected synonyms**.
- The canonical term is used identically in: domain types, database table and column names, API contract fields, permission keys, UI labels, and conversation.
- **Rejected synonyms are recorded**, not merely omitted, so a reader who encounters an old term in the prior art finds out what it maps to.
- **Two renames are decided now**, both carried over as corrections from the prior art:
  - `ServiceCategory` → **`Department`** wherever the concept is an organisational department. If service categorisation is a genuinely separate concept, it keeps a distinct name and a distinct table.
  - `PipelineEntry` / `Pipeline` → **`Opportunity`**, matching the flowchart's language and the business's own vocabulary.
- **Mining documents record the mapping** from prior-art names to canonical names (ADR-0003), so translation happens once, in writing, rather than repeatedly in people's heads.
- Renaming after data exists follows expand–contract (ADR-0014).

## Consequences

**Positive**
- Search works. One term finds every occurrence across code, schema, and contracts.
- Permission keys describe what they actually guard, removing an entire class of authorization confusion.
- The business and the codebase use the same words, so requirements translate directly.

**Negative / trade-offs**
- Renaming prior-art concepts adds friction while mining — a reader must consult the mapping. This is a one-time cost paid deliberately.
- The glossary must be maintained; a stale glossary is worse than none because it is trusted.
- Some renames are genuinely arguable (is an "Opportunity" the same as a "Quote Request"?). The glossary must record the decision and its reasoning, not just the winning term.

## Rejected alternatives

| Alternative | Why rejected |
|---|---|
| **Keep prior-art names for continuity** | Inherits C13 directly, including the `ServiceCategory`-as-Department confusion that reached authorization. |
| **Allow synonyms with a mapping layer** | A mapping layer is a permanent translation tax and a permanent source of drift. |
| **Naming conventions without a glossary** | Conventions govern *form* (snake_case, plural tables), not *which word means which concept*. C13 is a vocabulary problem, not a formatting one. |
| **Enforce naming purely by review** | Names arrive one file at a time and drift is invisible per PR. Exactly how C13 happened. |

## Enforcement

- **Glossary lint**: a CI script extracts identifiers from domain types, table names, and permission keys and checks each against the glossary's canonical terms and rejected-synonym list. A rejected synonym appearing anywhere fails the build. This is the mechanical fix for C13.
- **Permission-key naming**: keys follow `<module>:<action>` where `<module>` is a glossary term; the catalogue check (ADR-0021) validates the module segment against the glossary.
- **Contract naming**: field names in `packages/contracts` are checked against the same list, so the API vocabulary cannot diverge from the domain.
- **Migration lint** (ADR-0014): a new table or column whose name contains a rejected synonym fails.
- **Mining requirement**: each `docs/mined/*.md` includes a prior-art-name → canonical-name table; the mining check (ADR-0003) requires it.
- **Adding a term** is a glossary PR, which makes vocabulary a reviewed decision rather than an accident of whoever typed first.
