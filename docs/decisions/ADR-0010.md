# ADR-0010: REST + OpenAPI generated from Zod contracts

**Status:** Proposed
**Date:** 2026-08-02

## Context

The API will eventually be consumed by an admin dashboard, a customer booking portal, mobile applications, a partner API, background workers, and external integrations. Not all of those are TypeScript, and the partner surface needs a stable, versionable, publishable contract.

The failure mode to prevent is **contract drift**: the frontend declaring its own `interface Client { … }` that diverges from what the API actually returns. This is not prevented by discipline; it is prevented by removing the opportunity.

## Decision

We will use **REST with OpenAPI**, generated from **Zod schemas in `packages/contracts`** as the single source of truth.

Toolchain (verified compatible):
```
zod@^4
@asteasolutions/zod-to-openapi@^8.5   # Zod v4; v7.3.4 was the last Zod v3 line
@nestjs/swagger                        # serves the generated document
orval@^7.13                            # OpenAPI → typed React Query client
+ ZodValidationPipe for runtime request validation
```

One schema definition produces: TypeScript types, runtime request validation, the OpenAPI document, the frontend client, and test fixtures.

Additional rules:
- The **generated client is the only exported type surface** for API shapes.
- The **OpenAPI document is committed** and diffed on every PR, so breaking changes are visible in review.
- The frontend uses `zodResolver` with the *same* schemas, so client and server validation cannot diverge.
- **Internal API is unversioned** and moves with the monorepo. The **partner API is URL-versioned** (`/v1/…`) in its own app with an explicit mapping to a stable published shape (ADR-0004 defers the app itself).
- The error response shape is part of the contract, defined once in `packages/contracts`.

`ts-rest` is the cleaner contract-first model and should be revisited once its Zod v4 support leaves release-candidate status; it is not a blocker.

## Consequences

**Positive**
- Frontend model drift becomes structurally impossible rather than discouraged.
- Every future consumer — including non-TypeScript ones — can be generated from the same document.
- Breaking changes are visible as a diff in the PR rather than discovered at runtime.

**Negative / trade-offs**
- A codegen step in CI, and generated files committed to the repository.
- More boilerplate than tRPC for the internal case.
- The partner mapping layer is duplicated effort by design — internal contracts must never be exposed externally, so a rename internally does not break a partner's production.

## Rejected alternatives

| Alternative | Why rejected |
|---|---|
| **tRPC** | TypeScript-only, so it cannot serve the partner API or non-TS mobile clients. No versioning story. Its RPC shape leaks server internals to clients. |
| **GraphQL** | Authorization would move into per-field resolvers, where the scope model of ADR-0021 becomes very hard to apply consistently — and authorization inconsistency is exactly the predecessor's C1/C2/C23 failure. Also N+1 risk and caching complexity for CRUD-shaped ERP screens. |
| **Hybrid (tRPC internal + REST external)** | Two contract systems expressing the same rules. They drift. This is the failure mode, not the compromise. |
| **Hand-written OpenAPI YAML** | Drifts from the code immediately. Generation is what makes the document trustworthy. |
| **Code-first with `@nestjs/swagger` decorators only** | The document becomes a derivative of controller annotations rather than a contract, and the frontend has nothing to generate from until the API is written. |

## Enforcement

- **CI: `contract codegen → git diff --exit-code`.** If the committed generated client or OpenAPI document does not match what the schemas produce, the build fails. This is the mechanism that prevents drift.
- **CI: OpenAPI diff vs `main`**, posted as a PR comment, with breaking changes highlighted.
- **Lint rule**: `interface`/`type` declarations in `apps/*` whose names collide with a `packages/contracts` export are an error.
- **Runtime**: `ZodValidationPipe` on every route; an unvalidated body cannot reach a use-case.
- **Contract conformance tests**: responses are parsed against the response schema in integration tests, so a handler returning an undeclared shape fails.
