# ADR-0022: Row Level Security scope

**Status:** Proposed
**Date:** 2026-08-02

## Context

PostgreSQL Row Level Security is attractive as a safety net: a policy on the table cannot be forgotten by a developer writing a query. The temptation is to extend it from tenancy into the full authorization model.

That temptation must be resisted for a specific, mechanical reason. A policy's `USING` expression is evaluated **per candidate row**, as a SubPlan. A `DEPARTMENT`-with-descendants scope requires a `WITH RECURSIVE` department tree walk. Placed inside an RLS policy, that recursion executes once per row examined rather than once per query.

Three further constraints matter:
- Superusers and roles with `BYPASSRLS` are not subject to policies unless `FORCE ROW LEVEL SECURITY` is set.
- PgBouncer in transaction-pooling mode is incompatible with session-level `SET`, because the session may be handed to another client between statements.
- RLS policies are invisible to unit tests, and a test running as a superuser will not exercise them at all.

## Decision

We will use RLS for **`organization_id` equality only**, as defence in depth.

```sql
ALTER TABLE crm.clients ENABLE ROW LEVEL SECURITY;
ALTER TABLE crm.clients FORCE  ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON crm.clients
  USING (organization_id = current_setting('app.current_organization', true)::uuid);
```

- Applied to **every** business table.
- `FORCE ROW LEVEL SECURITY` so the table owner is also subject to the policy.
- The setting is applied with `SET LOCAL` **inside the transaction**, which is compatible with transaction pooling. Session-level `SET` is forbidden.
- **All hierarchical scope (`OWN`/`TEAM`/`DEPARTMENT`/`BRANCH`) is resolved in the repository layer** (ADR-0021). No scope logic of any kind goes into an RLS policy.
- The application database role does not have `BYPASSRLS`.

## Consequences

**Positive**
- A repository that forgets the `organization_id` predicate cannot leak across tenants — the database refuses.
- Two independent layers must both fail for a cross-tenant leak to occur.
- The policy is trivial, so its performance cost is a single indexed equality per row.

**Negative / trade-offs**
- Every connection must set `app.current_organization` before querying, and a missed `SET LOCAL` returns **zero rows** rather than an error — a confusing failure mode. Mitigated by setting it in a single connection-acquisition wrapper and by an integration test asserting the failure is visible.
- Policies are invisible in ORM query logs and in unit tests; only integration tests exercise them.
- Migrations and administrative scripts run as a role that must be handled deliberately.
- RLS gives no protection against *within-tenant* over-broad access; that is entirely ADR-0021's job. Recorded so the safety net is not mistaken for the mechanism.

## Rejected alternatives

| Alternative | Why rejected |
|---|---|
| **RLS as the primary authorization layer** | Cannot express `DEPARTMENT`-with-descendants without a recursive SubPlan evaluated per row. Untestable in unit tests, invisible in review, and duplicates rules the API already enforces. |
| **No RLS at all** | Removes the second layer; a single forgotten predicate becomes a cross-tenant data leak. The cost of the simple policy is low enough that this is not worth it. |
| **RLS with a `current_setting` carrying the full actor context** | Pushes the scope resolver into SQL policies, inheriting all the problems above. |
| **Session-level `SET` instead of `SET LOCAL`** | Breaks under transaction pooling, which is the pooling mode most likely to be adopted as load grows. |

## Enforcement

- **Migration lint** (ADR-0014): a new business table without `ENABLE`/`FORCE ROW LEVEL SECURITY` and a `tenant_isolation` policy fails CI.
- **Connection wrapper**: `SET LOCAL app.current_organization` is issued by the transaction-acquisition helper in `packages/database`; repositories cannot obtain a connection without it.
- **Integration test**: with the setting deliberately unset, a query returns zero rows and the wrapper raises — asserting the confusing failure mode is detected loudly rather than silently.
- **Cross-tenant test**: seeded with two organisations, every repository read is asserted to return only the current organisation's rows even when the application predicate is stubbed out.
- **Role check**: a startup assertion fails boot if the application role has `BYPASSRLS` or is a superuser.
- **Lint**: any `CREATE POLICY` whose `USING` clause contains `WITH RECURSIVE`, a join, or a subquery beyond the tenancy equality is rejected by migration lint.
