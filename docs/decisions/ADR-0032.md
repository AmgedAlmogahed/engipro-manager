# ADR-0032: Docker from commit #1

**Status:** Proposed
**Date:** 2026-08-02

## Context

Fragile deployment was the fifth problem motivating the rebuild. The predecessor's `DEPLOY.md` is a manual runbook against an OCI Ampere ARM Ubuntu VM (~6 GB RAM) using pm2:

- SSH to the box, then `npx playwright install --with-deps chromium`
- `sudo apt-get install -y fonts-noto fonts-noto-cjk` for Arabic glyph rendering
- `cp -r packages/web/.next/static` and `cp -r packages/web/public` into the standalone bundle by hand
- Hand-edit `scratch/ecosystem.config.js` to point pm2 at the standalone `server.js`
- Keep the API under a ~700 MB pm2 cap while leaving headroom for Chromium

The consequence recorded in that document: the **first PDF request in production failed** because the Chromium binary was never installed. Runtime dependencies were discovered at request time.

## Decision

**Every line of that runbook becomes a Dockerfile line.** Docker from the first commit, for local development and production alike.

```
infra/docker/
├─ Dockerfile.api          node:20-bookworm-slim, multi-stage
├─ Dockerfile.admin        Next.js output:'standalone', built INTO the image
├─ Dockerfile.pdf-worker   Chromium + Arabic fonts + tini
├─ docker-compose.dev.yml  postgres, minio, mailhog
└─ docker-compose.prod.yml api, admin, pdf-worker, postgres, caddy
```

**Memory budget (6 GB box):**

| Service | Limit | Notes |
|---|---|---|
| api | 1 GB | `--max-old-space-size=512` |
| admin | 512 MB | |
| **pdf-worker** | **2 GB + `shm_size: 2gb`** | own container |
| postgres | ~1 GB | |
| caddy | 64 MB | TLS termination |
| **headroom** | **~1.5 GB** | |

**Verified platform constraints, encoded in the images:**
- `node:20-bookworm-slim` — multi-arch (amd64 + arm64). **Never Alpine**: musl is incompatible with Chromium's glibc assumptions.
- The official Playwright image is documented as *"intended for testing and development purposes only"* — we build a custom slim image for production.
- Chromium is installed **as the non-root app user**, because it must run as the user that installed it.
- `/dev/shm` defaults to 64 MB and Chromium needs roughly 2 GB — hence `shm_size: '2gb'`.
- `fonts-noto-naskh-arabic` plus `fc-cache -fv`, in the image that runs Chromium.
- `tini` as PID 1 to reap Chromium zombie processes.
- Next.js `output: 'standalone'` with `outputFileTracingRoot` set to the monorepo root; `.next/static` and `public/` are copied **in the Dockerfile**, replacing the manual step.
- `pnpm deploy --filter=<app> --prod` for minimal per-app images; BuildKit cache mount for the pnpm store.

**PDF rendering runs in its own container** so that a Chromium out-of-memory event cannot take the API down.

Deployment is: CI builds arm64 images → push to registry → `docker compose pull && up -d` → health check. **No SSH step exists in the happy path.**

Deferred: Kubernetes, service mesh, autoscaling, multi-region. Kamal only when zero-downtime deployment becomes a requirement.

## Consequences

**Positive**
- Runtime dependencies are discovered at build time, not at the first production request.
- Local, CI, and production run the same image shape; environment parity stops being aspirational.
- Rollback is `docker compose up -d` with the previous tag.
- The memory budget is declared and enforced by the runtime rather than managed by convention.

**Negative / trade-offs**
- Docker Compose provides no zero-downtime deployment; `up -d` briefly interrupts the affected service. Accepted for an internal ERP; Kamal is the escalation path.
- arm64 image builds under QEMU emulation are slow, particularly for the Chromium layer — **CI should run on native ARM runners** or use a remote arm64 builder.
- The PDF worker image is large (Chromium plus fonts).
- Container memory limits mean an OOM kills a container rather than degrading; health checks and restart policies are therefore mandatory, not optional.

## Rejected alternatives

| Alternative | Why rejected |
|---|---|
| **pm2 with a manual runbook** | The predecessor. Produces exactly the snowflake this rebuild exists to eliminate, and defers dependency failures to runtime. |
| **Alpine base images** | musl libc is incompatible with Chromium. A known, documented dead end. |
| **The official Playwright Docker image in production** | Its own documentation states it is for testing and development only; it is also very large. |
| **Chromium inside the API container** | A Chromium OOM would take the API with it — on a 6 GB box this is a matter of when, not if. |
| **Kubernetes now** | One server, one small team. Operational cost with no benefit. |
| **Building the admin app on the server** | Requires a full toolchain and workspace install on the box, and reintroduces the manual copy steps. |

## Enforcement

- **CI builds the image**; there is no deployment path that does not go through it. A manual server change is out-of-band and will be overwritten by the next deploy.
- **`docker compose config` validation** in CI, plus an assertion that every service declares `mem_limit`, `restart`, and `healthcheck`.
- **Post-deploy smoke test**: issue one quotation PDF and assert a valid PDF is returned. This is precisely the check whose absence produced the predecessor's first-request failure.
- **Health checks**: `/health` and `/ready` wired to Docker health checks; the deployment script waits for healthy and rolls back to the previous tag on failure (ADR-0037).
- **Platform assertion**: the build fails if the produced image is not `linux/arm64`.
- **Font check**: the PDF worker image runs `fc-list | grep -i naskh` at build time and fails if Arabic fonts are absent.
- **Base-image lint**: a Dockerfile using an Alpine base fails CI.
