# ADR-0031: Backups with WAL-G

**Status:** Proposed
**Date:** 2026-08-02

## Context

The system runs on a single VM. Everything — application, database, job queue, outbox, and audit log — lives on one machine. There is no replica and no managed database service.

This makes backup and restore the single most important operational control in the architecture. A hardware failure, a disk-full event, or a bad migration without a tested restore is an extinction-level event for the business data.

Two facts shape the tool choice:
- **pgBackRest was archived by its maintainer in April 2026** after losing corporate sponsorship. A coalition subsequently funded resumption of development, but governance and long-term commitment remain unsettled. For a *new* deployment this is avoidable risk.
- PostgreSQL's own documentation states plainly: *"You should set up and test your WAL archiving procedure before taking your first base backup."*

## Decision

We will use **WAL-G**, pushing to **off-server, encrypted object storage**.

```ini
# postgresql.conf
wal_level = replica
archive_mode = on
archive_command = 'wal-g wal-push %p'
archive_timeout = 60          # bounds worst-case data loss to ~60 seconds
```

- **Weekly base backup** plus **continuous WAL archiving**.
- **Destination is off-server** — Cloudflare R2 or Backblaze B2 (ADR-0034), never MinIO on the same box. A server failure that destroys the database must not also destroy the archive.
- **Encrypted at rest** using WAL-G's libsodium support; the key is a managed secret (ADR-0035).
- **Archiving is configured and verified before the first base backup**, per the PostgreSQL documentation.
- **Monthly restore drill**: restore the latest backup into a throwaway container, run the integration suite against it, and **record the result** including the measured restore duration.
- The recorded drill duration **is** the RTO; `archive_timeout` bounds the RPO at approximately 60 seconds (ADR-0041).

## Consequences

**Positive**
- Point-in-time recovery to within roughly a minute of any failure.
- No dedicated backup host required; WAL-G pushes directly to object storage.
- The monthly drill converts "we have backups" — a belief — into "we restored in N minutes last month" — a measurement.
- Restoring into a plain `postgres:16` container doubles as the portability check for ADR-0012.

**Negative / trade-offs**
- Continuous WAL archiving adds steady write and network load, and `archive_timeout = 60` forces a segment every minute even when idle, producing some storage waste. Accepted for the RPO benefit.
- Object storage costs money and needs credentials on the box.
- Restore is a manual procedure. Automating it is deferred; the runbook plus the monthly drill is the mitigation.
- WAL-G's community support is broad but it is not a commercially backed product either. The tool sits behind a documented runbook, so replacing it is a runbook change, not an architectural one.

## Rejected alternatives

| Alternative | Why rejected |
|---|---|
| **pgBackRest** | Archived April 2026; funding resumed but governance unsettled. Avoidable risk for a new deployment. Reconsider if it stabilises under a foundation. |
| **`pg_dump` on a cron** | No point-in-time recovery — worst case loses everything since the last dump. Acceptable only as a temporary fallback before WAL-G is configured. |
| **Barman** | Capable, but typically expects a dedicated backup server, which does not fit a single-VM deployment. |
| **Filesystem or volume snapshots only** | Crash-consistent, not necessarily transaction-consistent without coordination, and no granular PITR. |
| **Backups to MinIO on the same server** | The failure that destroys the database destroys the backup. This is not a backup. |
| **Managed PostgreSQL with provider backups** | Solves this properly and is the Phase 4 answer; today it is cost with no other benefit. |

## Enforcement

- **Nightly CI job (`restore-drill`)**: fetches the latest backup, restores into a throwaway `postgres:16` container, runs the integration suite, and **writes a result row** with duration and outcome.
- **Backup-verification alert**: no successful drill result row within N days raises an alert (ADR-0036). This is what makes an untested backup impossible to ignore.
- **Startup check**: the API asserts `archive_mode = on` and that `archive_command` is non-empty; a misconfigured database fails to pass readiness.
- **Archive freshness metric**: age of the most recent archived WAL segment; alert above threshold catches a silently failing `archive_command`.
- **Encryption assertion**: the drill verifies the restored backup was encrypted in transit and at rest, failing if the key was absent.
- **Runbook**: `docs/runbooks/restore.md`, exercised monthly by the drill, so the procedure is known to work rather than assumed to.
