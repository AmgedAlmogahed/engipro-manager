# ADR-0035: Secrets management

**Status:** Proposed
**Date:** 2026-08-02
**Added beyond the supplied decision set** — a secret committed to git is irreversible: rotation is required even after removal, because history persists. Several ADRs (identity, object storage, backups, notifications) depend on secrets having a defined home, and none of them can specify one.

## Context

The system requires: a JWT signing secret, a database password, object storage credentials (application files and backups, deliberately separate per ADR-0034), a WAL-G encryption key, notification provider credentials (SMTP, WhatsApp Business API), and later payment gateway and accounting integration keys.

The predecessor's `.env.example` shows a reasonable posture — a boot-time validation that refuses to start in production without a strong `JWT_SECRET`, with the development fallback value explicitly rejected. That check is worth keeping.

At the current scale (one server, a small team), a secrets manager is disproportionate. What is not disproportionate is guaranteeing that a secret never enters version control, because that failure cannot be undone.

## Decision

**Phase 1–3:** environment variables loaded at boot from a `.env` file on the server, owned by the deploying user with `chmod 600`, outside the repository and outside the Docker build context.

- **Nothing secret is ever committed.** `.env.example` contains keys with placeholder values only.
- **Boot-time validation** rejects missing secrets, secrets below a minimum length, and any value equal to a known development placeholder. The API refuses to start rather than running insecurely.
- **Docker**: secrets are passed as environment variables at run time, never baked into an image layer (an image layer is effectively public to anyone who can pull it).
- **Separation**: application file storage credentials and backup storage credentials are distinct, with distinct bucket scopes (ADR-0034).
- **Rotation runbook** exists in `docs/runbooks/rotate-secrets.md` for each secret, including which services must restart.

**Phase 4** (trigger: more than one server, or more than a handful of people with production access): move to a managed secrets store — cloud provider secret manager or Vault — behind the same environment-variable interface, so application code does not change.

## Consequences

**Positive**
- Simple enough that it is actually followed; complexity is the enemy of secret hygiene at small scale.
- Boot-time validation converts a silent misconfiguration into a loud startup failure.
- The environment-variable interface means the Phase 4 migration is an infrastructure change, not an application change.

**Negative / trade-offs**
- No rotation automation, no access audit, no versioning of secret values. Rotation is a manual runbook.
- The `.env` file is a single artefact on the server holding everything; anyone with shell access has all secrets. Accepted at current team size and access scope, and it is the main reason Phase 4 exists.
- Backup encryption keys stored beside the system being backed up is a known weakness — the key should additionally exist in a separate password manager, or a restore is impossible if the box is lost.

## Rejected alternatives

| Alternative | Why rejected |
|---|---|
| **Secrets in the repository (even encrypted)** | Git history is permanent; a leaked key requires rotation regardless of removal. Not worth the convenience. |
| **Secrets baked into Docker images** | Image layers are readable by anyone who can pull the image, and images are pushed to a registry. |
| **Vault / cloud secret manager now** | Disproportionate for one server and a small team; introduces an availability dependency for application boot. Correct at Phase 4. |
| **Docker Compose `secrets:`** | Full functionality requires Swarm mode; without it, it reduces to bind-mounted files, which is what the `.env` approach already provides more simply. |
| **SOPS / git-crypt** | Better than plain committed secrets, but still places ciphertext in permanent history and adds key distribution. Reasonable middle ground; rejected as unnecessary complexity at this size. |

## Enforcement

- **Secret scanning in CI**: `gitleaks` (or equivalent) runs on every PR and on the full history; a detected secret fails the build.
- **`.gitignore`** covers `.env`, `.env.*`, and `*.key`, with `.env.example` explicitly allow-listed.
- **Boot-time validation**: a config schema validates every required secret's presence and minimum entropy, and rejects known placeholder values. Production boot fails otherwise — inherited from the predecessor's `env.validation.ts`.
- **Image inspection in CI**: the built image is scanned for environment values matching secret-like patterns baked into layers.
- **Separation assertion**: startup fails if backup and application storage credentials are identical (ADR-0034).
- **Rotation drill**: rotating `JWT_SECRET` is exercised once, and the observed effect (all sessions invalidated) is recorded in the runbook so it is not discovered during an incident.
