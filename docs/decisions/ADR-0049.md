# ADR-0049: Multi-role resolution and approval authority limits

**Status:** Accepted
**Date:** 2026-08-08
**Supersedes:** [ADR-0043](ADR-0043.md) (multi-role conflict resolution, never Accepted)

## Context

ADR-0021 allows a user to hold more than one role, and each role grants permission keys at a scope (`OWN ⊂ TEAM ⊂ DEPARTMENT ⊂ BRANCH ⊂ ORGANIZATION ⊂ PLATFORM`). When two roles grant the same key at different scopes, a rule must decide the effective scope.

ADR-0043 proposed two rules: most-permissive by default, most-restrictive for a declared set of financial keys (`quote:approve`, `finance:validate_payment`, `finance:manage_invoice`, `project:licence_override`), with the exception set held as a `conflict_resolution` column on `permission_definitions`. It was blocked on confirmation and is superseded here.

The reason it is superseded rather than answered: it was solving a financial-control problem inside the permission resolver, which is the wrong layer. The concern behind it was real — someone holding `quote:approve` at `ORGANIZATION` through an unrelated role should not thereby be able to approve any quotation in the company. But the thing being controlled is not *whether* a person participates in approvals; it is *how large* an amount they may approve. A scope enum cannot express an amount, so ADR-0043 was forced to approximate a monetary limit with an organisational one.

Every established ERP separates these: SAP release strategies, Oracle approval limits, NetSuite approval routing. All of them keep "may act in this workflow" separate from "up to this value."

This is also not new scope. ABAK Module 4 already requires value-based approval thresholds that are administrator-configurable, so an approval engine that understands amounts has to exist regardless. ADR-0043's design would have duplicated a weaker, amount-blind version of it inside authorization — and left two mechanisms disagreeing about the same question, which is the C1 shape.

## Decision

We will separate the two concerns onto two layers.

### 1. The permission resolver is a most-permissive union. One rule, no exceptions.

Effective permissions are the union of all grants from all of a user's roles. Where the same key appears at multiple scopes, the **widest** applies. There is no exception set, and **no `conflict_resolution` column** on `permission_definitions`.

The resolver is therefore **monotone**: adding a role can only add capability, never remove it. This is standard RBAC behaviour, it matches what administrators expect, and it makes "why can this user do X?" answerable by listing their roles.

Combined with ADR-0044 (no explicit deny), resolution is a **single pass with no subtraction**.

### 2. Approval authority is a separate concept, evaluated by the approval workflow engine.

```sql
CREATE TABLE platform.approval_authorities (
  id                uuid PRIMARY KEY,            -- UUIDv7, ADR-0015
  organization_id   uuid NOT NULL,               -- ADR-0017
  subject_type      text NOT NULL,               -- 'USER' | 'ROLE'
  subject_id        uuid NOT NULL,
  permission_key    text NOT NULL REFERENCES platform.permission_definitions(key),
  max_amount        numeric(19,4) NOT NULL,      -- ADR-0016
  currency          char(3) NOT NULL DEFAULT 'SAR',
  scope             text NOT NULL,               -- same enum as role_permissions
  service_line_id   uuid NULL,                   -- NULL = all service lines
  effective_from    timestamptz NOT NULL,
  expires_at        timestamptz NULL,
  ...                                            -- audit columns per ADR-0014
);
```

Evaluation rules:

- An approval action requires **both** the permission key (resolver) **and** sufficient approval authority (this table). Holding the key without an authority row means the person may participate in approval workflows but may not approve any amount — which is a legitimate configuration, not an error.
- Where a subject has several applicable authorities, **the lowest `max_amount` wins.** Most-restrictive genuinely belongs here: an approval limit that rises because someone was granted an unrelated role is precisely the control failure ADR-0043 was worried about, and here the narrowing is expected, explainable, and expressible as a number.
- `max_amount` is compared against a defined **basis** per permission key — for quotations, the quotation total; for payments, the payment amount. The basis is part of the permission definition, not inferred at the call site.
- Authorities are **configuration**, editable by administrators without a deploy, consistent with ADR-0021's rejection of hardcoded authorization behaviour (C14).
- `currency` is `SAR` only for now, enforced by a check constraint, because multi-currency is deferred (ADR-0040). The column exists so that lifting that deferral is not a migration of financial control data.

### 3. Amount checks live in the approval workflow engine, not in `authorize()`

`authorize(actor, 'quote:approve', resource?)` continues to answer a boolean question about a key and a scope, exactly as ADR-0021 defines it. It gains no amount parameter. The approval engine calls `authorize()` first and then applies the authority check, so the two layers stay independently testable and the resolver keeps no knowledge of money.

## Consequences

**Positive**
- The resolver is a monotone single-pass union: trivially testable, trivially explainable, and it cannot produce "you hold a role that appears to permit this but does not."
- Approval limits gain an amount, which is what the control actually needed. `quote:approve` up to 500,000 SAR is expressible; under ADR-0043 it was not.
- Limits can differ per service line and carry an expiry, which supports delegation during leave — a real requirement that a scope enum could not express at all.
- One mechanism for value-based thresholds, shared with Module 4's requirement, instead of two that can disagree.
- The permission catalogue keeps one less dimension.

**Negative / trade-offs**
- Two checks guard an approval instead of one, so a rejection has two possible causes. The UI must distinguish "you cannot approve quotations" from "this quotation exceeds your limit" — if it does not, this becomes a support burden. That requirement is the enforcement item below.
- A new table and an evaluation path that must be correct, since it guards money.
- An administrator can grant `quote:approve` and forget the authority row, producing a user who appears able to approve but cannot. Mitigated by an admin-UI warning, below.
- Most-permissive on the resolver means an unrelated role really can widen *visibility* of quotations. That is accepted: seeing a quotation is not approving it, and scope-based read access was never the financial control.

## Rejected alternatives

| Alternative | Why rejected |
|---|---|
| **ADR-0043 as proposed: per-key permissive/restrictive column** | Encodes a monetary control as an organisational scope, so no limit can carry an amount. Adds a dimension to the permission catalogue, makes effective permissions non-monotone for a subset of keys, and duplicates the approval-threshold engine Module 4 already requires. |
| **Most-restrictive everywhere** | Violates the expectation that adding a role adds capability. A user holding a broad role and a narrow one would lose access — surprising, and a support load. |
| **Explicit deny to cap approval authority** | Requires the overrides table rejected in ADR-0044, adds a subtraction pass to every resolution, and still cannot express an amount. |
| **Amount limits inside `authorize()`** | Pushes money into the authorization primitive used by every module, so every call site must know whether the resource has a total. Couples the resolver to Finance and Quotation semantics. |
| **Thresholds in the quotation module only** | Payments, invoices, and licence overrides need the same control. Implemented per-module it would be reimplemented per-module, inconsistently. |
| **Prevent users from holding multiple roles** | Real organisations have people who are both a department head and a project manager. Denying it forces bespoke composite roles, which is role explosion. |

## Enforcement

- **Resolver test asserts monotonicity**: for any role set, adding a role never reduces the resolved permission set. Property-based, over generated role combinations. This is the test that makes reintroducing an exception set an explicit, visible decision.
- **Migration lint** (ADR-0014) fails on a `conflict_resolution` column, or any column resembling a per-key resolution mode, on `permission_definitions`, with a pointer to this ADR.
- **Role-matrix suite** (ADR-0009) gains: a user holding two roles granting the same key at different scopes resolves to the widest; a subject with two applicable authorities resolves to the lowest `max_amount`; an actor holding the key with no authority row cannot approve any amount; an approval at exactly `max_amount` succeeds and one cent above it fails.
- **No amount comparison outside the approval engine**: a lint rule fails any comparison of a `max_amount` or an approval threshold in a module other than the approval engine, so the check cannot be reimplemented locally.
- **Admin UI, two requirements, both load-bearing**: the effective-permissions view shows the resolved scope and the contributing roles; and assigning an approval permission key without a corresponding authority row raises a visible warning at assignment time, since the failure would otherwise surface as a confused user mid-approval.
- **Rejection messages are distinguishable**: the API returns different error codes for "lacks the permission key" and "exceeds approval authority", asserted by contract test. Collapsing them into one 403 is what makes limits unexplainable.
- **Audit** (ADR-0024): every authority grant, change, and expiry is audited, and every approval records the authority row that permitted it and the amount basis compared. An approval that cannot name the authority that allowed it is unauditable.
- **Currency guard**: a check constraint pins `currency` to `SAR` until ADR-0040's deferral is lifted.
