# ADR-0008: Boundary enforcement with dependency-cruiser

**Status:** Accepted
**Date:** 2026-08-02
**Accepted:** 2026-08-08 — ratified as wave W1b (machinery).
**`$1` back-reference verification: DONE, and it works.** The Decision below instructs that rules 3 and 4 not be relied on until `$1` interpolation is verified against the installed version. Verified on **dependency-cruiser 18.1.1** by `tools/dependency-cruiser.test.sh`, which builds a temp tree containing a deliberate cross-module-internals violation and a deliberate app-to-app violation and asserts both are reported, then removes them and asserts the compliant tree is clean. The barrel-file allow-list fallback is **not** needed. Had this failed, rules 3 and 4 — which carry C5, C18 and the app boundary — would have matched nothing and reported green.
**Live-fire demo: RUN 2026-08-08, and it found a dead rule.** Results below — this is the Phase-1 exit criterion, and it earned its place.

## Live-fire demo result (2026-08-08)

A deliberate `@nestjs/common` import was committed into `apps/api/src/modules/demo/domain/` and pushed. Outcome:

| Run | Gate | Result |
|---|---|---|
| Old config | `Boundaries` | **PASSED the violation** — "no dependency violations found (27 modules)" |
| Old config | `Mining gate` (ADR-0003) | Failed — `docs/mined/demo.md` MISSING |
| Fixed config | `Boundaries` | Failed — `error no-vendor-in-domain-or-application` |
| Fixed config | `Mining gate` | Failed — as above |

**`no-vendor-in-domain-or-application` had never fired in this repository.** Its `to` matcher was anchored `^node_modules/(@nestjs|drizzle-orm|…)`, which assumes npm/yarn flat hoisting. Under pnpm a vendor import resolves to `node_modules/.pnpm/@nestjs+common@11.1.28_…/node_modules/@nestjs/common/index.js`, so the anchor matched nothing and the rule reported clean on every run.

This is the rule that makes ADR-0005's *"the framework is replaceable"* and ADR-0011's *"the ORM is behind ports"* true claims rather than intentions. Both would have been false for the entire life of the project, behind a green check.

**Nothing else caught it.** The config self-test reported 6/6 because its fixture created a *flat* `node_modules/@nestjs/common` — npm-shaped, not pnpm-shaped — so it tested the fixture rather than the rule. The boundary gate reported clean. Two agents reviewed the config and both signed off. Only committing a real violation and watching CI found it.

Fixed: the matcher is unanchored on the `node_modules` boundary and works for either layout, and the fixture now mirrors pnpm's real layout and asserts both. The `$1` back-reference support of rules 3 and 4 is separately verified on dependency-cruiser 18.1.1 (see the status block above); the barrel-file fallback is not needed.

**The generalisation, which is why this ADR mandates the demo:** a boundary rule is a regex against paths produced by a package manager, so it is only correct for the layout it was written against. Changing package manager, hoisting strategy, or workspace layout can silently disable one. Re-run this demo after any such change — an untested boundary rule is indistinguishable from an absent one.

The unrelated bonus finding: the mining gate (ADR-0003) fired correctly and independently on the same commit, refusing domain code for a module with no mining document.

## Context

This is the ADR that makes the rest of the architecture real.

The predecessor **already had boundary enforcement**: `@nx/enforce-module-boundaries` with `scope:*` and `type:*` tags, documented in its `ARCHITECTURE.md`. It still produced C1 (two authorization models coexisting), C5 (the leads module writing Client, PipelineEntry and Rfq in one transaction), and C18 (Interaction written by four modules).

The reason is precise and verifiable: **Nx tags operate at the project level.** Its own documentation states the rule "controls which projects can depend on other projects — it doesn't manage dependencies between folders or modules within a single project/app." Every one of those violations occurred *inside* `packages/api`, where Nx cannot look.

Turborepo does not close this gap either. Its `boundaries` command (introduced 2.4, January 2025) is marked **experimental** and detects two things: importing a file outside a package directory, and importing a package not declared in `package.json`. Both are package-level.

Shopify reached the same conclusion from the other direction: they built Packwerk after finding that "agreed-upon social contracts can be easily broken," and that violations kept accumulating under a documented convention.

## Decision

We will enforce boundaries with **dependency-cruiser** as the blocking CI gate, supplemented by **eslint-plugin-boundaries** for editor feedback and an **agent `PostToolUse` hook** for AI-assisted implementation.

Four rules carry the architecture:

```js
// tools/.dependency-cruiser.js
forbidden: [
  { name: 'domain-imports-nothing',
    from: { path: '^packages/domain/src/' },
    to:   { pathNot: '^packages/domain/src/' } },

  { name: 'no-vendor-in-domain-or-application',
    from: { path: '^(apps/api/src/modules/[^/]+/(domain|application)|packages/domain/src)/' },
    to:   { path: '^node_modules/(@nestjs|drizzle-orm|@prisma|@aws-sdk|playwright|axios)/' } },

  { name: 'no-cross-module-internals',
    from: { path: '^apps/api/src/modules/([^/]+)/' },
    to:   { path: '^apps/api/src/modules/(?!$1)[^/]+/(domain|application|infrastructure)/' } },

  { name: 'no-app-to-app',
    from: { path: '^apps/([^/]+)/' },
    to:   { path: '^apps/(?!$1)[^/]+/' } },
]
```

**Before relying on rules 3 and 4, verify `$1` back-reference support in the installed dependency-cruiser version by committing a deliberate violation and confirming CI fails.** If unsupported, replace with explicit allow-lists of barrel files.

## Consequences

**Positive**
- Layer violations fail the build rather than surviving review. This is the single control that would have prevented most of C1–C23.
- Rule 3 makes cross-module coupling (C5, C18) impossible rather than discouraged.
- Rule 2 is what makes ADR-0005's "the framework is replaceable" and ADR-0011's "the ORM is behind ports" true claims instead of intentions.
- Editor-time feedback via eslint-plugin-boundaries means violations are caught before commit.

**Negative / trade-offs**
- dependency-cruiser runs as a separate CLI step, not an ESLint plugin, so it is a CI gate rather than inline editor errors — hence the eslint-plugin-boundaries complement.
- Two tools with overlapping configuration that can drift apart. Mitigated by keeping dependency-cruiser authoritative and treating the ESLint config as a convenience mirror.
- Occasional false positives requiring an explicit, reviewed exception. Exceptions must be a named rule change, never an inline suppression comment.
- Element mapping in eslint-plugin-boundaries needs updating when new folder types appear.

## Rejected alternatives

| Alternative | Why rejected |
|---|---|
| **Nx `enforce-module-boundaries` alone** | Project-level only, per its own docs. Empirically insufficient — it was present in the predecessor and did not prevent C1, C5, or C18. |
| **Turborepo `boundaries` alone** | Experimental, and package-level. Cannot see inside `apps/api`. |
| **Code review as the control** | Shopify's documented finding is that social contracts break under delivery pressure. Reviewers get tired; CI does not. |
| **Rules in CLAUDE.md / documentation** | Anthropic's guidance is explicit: "if something absolutely must not happen, an instruction is the wrong tool." Probabilistic adherence for a deterministic requirement. |
| **Bazel or a build-system-level enforcement** | Correct in principle, disproportionate for a 2–5 person team on a single VM. |

## Enforcement

This ADR **is** an enforcement mechanism. Its own enforcement:

- **CI (blocking)**: `pnpm check:boundaries` → `depcruise apps packages --config tools/.dependency-cruiser.js`. Required status check on `main`.
- **Editor**: `eslint-plugin-boundaries` with `default: "disallow"` and explicit per-layer policies.
- **Agent hook**: `PostToolUse` on `Write|Edit` runs `pnpm lint && pnpm typecheck` so an AI implementer sees violations immediately in context (ADR-0038).
- **Suppression policy**: `eslint-disable` for boundary rules is itself a lint error. Exceptions are rule changes, reviewed.
- **Phase 1 exit criterion**: the foundation phase is not complete until a deliberately introduced violation (importing `drizzle-orm` into a `domain/` folder) **fails CI**. Until that has been demonstrated, the architecture is unverified.
