# ADR-0001: Monorepo tooling and structure

**Status:** Accepted
**Date:** 2026-08-02
**Accepted:** 2026-08-08 — ratified as wave W1a (substrate). Amended at ratification: the frontend app is `web`, not `admin`, for consistency with ADR-0050 and ADR-0032.

## Context

The rebuild spans several deployables that must share domain types, API contracts, and UI primitives: a standalone API, an internal web application, a background worker, and — later — a customer portal, partner API, and mobile app. Contract types must never be redefined per surface; that drift is a known failure mode.

The predecessor used an Nx monorepo. Nx worked as a task runner but did not prevent the architectural decay recorded in the conflict register, because its boundary enforcement operates at the *project* level and every one of those violations occurred *inside* `packages/api` (see ADR-0008).

The team is small (2–5 developers). Tooling that requires ongoing configuration maintenance is a real cost.

## Decision

We will use **Turborepo + pnpm workspaces** in a single repository, with this structure:

```
engipro-manager/
├─ apps/       prototype (frozen) · api · web · worker (Phase 4)
├─ packages/   config · domain · contracts · database · ui · testing
├─ infra/      docker
├─ tools/      dependency-cruiser config, codegen, scripts
└─ docs/       decisions · mined
```

We will create **three apps now** (`prototype`, `api`, `web`) and **six packages now**. `worker` arrives in Phase 4 (earlier for PDF — see ADR-0032). Note the ratification bound: only `apps/prototype` exists at W1a; `api` and `web` are scaffolded once W1b's machinery is installed and green (see the README's ratification order). Additional packages (`ui-erp`, `i18n`, `auth`, `utils`) are extracted **only when a second consumer exists**; until then they live inside their single consumer.

## Consequences

**Positive**
- Atomic changes across contract, API, and UI in one commit; no cross-repo version dance.
- Turborepo caching keeps CI proportional to what changed.
- `pnpm deploy --filter` produces minimal per-app Docker images (ADR-0032).
- Leaving is cheap: deleting `turbo.json` leaves working pnpm workspaces.

**Negative / trade-offs**
- Turborepo provides **no** architectural enforcement. This is not a partial gap; it is absent. ADR-0008 exists because of it.
- A single repository concentrates access control — everyone with commit rights can touch everything.
- The "shared common package becomes a junk drawer" failure mode is real; ADR-0008's rules on `packages/domain` are the mitigation.

## Rejected alternatives

| Alternative | Why rejected |
|---|---|
| **Nx** | Its `enforce-module-boundaries` is project-level only, per its own documentation: tags "don't manage dependencies between folders or modules within a single project/app." The old system had Nx and still produced C1, C5, C18. Also carries plugin-to-framework version coupling (`@nx/next` pinned against Next major versions). |
| **pnpm workspaces alone** | No task graph, no caching. CI time grows linearly with package count. Acceptable for a month; you would add Turborepo by month three. Skip the detour. |
| **Separate repositories** | A contract change becomes publish → bump → coordinate deploys. Highest friction option for a team of this size sharing domain types across six future surfaces. Atomic refactors become impossible. |
| **Scaffolding all eight future apps now** | Empty apps carry tsconfig, eslint config, Dockerfile, and CI matrix entries that decay unused. The intended list is recorded here instead. |

## Enforcement

- `pnpm-workspace.yaml` defines the workspace; `packageManager` field pins the pnpm version; CI installs with `--frozen-lockfile`.
- pnpm **catalogs** (`pnpm-workspace.yaml`, `catalog:` protocol) pin shared dependency versions in one place; version drift between packages becomes impossible rather than merely discouraged.
- `turbo.json` declares the task graph; `turbo run build` failing on a missing `dependsOn` surfaces ordering errors in CI.
- Package-count discipline (extract on second consumer) has **no mechanical enforcement** — it is a review-time judgement recorded here so the rule is citable in a PR discussion.
