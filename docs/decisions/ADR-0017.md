# ADR-0017: Tenancy — `organization_id` from day one

**Status:** Accepted
**Date:** 2026-08-02
**Accepted:** 2026-08-08 — ratified as wave W3 (data foundation).

## Context

Abak is a single organisation today.

**Open question B — answered 2026-08-08.** *Does this system become a sellable multi-tenant product, or does it remain Abak's internal ERP?* The question was previously routed through ADR-0043, which was the wrong home for it and has since been superseded.

**Answer: product intent exists, on both sides — and it changes nothing about the decision below.**

- The **schema decision is unchanged**: `organization_id` stays, for the cost-asymmetry reasons that follow.
- The **deliverable deploys single-tenant**. It is a complete, honest, single-organisation ERP. Nothing in this repository exists to constrain how it is deployed or scaled: no licensing enforcement, no tenant control plane, no phone-home telemetry, no anti-scaling measures. This is a firm boundary, not a deferral.
- **Any multi-tenant productization is a separate product in a separate repository**, outside this contract's scope. It is not designed here and gets no ADR here, because it is not this repository's decision to make.
- **Client-side extension is an expected, supported use.** The client intends to add their own modules — HR and accounting are anticipated. This is a stated requirement, not a tolerated side effect, and it is the reason the module-addition path must stay clean and documented: the modular monolith (ADR-0004), schema-per-context (ADR-0013), and the module template are what serve it. ADR-0048's naming and ubiquitous-language rules apply to third-party modules too.
- **No restriction mechanisms, ever.** Not deferred, not conditional. The asymmetry between the deliverable and any future multi-tenant product is scope-natural: control-plane machinery — onboarding, billing, tenant operations, isolation testing — is simply absent from the deliverable. There is nothing to engineer here and nothing to audit for.

The consequence for reviewers: this ADR's `organization_id` column is **not** a productization hook. It is a scope anchor for the permission model (ADR-0021) and the RLS predicate (ADR-0022), and it is correct for a single-organisation deployment on its own merits. Do not cite it as groundwork for a tenant control plane.

The cost asymmetry is the whole argument. Adding a tenant column now is one migration and a constant. Adding it after production data exists requires a schema migration on every table, a data backfill, an audit of every query in the codebase, and — the part teams underestimate — unlearning the habit of writing unscoped queries. Reported real-world experience frames this as "six weeks of queries without tenant context, six weeks of habits to unlearn."

AWS's SaaS guidance makes the structural point: isolation enforcement must not be left to individual service developers; it must be a shared mechanism.

Even in the single-tenant case the column has immediate value: it is the natural anchor for branch-level and organisation-level scope in the permission model (ADR-0021), and it is the RLS predicate (ADR-0022).

## Decision

We will add **`organization_id uuid NOT NULL`** to every business table from the first migration, seeded to a fixed UUID constant for the single existing organisation.

- Every list query carries an `organization_id` predicate, applied in the repository base (ADR-0021).
- Primary index shape for most tables is composite: `(organization_id, <domain column>)`.
- `organization_id` is the **only** identifier permitted to have a cross-schema foreign key (ADR-0013).
- The value is carried in the access token and placed in a request-scoped context at authentication; repositories read it from there, never from a request parameter.
- RLS provides defence in depth on the same column (ADR-0022).

Tenant *lifecycle* — offboarding, per-tenant export, per-tenant restore — is deferred to Phase 3 and depends on open question B.

## Consequences

**Positive**
- The most expensive retrofit in the set is avoided for the cost of one column.
- Scope resolution and RLS both have a stable anchor.
- Cross-tenant leakage becomes a two-layer failure (application predicate *and* RLS policy) rather than a one-layer one.

**Negative / trade-offs**
- A column on every table and a predicate on every query, with no immediate business benefit while single-tenant. This is the YAGNI objection and it is legitimate; it is overruled on cost asymmetry, not dismissed.
- Composite indexes are marginally larger.
- If the product is confirmed single-tenant forever, the column becomes inert overhead. Acceptable.
- Taking `organization_id` from the token rather than the request means a system/worker actor needs an explicit organisation context; jobs must carry it (ADR-0026 puts it on the outbox row).

## Rejected alternatives

| Alternative | Why rejected |
|---|---|
| **Add tenancy later, when needed** | The documented cost is a schema migration, a data backfill, a full query audit, and habit re-training under production load. Asymmetric against one column now. |
| **Schema per tenant** | Does not scale operationally past a small tenant count; migrations must run N times; conflicts with schema-per-context (ADR-0013), which already uses the schema axis. |
| **Database per tenant** | Highest isolation, highest operational cost. Revisit only if an enterprise customer demands database-level isolation for compliance. |
| **Rely on RLS alone** | RLS is bypassed by superusers and `BYPASSRLS` roles, is invisible to unit tests, and breaks under PgBouncer transaction pooling (ADR-0022). It is a safety net, not the mechanism. |

## Enforcement

- **Migration lint** (ADR-0014): a new business table without `organization_id uuid NOT NULL`, or without an index including it, fails CI.
- **Repository base class**: every query builder is constructed from a `RequestContext` that carries `organizationId`; a repository method that does not accept the context does not compile.
- **RLS** (ADR-0022): `USING (organization_id = current_setting('app.current_organization')::uuid)` with `FORCE ROW LEVEL SECURITY` on every business table.
- **Cross-tenant test**: the role-matrix suite (ADR-0009) includes probes that request a resource belonging to a different `organization_id` and assert 404 (not 403 — existence must not leak).
- **Nightly check**: assert no business table contains a row with a `NULL` or unknown `organization_id`.
