# ADR-0047: UI component standards — data states and design system ownership

**Status:** Proposed
**Date:** 2026-08-02
**Added during the completeness check** — conflict register items **C8** and **C9** had no home in the supplied decision set. Both are cross-cutting UI standards that are expensive to retrofit across a built application.

## Context

Two defects in the register are UI-structural rather than cosmetic:

- **C8** — *"The five data states are inconsistently handled. Only `clients.detail` distinguishes 403 from a generic error. `clients.list` and `pipeline.board` bypass `DataState` entirely; `pipeline.board` has no error state at all."* A missing 403 state is a security-adjacent bug: a user denied access sees a generic failure and cannot tell whether the record exists, was deleted, or is forbidden — and neither can support.
- **C9** — *"Raw status colour maps in page files, explicitly forbidden by `DESIGN_SYSTEM_MASTER.md` §17."* The design system existed and said not to do this; it was done anyway, in at least two page files. A rule in a document is not a rule.

Retrofitting a consistent state model and centralised status colour across dozens of built screens is significantly more work than establishing them before the screens exist.

The frozen prototype (ADR-0002) is useful here: it already demonstrates the needed component inventory and RTL discipline, and that inventory should be mined rather than re-derived.

## Decision

**One `DataState` primitive in `packages/ui`, with five mandatory states**, used by every data-bearing view:

| State | Requirement |
|---|---|
| Loading | Skeleton matching the eventual layout |
| Empty — first run | Icon, explanation, and a create action if the user is permitted |
| Empty — filtered | Distinct from first-run; offers to clear filters |
| Error | Message plus retry |
| **Forbidden (403)** | **Distinct from error.** Explains that access is denied; does not reveal whether the record exists |

**Status colour is owned by `StatusBadge`**, which maps a domain status to a token. Colour is never chosen in a page or feature file — this is C9's structural fix.

Additional standards:
- **Permission-aware UI**: a `<Can permission="…">` guard reads the same catalogue the API enforces (ADR-0021). Hiding a control is a courtesy; the endpoint is the control.
- **Optimistic updates** only for reversible, low-stakes actions. **Never** for state transitions with side effects — marking a quotation Won issues a purchase order, and an optimistic rollback after the user has seen success is worse than a spinner (ADR-0029).
- **RTL**: logical CSS properties only (ADR-0019).
- The ERP composite layer (`DataTable`, `FilterBar`, `Stepper`, `Timeline`, `KpiCard`, `MoneyInput`, `ApprovalChain`) is extracted to `packages/ui-erp` on its second consumer, per ADR-0001; until then it lives in `apps/web`.

## Consequences

**Positive**
- A denied user gets an accurate, non-leaking explanation, consistently — C8's fix.
- Status colour cannot drift between screens — C9's fix.
- The 403 state is built into the primitive, so it cannot be omitted by forgetting.
- Reuses the prototype's validated component inventory rather than rediscovering it.

**Negative / trade-offs**
- Every data view must supply five states, which is more work than a spinner and a table — including for trivial screens.
- A single `DataTable` grows options over time and risks becoming an unmaintainable god-component. Reviewed at each addition; a genuinely different table is a different component.
- Centralised colour mapping means an unusual one-off requires extending the token set rather than a local override, which is deliberate friction.

## Rejected alternatives

| Alternative | Why rejected |
|---|---|
| **A design system document stating these rules** | This existed (`DESIGN_SYSTEM_MASTER.md` §17) and was violated. Documents do not enforce. |
| **Four states, folding 403 into error** | Precisely C8. The user cannot distinguish "denied" from "broken", and support cannot either. |
| **Per-screen state handling** | Produces exactly the inconsistency the register records. |
| **A third-party component library used directly in pages** | Puts vendor components in feature code, making a later swap a full-application edit — the same objection as vendor SDKs in the domain (ADR-0006). |
| **Optimistic updates everywhere for responsiveness** | Unacceptable for transitions with financial side effects. |

## Enforcement

- **Structural lint**: a component that calls a data hook and does not render `DataState` (or explicitly opts out with a documented reason) fails lint.
- **Type-level completeness**: `DataState` requires all five state renderers as props; omitting one is a TypeScript error, so 403 cannot be forgotten.
- **Colour lint**: object literals mapping status values to colour or Tailwind classes are forbidden outside `packages/ui`. This is C9's mechanical fix.
- **Directional-utility lint**: `ml-`, `mr-`, `pl-`, `pr-`, `left-`, `right-`, `text-left`, `text-right` are errors in `apps/web` and `packages/ui` (ADR-0019).
- **403 test**: for every list and detail route, an integration test authenticates as a user without permission and asserts the forbidden state renders — not a generic error.
- **Optimistic-update policy**: mutations that emit domain events are flagged by lint if used with an optimistic handler.
