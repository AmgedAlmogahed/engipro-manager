# ADR-0040: Multi-currency deferred

**Status:** Proposed
**Date:** 2026-08-02

## Context

Abak operates in Saudi Arabia and quotes in SAR. Multi-currency support — foreign-currency quotations, exchange rate capture, revaluation, and reporting in a base currency — is a substantial feature: it touches rate sourcing, rate-at-what-moment semantics, gain/loss recognition, and every financial report.

ADR-0016 already requires an explicit `currency char(3)` column beside every monetary amount. That means the *schema* is multi-currency-ready even though the *application* is not.

## Decision

**SAR only** in the application. Multi-currency is deferred.

- Every monetary amount carries an explicit `currency` column, always `'SAR'` for now (ADR-0016).
- The domain `Money` value object carries a currency and **refuses to add different currencies** from day one, so the invariant exists before it is needed.
- The default currency is a Settings value, not a constant, so it is configuration rather than code.
- **Deferred until required**: exchange rate sourcing and storage, rate-effective-date semantics, base-currency reporting, revaluation, and realised/unrealised gain-loss handling.

## Consequences

**Positive**
- No schema migration when multi-currency arrives — the columns already exist and are populated.
- The `Money` type prevents the most common multi-currency bug (adding mismatched currencies) before there is a second currency.
- No effort spent on rate handling that may never be needed.

**Negative / trade-offs**
- The `currency` column is redundant while there is one currency, costing a small amount of storage and appearing in every contract. This is the deliberate price of avoiding the migration.
- Developers may treat currency as ignorable and hardcode `'SAR'` in places, which becomes a bug when a second currency arrives. The lint rule below is the mitigation.
- When multi-currency does arrive, the application work is still substantial; only the schema work is pre-paid.

## Rejected alternatives

| Alternative | Why rejected |
|---|---|
| **Full multi-currency now** | Rate sourcing, effective dating, revaluation, and gain/loss recognition are a significant body of work for a requirement that does not currently exist. Textbook YAGNI. |
| **No currency column (assume SAR)** | Adding a currency column to financial records after issuance means backfilling legally significant documents, and every historical amount becomes ambiguous. Cheap to add now, expensive later — the same asymmetry argument as ADR-0017. |
| **Minor units without currency** | Different currencies have different minor-unit scales; the amount alone is not interpretable. |

## Enforcement

- **Migration lint** (ADR-0014): a monetary column without a sibling `currency` column fails CI.
- **ESLint rule**: the string literal `'SAR'` is forbidden outside `packages/domain` defaults and seed data — currency comes from Settings or from the record, never hardcoded in business logic.
- **Domain test**: `Money.add` across differing currencies throws; asserted regardless of whether a second currency is in use.
- **Contract**: `Money` is a shared Zod schema of `{ amount, currency }`; an endpoint returning a bare number fails contract conformance tests.
- **Trigger to revisit**: the first quotation request in a non-SAR currency. No mechanical detection; recorded as the explicit condition.
