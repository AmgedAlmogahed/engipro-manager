# ADR-0026: Transactional outbox

**Status:** Proposed
**Date:** 2026-08-02

## Context

This ADR addresses two of the five problems that motivated the rebuild: module coupling and notification unreliability.

The conflict register states the root cause in its own words (C11): *"No event backbone. Notifications are fire-and-forget with swallowed failures; no outbox, no retry, no consumers. Every cross-module effect is therefore an inline write."*

That last sentence is the diagnosis. Modules called each other directly because there was no other way to react to something happening. That produced C5 (the leads module writing Client, PipelineEntry and Rfq in one transaction) and C16 (RFQ terminal state read off a Quote at render time, giving two sources of truth).

An in-process event emitter does not solve this: if the process dies between the database commit and the emit, the event is lost with no record that it should have happened.

## Decision

We will implement a **transactional outbox from the first migration**.

```sql
CREATE TABLE platform.outbox_events (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),  -- this IS the idempotency key
  organization_id uuid NOT NULL,
  aggregate_type text NOT NULL,
  aggregate_id   text NOT NULL,
  event_type     text NOT NULL,
  event_version  int  NOT NULL DEFAULT 1,
  payload        jsonb NOT NULL,
  status         text NOT NULL DEFAULT 'pending',   -- pending | processing | dead
  attempts       int  NOT NULL DEFAULT 0,
  available_at   timestamptz NOT NULL DEFAULT now(),
  locked_at      timestamptz,
  locked_by      text,
  correlation_id uuid,
  error_detail   text,
  created_at     timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX idx_outbox_pending ON platform.outbox_events (available_at, id) WHERE status = 'pending';
CREATE INDEX idx_outbox_stale   ON platform.outbox_events (locked_at)        WHERE status = 'processing';
```

- **Written in the same transaction as the state change.** If the business change commits, the event exists; if it rolls back, no phantom event.
- **Relay wake-up**: `NOTIFY` on insert as a *latency hint*, plus a **5-second poll as the durability guarantee**. `NOTIFY` acquires a global lock at commit and silently drops notifications when the listener is disconnected, so it can never be the durability mechanism.
- **Claim**: `SELECT … FOR UPDATE SKIP LOCKED LIMIT 25`, so multiple relay workers never block one another.
- **Delete on success.** Marking rows `processed_at` leaves a graveyard that autovacuum cannot reclaim efficiently because update transactions pin the xmin horizon. The outbox is a ledger, not an archive; history lives in the audit log (ADR-0024).
- **Backoff**: `available_at = now() + 2^attempts minutes + jitter`; 5 attempts, then `status = 'dead'` — queryable and replayable by resetting to `pending`.
- **Stale-lock recovery** every 2 minutes: rows `processing` for more than 3 minutes return to `pending`.
- **Consumers deduplicate** on `(event_id, consumer)` in a shared `platform.processed_events` table, inserted in the **same transaction as their effect**.
- Delivery is **at-least-once**. Exactly-once is not pursued.

Phase 1 dispatch is in-process (stack traces survive, which materially helps debugging). Phase 4 moves the relay into `apps/worker` — **handlers do not change**.

## Consequences

**Positive**
- Cross-module effects stop being inline writes. C11's root cause is removed, and C5 and C16 lose their mechanism.
- A crash between commit and dispatch loses nothing.
- Notifications gain retries, dead-lettering, and an audit trail (ADR-0028) instead of being fire-and-forget.
- Later service extraction changes the transport, not the handlers.

**Negative / trade-offs**
- Cross-module propagation becomes **eventually consistent**. The business state change is synchronous within its own transaction; the propagation is not. Product must understand that a project appears moments after a quote is won, not in the same render.
- Duplicate delivery is possible by design, so every handler must be idempotent. A non-idempotent handler is a latent double-write.
- Failures surface asynchronously, which is the most legitimate criticism of event-driven design. Mitigated by in-process dispatch in Phase 1, `correlation_id` propagation, and a dead-letter alert from day one (ADR-0036).
- Autovacuum health on the outbox table becomes operationally relevant.

## Rejected alternatives

| Alternative | Why rejected |
|---|---|
| **In-process event emitter (`@nestjs/event-emitter`) alone** | No durability: a crash between commit and emit loses the event silently. This is C11 with better ergonomics. |
| **Direct cross-module service calls** | The predecessor's approach, and the direct cause of C5, C11, C16, and C18. |
| **Change Data Capture (Debezium + Kafka Connect)** | Requires Kafka and Kafka Connect; on a 6 GB box that leaves roughly 2 GB for the application. Correct choice above ~1,000 events/second, which this system will not approach. |
| **Listen-to-yourself** | Requires a durable log (Kafka). Using `NOTIFY` for it would reintroduce exactly the fire-and-forget problem. |
| **Two-phase commit** | Reintroduces the coupling the outbox exists to remove. |
| **Marking rows processed instead of deleting** | Pins the xmin horizon and bloats the table; a growing graveyard degrades the relay query. |

## Enforcement

- **Same-transaction test**: an integration test commits a state change with the process killed before dispatch, restarts the relay, and asserts the event is still delivered.
- **Structural rule**: use-cases emit events through the unit of work; a use-case that calls another module's service directly fails dependency-cruiser rule `no-cross-module-internals` (ADR-0008).
- **Idempotency test**: every consumer is invoked twice with the same `event_id` and asserted to produce exactly one effect.
- **Dead-letter alert**: `status = 'dead'` count greater than zero raises an alert (ADR-0036). Non-negotiable once the relay leaves the API process.
- **Outbox lag metric**: age of the oldest `pending` row, alerted above threshold.
- **Migration lint**: `platform.outbox_events` is on the base-column exemption list, recorded explicitly rather than by omission.
