# ADR-0034: Object storage

**Status:** Accepted
**Date:** 2026-08-02
**Accepted:** 2026-08-08 — ratified as wave W6 (infrastructure).

## Context

Two distinct storage needs are frequently conflated, and conflating them is dangerous:

1. **Application files** — quotation PDFs, client documents, tender booklets, licence scans, site photographs. These are business records referenced by database rows.
2. **Backup target** — PostgreSQL base backups and archived WAL segments (ADR-0031).

They differ in access pattern, permission model, and — critically — in failure correlation. A backup stored on the same machine as the database is not a backup. An application file store on the same machine merely fails together with everything else, which is a smaller problem but still a data-loss risk on a single VM with no replica.

The predecessor stored uploads on the local filesystem, which on a single box means an unbacked-up volume holding business records.

## Decision

Two separate decisions, both resolving to **off-box S3-compatible object storage**.

**(a) Application files** — behind a `FileStorage` port (ADR-0006):
```ts
interface FileStorage {
  put(key: string, body: Buffer, meta: FileMeta): Promise<StoredFile>
  getSignedUrl(key: string, ttlSeconds: number): Promise<string>
  delete(key: string): Promise<void>   // administrative use only
}
```
- Production adapter: S3-compatible provider (Cloudflare R2 or Backblaze B2), **from day one**, not the local filesystem.
- Development adapter: MinIO in `docker-compose.dev.yml` — same S3 API, so the adapter code is identical and only the endpoint differs.
- Buckets are **private**; files are served via short-lived signed URLs, never public links.
- Uploads are validated for content type and size, stored under a key namespaced by `organization_id`, and their metadata rows carry the standard base columns (ADR-0014).

**(b) Backup target** — off-server, encrypted, a **different bucket and different credentials** from application files (ADR-0031).

**Not MinIO on the production box for either purpose.**

## Consequences

**Positive**
- Business documents survive the loss of the VM.
- The S3 API means development, production, and any future cloud migration use the same adapter.
- Signed URLs keep authorization in the application rather than relying on bucket ACLs.
- Object storage does not consume the 6 GB memory budget or the VM's disk.

**Negative / trade-offs**
- Network dependency and latency for every file read and write; a provider outage makes documents unavailable even though the ERP is up. Acceptable for an internal system.
- Egress and storage costs, small at this scale but non-zero.
- Two sets of credentials to manage (ADR-0035).
- Deleting a file is deliberately awkward, consistent with ADR-0023's no-deletion posture — file deletion is an administrative operation, not an application feature.

## Rejected alternatives

| Alternative | Why rejected |
|---|---|
| **Local filesystem on the VM** | Unbacked-up business records on a single box with no replica. The predecessor's posture. |
| **MinIO on the same server** | For backups this is not a backup at all — the failure that destroys the database destroys the archive. For application files it adds a service to the memory budget while still failing with the host. Correct only for local development. |
| **Storing files as `bytea` in PostgreSQL** | Inflates the database, inflates every backup, and puts large-object I/O in the transactional path. |
| **AWS S3 specifically** | No objection technically; R2/B2 are chosen for cost (notably egress) at this scale. The adapter makes the provider a one-line change, so this is not a lock-in decision. |
| **Public bucket URLs** | Bypasses the permission model entirely — anyone with a URL reads a client's documents. |

## Enforcement

- **Port discipline**: the storage SDK may be imported only inside `infrastructure/` (ADR-0008 rule 2). Domain and application layers see only the `FileStorage` interface.
- **Adapter parity test**: the same integration test suite runs against MinIO (development) and the production provider, so behaviour differences surface in CI rather than production.
- **Signed-URL test**: an integration test asserts a bucket object is not retrievable without a signature and that signatures expire.
- **Config assertion**: production boot fails if the `FileStorage` adapter resolves to the local-filesystem implementation.
- **Separation assertion**: a startup check fails if the application file bucket and the backup bucket resolve to the same bucket or the same credentials.
- **Upload validation tests**: content-type and size limits are asserted, including a test that a mismatched extension and magic-number combination is rejected.
