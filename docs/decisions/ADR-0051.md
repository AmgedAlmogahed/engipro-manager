# ADR-0051: Offline sync strategy

**Status:** Proposed — spike complete, awaiting user review
**Date:** 2026-08-09

## Context

Sales reps work in the field and the requirements call for key mobile actions to work offline and sync. No prior ADR said how. This is the decision that is expensive to get wrong late: an online-first client data layer retrofitted for offline is a rewrite, and a bad conflict-resolution story on a *quotation* system can produce two divergent versions of a price — a financial correctness failure, not a UX blemish.

A timeboxed spike (2026-08-09) evaluated PowerSync, ElectricSQL, Zero, and a hand-rolled approach against this architecture. Two findings dominate everything else:

**Finding 1 — replication-based read sync bypasses RLS and creates a second authorization surface.** PowerSync, ElectricSQL, and Zero all consume Postgres logical replication, which reads the WAL with a `REPLICATION`-privileged role — RLS (ADR-0022) does not apply to it; PowerSync's own service explicitly warns when replicating RLS-enabled tables without `BYPASSRLS`. Per-user filtering therefore moves into engine-side definitions (PowerSync "sync rules", Electric "shapes", Zero queries). Those definitions duplicate what `scopeFilter()` (ADR-0021) already expresses — **two authorization models that can disagree, which is conflict-register C1 reborn at the sync layer.** The register's worst defect, reintroduced by infrastructure.

**Finding 2 — engine write paths bypass the domain.** Any write path that syncs client mutations into Postgres directly skips `authorize()`, the state machines (ADR-0029), the same-transaction audit (ADR-0024), and the outbox (ADR-0026) — structurally the C5 pattern. All three engines *can* route writes through your own backend instead (PowerSync `uploadData`, Electric's writes-are-your-API posture), which concedes the point: **the write path must be ours regardless of engine choice.**

What changed since this number was reserved: the component whose hand-rolling was the original risk — a durable, replay-safe client mutation queue — now exists as first-party TanStack infrastructure. `@tanstack/offline-transactions` (with TanStack DB 0.6, March 2026) implements the outbox pattern client-side: mutations persisted to IndexedDB before dispatch, exponential backoff with jitter, FIFO ordering, leader election for multi-tab. The client stack decided in ADR-0050 (Vite + TanStack Query) extends to TanStack DB without replacement.

## Decision

**Offline is scoped by data shape, not bolted on by engine.** Three rules, then the mechanism.

**Rule 1 — offline writes are limited to conflict-free shapes:**
- **Append-only records** — interactions, visit logs, follow-ups, notes. No conflict is possible by construction; two offline appends are two rows.
- **OWN-scoped drafts** — quotation drafts belonging to the rep. The server assigns the version number on sync (ADR-0025 counters are server-side); two offline edits to the same draft resolve last-write-wins *within one owner's own draft*, which is the only place last-write-wins is acceptable.
- **Status transitions never execute offline.** A transition has side effects (PO issuance, audit, events) and permission checks that must be evaluated server-side at execution time. Offline, the UI queues an *intent* at most and shows it as pending — the same posture ADR-0047 takes against optimistic updates for side-effectful transitions.

**Rule 2 — the write path is the existing API.** Queued mutations replay through the same REST endpoints, use-cases, state machines, audit, and outbox as online writes. Every replayed mutation carries an **idempotency key** (client-generated UUIDv7), using the same idempotency machinery ADR-0046 already mandates for inbound integrations — a replayed queue after a crash produces one effect per mutation. A mutation rejected on replay (state moved on, permission revoked, validation failed) is surfaced to the user as a rejected pending item with the server's reason — never silently dropped, never silently forced.

**Rule 3 — offline reads are persisted query caches, not a replica.** TanStack DB collections persisted to IndexedDB, covering an explicit allow-list: the rep's OWN clients, pipeline, quotations, follow-ups, and the reference data (service catalog, settings) needed to draft. Data is fetched through the API under `scopeFilter()` — **one authorization model, no replication role, no second scope definition, no RLS bypass.** Staleness is bounded by last-fetch and shown (“as of …”), consistent with ADR-0030's staleness-disclosure posture.

**Mechanism (Phase: with `apps/web` mobile flows):** TanStack DB + `@tanstack/db-sqlite-persistence-core`/IndexedDB persistence + `@tanstack/offline-transactions` for the mutation outbox. No new server-side service. No replication slot. No engine.

**Escalation path, recorded now:** if measured usage shows the persisted-cache read model insufficient (reps needing fresher-than-fetch data across a wider surface), **ElectricSQL shapes** are the designated read-path escalation — read-only, HTTP-based, behind the same API gateway authentication, with shape definitions **generated from the permission catalog** so the second surface is derived, not parallel. Writes do not change. PowerSync and Zero are not the escalation path (below).

## Consequences

**Positive**
- One authorization model, end to end. Finding 1's C1-recurrence risk is not mitigated — it is not incurred.
- Every offline write passes through the domain: state machines, audit, outbox, permissions. Finding 2 resolved by construction.
- No new stateful service on the 6 GB box (ADR-0012/0032 budgets untouched); no `REPLICATION` role; no bucket-storage dependency.
- The conflict problem is dissolved rather than solved: append-only + own-drafts + no-offline-transitions leaves nothing that requires a merge algorithm on financial data.
- Client stack is a strict extension of ADR-0050's choices; first-party maintained queue instead of bespoke code.

**Negative / trade-offs**
- Offline reads are as fresh as the last fetch, not continuously synced. A rep who hasn't opened the app for days works from stale data. Accepted: bounded, disclosed staleness on OWN-scope data — and the escalation path exists with a measured trigger.
- Pending-intent UX for transitions is more honest but less magical than full offline execution; reps see “queued, will apply when online” for status moves.
- TanStack DB 0.6 is young (persistence landed 2026-03). Mitigated: it sits *client-side only* — a failure loses a queue on one device, not server data — and the blast radius is bounded by Rule 2 (server never trusts the client's ordering or authorization).
- The offline collection allow-list must be maintained as modules ship; an unlisted collection silently has no offline support (visible in review, not silent corruption).

## Rejected alternatives

| Alternative | Why rejected |
|---|---|
| **PowerSync (self-hosted Open Edition)** | Replication-based: RLS bypass + sync-rules-as-second-authz (Finding 1). Adds a sync service plus bucket storage to the box. Client model is SQLite-first, replacing rather than extending the ADR-0050 stack. Its write path through one's own backend is correct — but that half is available without the engine. |
| **ElectricSQL now** | The best of the engines for this architecture (read-only shapes, writes stay ours) — which is why it is the recorded escalation path rather than the start. Adopting it day one buys continuous read sync nobody has yet measured a need for, at the cost of a service, a replication slot, and a derived-but-real second read-scope surface. |
| **Zero (Rocicorp)** | 1.0 stable only since 2026-06; requires `zero-cache` service and adopts ZQL as the client data language — the largest stack commitment of the three, replacing the decided client layer wholesale. |
| **Full hand-rolled queue** | The original risk this number was reserved against. Superseded by events: the queue half now exists first-party (`@tanstack/offline-transactions`); what remains hand-rolled is only the allow-list and replay wiring, which is application code through existing endpoints. |
| **No offline support** | Contradicts a stated requirement; sales reps work in the field, and Saudi site visits include genuinely offline environments. |
| **Full offline execution of transitions (CRDT/merge on quotations)** | Merging concurrent financial state is the two-prices failure mode. No merge algorithm makes an approval-gated transition safe to execute without the server's current state. |

## Enforcement

- **Dependency denylist** (ADR-0012 pattern): `@powersync/*`, `electric-sql`/`@electric-sql/*`, `@rocicorp/zero` fail the CI dependency check unless this ADR is superseded — the escalation is a decision, not a drift.
- **Idempotency**: every mutation endpoint accepts the client idempotency key; an integration test replays a queued mutation twice and asserts one effect (same machinery and test shape as ADR-0046).
- **Replay-against-moved-state test**: a queued transition intent replayed after the server state changed is rejected with a reason and produces no partial write — asserted in the integration lane.
- **No-offline-transition lint**: mutation hooks for endpoints that emit domain events may not be registered with the offline queue executor; same lint family as ADR-0047's optimistic-update rule.
- **Allow-list is data**: persisted collections are declared in one module; the zero-rules-parsed guard (ADR-0048 standing rule) applies — an empty allow-list is a distinct state, not silent success.
- **Staleness disclosure**: persisted collections carry `fetchedAt`; a UI surface rendering offline data without the staleness indicator fails the ADR-0047 structural lint's offline variant.
