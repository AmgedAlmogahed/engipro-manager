# ADR-0041: Service level objectives

**Status:** Accepted
**Date:** 2026-08-02
**Accepted:** 2026-08-08 — ratified as wave W6 (infrastructure).

**On the targets.** The original status line read "Accepted — initial targets require confirmation", which is the same self-contradiction ADR-0042 had: a status qualified by a condition that has not been met is not a status. Resolved the same way. The targets below are **initial values**, and what they drive is bounded: they raise alerts and open issues. **No target triggers a destructive or automated corrective action**, so a wrong figure produces noise rather than damage. Confirmation against real usage is an outstanding action that *cannot* precede real usage, and the quarterly review is the correction mechanism. Treating that as a blocker would mean the SLOs arrive after the system they are meant to measure.

## Context

Several decisions in this set are deliberately deferred **until a measurement crosses a threshold**:

- ADR-0030 defers materialized views until a report query exceeds roughly 200 ms.
- ADR-0030 defers CQRS and read replicas until reporting measurably affects operational latency.
- ADR-0012 records a job-throughput ceiling as the trigger to reconsider the queue.
- ADR-0027 records the same for Redis.
- Caching is deferred across the board on the same basis.

**Without a measurement loop, every one of those deferrals is unenforceable** — they become "we will do it when it feels slow," which in practice means either never or prematurely, decided by whoever is most annoyed that week.

Separately, the backup regime (ADR-0031) produces an RTO and RPO that should be stated rather than implied.

## Decision

We will define and measure these objectives. **Initial values are proposals and need confirmation against real usage.**

| Objective | Initial target | Measured by |
|---|---|---|
| API p95 latency (read endpoints) | **< 300 ms** | Request logs (ADR-0036) |
| API p95 latency (write endpoints) | **< 800 ms** | Request logs |
| Report endpoint p95 | **< 2 s** — crossing this opens the materialized-view decision (ADR-0030) | Request logs |
| Quotation PDF generation | **< 15 s** from request to stored document | Job duration metric |
| Outbox dispatch lag p95 | **< 10 s** | Age of oldest pending row |
| Notification delivery (in-app) | **< 30 s** from the triggering event | Execution timestamps |
| **RPO** | **≈ 60 s** — set by `archive_timeout` (ADR-0031) | Configuration |
| **RTO** | **Whatever the monthly restore drill measures.** Not a target we assert; a number we observe | Restore drill result row |
| Availability | Best-effort, business hours. **No formal uptime SLO** while single-VM | Uptime check |

Each objective is either a **gate** (crossing it opens a specific deferred decision) or an **alert** (crossing it pages someone). They are reviewed quarterly.

## Consequences

**Positive**
- Deferred decisions gain an objective trigger, so "when do we add caching?" has an answer that is not a preference.
- The RTO is a measured fact from the restore drill rather than an assumption.
- Explicitly declining an availability SLO is honest about a single-VM deployment, rather than implying a guarantee the architecture cannot make.

**Negative / trade-offs**
- Targets set before real usage are guesses. Setting them too tight produces noisy alerts that get ignored; too loose and they never fire. Hence quarterly review and the explicit "requires confirmation" status.
- Measurement infrastructure is itself work (ADR-0036).
- An SLO without an owner is decoration. Someone must be accountable for the review.

## Rejected alternatives

| Alternative | Why rejected |
|---|---|
| **No SLOs** | Makes every deferral in this ADR set unenforceable, which is the specific failure this document exists to prevent. |
| **Formal availability SLO now** | A single VM with no replica cannot honour a meaningful uptime commitment. Declaring one would be false. |
| **Copying industry-standard targets** | An internal ERP with ~50 users has a different latency profile from a consumer product; borrowed numbers would be arbitrary. |
| **Asserting an RTO target** | RTO is determined by how long a restore actually takes. Measuring it is honest; asserting it is not. |

## Enforcement

- **Metric collection**: request duration, job duration, and outbox lag are emitted as structured log fields and metrics (ADR-0036).
- **Gate automation**: a scheduled job compares report-endpoint p95 against the threshold and, when crossed, opens a tracking issue referencing ADR-0030 — so the decision surfaces automatically rather than depending on someone noticing.
- **Alerts**: outbox lag and notification delivery breaches page; latency breaches open an issue rather than paging.
- **RTO recording**: the monthly restore drill writes duration to a result row; the current RTO is the trailing maximum of the last three drills (ADR-0031).
- **Quarterly review**: a recurring calendar item; the review updates this ADR's table, which is the only mechanism here that depends on a human remembering — recorded as a known weakness.
