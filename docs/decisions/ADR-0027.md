# ADR-0027: Job queue — graphile-worker

**Status:** Accepted
**Date:** 2026-08-02
**Accepted:** 2026-08-08 — ratified as wave W5 (platform mechanics).

## Context

The system needs background work: the outbox relay (ADR-0026), notification dispatch (ADR-0028), PDF generation (ADR-0032), SLA recomputation, licence reminder crons, dormant-client detection, and overdue-payment flagging.

The constraint that decides this is the deployment target: a single OCI Ampere ARM VM with roughly 6 GB of RAM, already running PostgreSQL, the API, the admin app, and a Chromium container (ADR-0032's memory budget).

Redis for BullMQ would consume 256–512 MB of that budget. The throughput it buys — roughly 2,000 jobs/second versus 100–200 for a PostgreSQL-backed queue — is two orders of magnitude beyond what an internal ERP for one engineering consultancy will generate.

## Decision

We will use **graphile-worker**, backed by the existing PostgreSQL instance.

Rationale:
- **Zero additional infrastructure and zero additional RAM.**
- `LISTEN`/`NOTIFY` wake-up gives sub-3ms latency under normal conditions, better than polling-based alternatives.
- Built-in exponential backoff with 25 retries spanning roughly three days — more than sufficient for transient provider failures.
- Cron syntax for scheduled jobs, so no separate scheduler.
- `job_key` deduplication for singleton jobs.
- **ACID job scheduling**: a job enqueued in the same transaction as a business change cannot be orphaned. Redis cannot offer this, and it is the property that matters most here.

graphile-worker's own tables live in a dedicated schema, consistent with ADR-0013.

## Consequences

**Positive**
- One less stateful service to run, secure, monitor, back up, and reason about.
- Transactional enqueue is a correctness property, not a convenience.
- Failure handling (backoff, retry limits) is provided rather than hand-rolled.
- Jobs are visible with SQL — inspecting the queue is a query, not a separate tool.

**Negative / trade-offs**
- Throughput ceiling of roughly 100–200 jobs/second. Recorded as the revisit threshold; not a constraint at ERP volumes.
- Queue load and application load share one PostgreSQL instance; a heavy job burst competes with user queries. Mitigated by concurrency limits on the worker.
- Job table churn adds autovacuum pressure, on top of the outbox's.
- The NestJS integration wrapper is community-maintained. The Node API is simple enough to wrap directly if that becomes a problem.

## Rejected alternatives

| Alternative | Why rejected |
|---|---|
| **BullMQ + Redis** | 256–512 MB of a 6 GB box for throughput never approached, and it removes the transactional-enqueue guarantee. Reconsider only if Redis is introduced for another reason — a session store or rate limiting — at which point BullMQ's richer features (parent/child flows, rate limiting) become worth adopting. |
| **pg-boss** | Also PostgreSQL-backed and a reasonable choice; polling-based wake-up gives slightly higher latency than graphile-worker's `LISTEN`/`NOTIFY`, and its cron support is comparable. Close second, not materially better. |
| **A hand-rolled queue over the outbox table** | The outbox is a ledger for domain events, not a general job queue. Conflating them would mean PDF rendering and domain events share retry semantics and retention rules, which they should not. |
| **Cloud queue (SQS, Cloud Tasks)** | External dependency and network hop for a single-server deployment, plus it breaks transactional enqueue. |
| **`node-cron` in the API process** | No durability, no retries, and two API instances would double-fire every scheduled job. |

## Enforcement

- **Dependency denylist** (ADR-0012): adding `redis`, `ioredis`, or `bullmq` fails the CI dependency check without an ADR superseding this one.
- **Transactional enqueue**: jobs are enqueued through the same unit of work as the business change; an integration test asserts a rolled-back transaction leaves no job behind.
- **Idempotency**: every job handler is idempotent and tested by double invocation, matching ADR-0026's consumer rule.
- **Singleton jobs**: scheduled jobs use `job_key` so two worker instances cannot double-fire; asserted by a test running two workers concurrently.
- **Concurrency limit**: worker concurrency is configured explicitly and capped so background work cannot starve user-facing queries.
- **Monitoring**: failed-job count and oldest-pending-job age are exported as metrics with alerts (ADR-0036).
