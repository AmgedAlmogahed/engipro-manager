# ADR-0005: NestJS with the Fastify adapter

**Status:** Proposed
**Date:** 2026-08-02

## Context

ADR-0006 commits to ports and adapters on the outbound side: use-cases depend on interfaces, and infrastructure adapters are bound to those interfaces at composition time. **Dependency injection is the load-bearing capability** for that design. Without a DI container you either hand-wire a composition root or pass dependencies through constructors manually across dozens of modules.

The predecessor used NestJS with the default Express adapter. That was not the source of its defects — those came from the absence of a domain layer — but the framework choice should be re-derived rather than inherited.

## Decision

We will use **NestJS with the Fastify adapter** (`NestFactory.create<NestFastifyApplication>(AppModule, new FastifyAdapter())`).

Critically: **`domain/` and `application/` layers are plain TypeScript.** No decorators, no `@Injectable`, no imports from `@nestjs/*`. NestJS exists only in `interface/` (controllers, guards, pipes) and in each module's composition file.

## Consequences

**Positive**
- DI, modules, guards, interceptors, and OpenAPI integration are first-class rather than hand-rolled.
- The Fastify adapter roughly closes the performance gap to standalone Fastify (~45k vs ~28k req/s with Express), and `@nestjs/swagger` works with both adapters.
- Guards give a single interception point for `authorize()` (ADR-0021).
- Because the domain and application layers import nothing from NestJS, swapping the HTTP framework later touches only `interface/` and module wiring — roughly 15% of the API and none of the business logic.

**Negative / trade-offs**
- Decorator-heavy code obscures execution flow and makes some debugging harder. This is a real cost, contained to the interface layer by the rule above.
- `experimentalDecorators` and `emitDecoratorMetadata` are still required; NestJS's migration to TC39 decorators is incomplete as of 2026. Pin the NestJS version and verify `@nestjs/swagger` compatibility before upgrading.
- Learning curve for developers unfamiliar with Angular-style DI.
- Some Express-specific middleware is incompatible with the Fastify adapter. First-party NestJS constructs (Guards, Interceptors, Pipes) are unaffected.

## Rejected alternatives

| Alternative | Why rejected |
|---|---|
| **NestJS + Express (default)** | ~28k vs ~45k req/s for a one-line change, with no compensating benefit. Only relevant if an Express-only middleware becomes essential. |
| **Fastify standalone + Awilix / InversifyJS** | Recovers exactly the complexity NestJS was dropped to avoid — you build DI, module conventions, guard equivalents, and OpenAPI plumbing yourself, then maintain those conventions with documentation instead of a framework. Roughly a week of plumbing for a small team, and no ecosystem. |
| **Hono** | No dependency injection at all. Its performance advantage is irrelevant for an internal ERP. Choosing it means the ports/adapters design has no container and every wiring decision is manual. |
| **Express + manual DI** | Same objection as Fastify standalone, with worse performance and a less modern plugin model. |

## Enforcement

- **dependency-cruiser** rule `no-vendor-in-domain-or-application` forbids `^node_modules/@nestjs/` from `apps/api/src/modules/*/domain/` and `.../application/` and from `packages/domain/`. This is what makes the framework replaceable rather than merely "layered."
- **CI**: `packages/domain` builds with a tsconfig that does not include `@nestjs/*` types; a decorator in that package fails to compile.
- **Adapter check**: a smoke test asserts the app bootstraps under `FastifyAdapter` and that `/api/docs` serves a valid OpenAPI document (ADR-0010).
