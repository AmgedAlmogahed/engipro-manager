# ADR-0016: Money representation

**Status:** Proposed
**Date:** 2026-08-02

## Context

The predecessor stored money as `Float` — `totalAmount`, `lifetimeValue`, `contractValue`, `subtotal` are all floating point in `prisma/schema.prisma`. The frozen prototype inherited the same mistake in `utils/quote.ts`.

Binary floating point cannot represent 0.1 exactly. On a system that issues quotations with percentage discounts, computes 15% VAT, splits totals into a payment schedule that must sum to exactly 100%, and calculates commission percentages, this produces reconciliation errors that are extremely difficult to trace back to a cause.

PostgreSQL's documentation is direct: `numeric` yields exact results, floating point for money is "not recommended," and the `money` type is locale-dependent (`lc_monetary`), truncates on integer division, and requires a two-step cast to convert.

Two decimal places are insufficient for intermediate arithmetic: 14.5% VAT on 99.99 produces 14.49855, and rounding that at each line item before summing produces a different total than rounding once at the end.

## Decision

We will represent money as:

| Purpose | Type | Example |
|---|---|---|
| Monetary amounts | `numeric(19, 4)` | `2450000.0000` |
| Rates and percentages | `numeric(5, 4)` | `0.1500` for 15% |
| Currency | `char(3)` NOT NULL, ISO 4217 | `SAR` |

- 19 total digits gives 15 to the left of the decimal — sufficient for any realistic contract value — and 4 to the right so intermediate arithmetic does not round prematurely.
- **Presentation rounds to 2 places; storage and calculation keep 4.**
- Every monetary column is paired with an explicit currency column. SAR-only initially (ADR-0040), but the schema does not assume it.
- A `Money` value object in `packages/domain` wraps amount and currency and **refuses to add different currencies**.
- Drizzle returns `numeric` as **strings**; `decimal.js` is the only permitted arithmetic path.

**Never** `float`, `double precision`, `real`, or PostgreSQL's `money` type.

## Consequences

**Positive**
- Exact arithmetic. Invoice totals reconcile.
- The 100%-payment-schedule invariant (ADR-0029) becomes checkable exactly, not within a tolerance.
- Multi-currency later requires no schema migration (ADR-0040).

**Negative / trade-offs**
- `numeric` arithmetic is materially slower than integer arithmetic. Irrelevant at ERP volumes; recorded for completeness.
- Values cross the ORM boundary as strings, so every arithmetic site must go through `decimal.js`. A missed conversion produces string concatenation — `"100" + "50" === "10050"` — which is a silent, severe bug. The lint rule below exists specifically for this.
- Developers must remember that the domain `Money` type is not a `number`.

## Rejected alternatives

| Alternative | Why rejected |
|---|---|
| **`float` / `double precision`** | Inexact. This is the predecessor's defect and the most expensive one to discover late. |
| **PostgreSQL `money` type** | Locale-dependent output (`lc_monetary`), truncating integer division, and awkward casting — all documented in the PostgreSQL manual. |
| **`bigint` minor units (halalas)** | Genuinely defensible and faster. Rejected because every read and write requires a mental conversion, a single missed division produces a 100× error, and multi-currency with differing minor-unit scales (JOD has 3) becomes error-prone. `numeric` is self-describing in the database. |
| **`numeric` without an explicit scale** | Drizzle and Prisma have both been observed generating unexpected precision. Explicit precision in the DDL is the point. |
| **Two decimal places** | Insufficient for intermediate VAT and discount arithmetic; forces premature rounding at each line item. |

## Enforcement

- **Migration lint** (ADR-0014): any `float`, `double precision`, `real`, or `money` column fails CI. Any column whose name matches a monetary pattern (`*_amount`, `*_price`, `*_total`, `*_value`, `subtotal`, `discount`, `vat`) that is not `numeric(19,4)` fails. Any `*_rate` or `*_pct` column that is not `numeric(5,4)` fails.
- **ESLint rule**: arithmetic operators applied to a value typed as `Money` or to a known `numeric`-backed field are an error; only `decimal.js` methods are permitted.
- **Domain unit tests**: `Money.add` across differing currencies throws; a rounding-behaviour test suite covers VAT and discount cases at 4 decimal places.
- **Property test**: for randomly generated line items, `sum(line totals) === quote total` exactly, and the payment schedule sums to exactly 100%.
