# ADR-0025: Business number allocation

**Status:** Proposed
**Date:** 2026-08-02

## Context

Every first-class entity needs a human-facing identifier that can be spoken on a phone call, written in an email, and printed on a document: `CLIENT-2026-0042`, `QUO-2026-0021`, `RFQ-2026-0031`, `PO-2026-0012`, `PRJ-2026-0007`.

These are distinct from primary keys (ADR-0015). Primary keys are opaque and internal; business numbers are meaningful, sequential, and appear on legal and financial documents.

Two failure modes must be prevented:

1. **Duplicates.** The frozen prototype currently allocates with the equivalent of `MAX()+1`, which under concurrency assigns the same number twice. On an invoice or purchase order this is an accounting problem, not a cosmetic one.
2. **Gaps where gaps are unacceptable.** PostgreSQL's documentation states this plainly: "Because `nextval` and `setval` calls are never rolled back, sequence objects cannot be used if 'gapless' assignment of sequence numbers is needed."

The predecessor also had entities with **no** business number at all (C15 — a pipeline entry could not be referenced in conversation or on paper).

## Decision

We will allocate business numbers from a **counter row**, updated inside the same transaction as the entity insert.

```sql
CREATE TABLE platform.business_counters (
  organization_id uuid NOT NULL,
  entity_type     text NOT NULL,     -- 'CLIENT' | 'QUO' | 'RFQ' | 'PO' | 'PRJ' | …
  year            int  NOT NULL,
  last_value      bigint NOT NULL DEFAULT 0,
  PRIMARY KEY (organization_id, entity_type, year)
);
```

```sql
INSERT INTO platform.business_counters (organization_id, entity_type, year, last_value)
VALUES ($1, $2, $3, 1)
ON CONFLICT (organization_id, entity_type, year)
DO UPDATE SET last_value = platform.business_counters.last_value + 1
RETURNING last_value;
```

The `UPDATE` takes a row-level lock automatically; concurrent allocators queue and are served in order. Formatting (`CLIENT-2026-0042`) happens in the application from the returned value, with the format held in Settings.

**Every first-class entity gets one**, including opportunities — the specific gap C15 identifies.

## Consequences

**Positive**
- No duplicates under concurrency, and no gaps from rolled-back transactions, because allocation shares the business transaction.
- Per-organisation and per-year counters, so numbering restarts naturally each year and does not leak volume across tenants.
- The format is configuration, so changing `CLIENT-` to `CL-` does not require a deploy.

**Negative / trade-offs**
- All allocations for one `(organization, entity_type, year)` serialise on a single row lock. At ERP volumes this is irrelevant; at thousands of inserts per second it would be a bottleneck. Recorded as the revisit threshold.
- The lock is held for the remainder of the business transaction, so a long transaction holds the counter. Allocation should therefore happen **late** in the transaction, immediately before commit.
- Rolled-back transactions release the number for reuse, which is the desired gapless behaviour but means a number briefly seen in an error path may later belong to a different record. Numbers must not be shown to users before commit.

## Rejected alternatives

| Alternative | Why rejected |
|---|---|
| **`MAX(number) + 1`** | Allocates duplicates under concurrency. Present in the frozen prototype and must not carry over. |
| **PostgreSQL sequences** | Explicitly documented as non-gapless: `nextval` is never rolled back. Acceptable for opaque internal identifiers, unacceptable for document numbers. |
| **Advisory locks** | Workable, but the lock key is implicit and easy to get wrong, and the counter still needs a table. The row lock is simpler and self-documenting. |
| **UUID as the human identifier** | Unspeakable on a phone call and unusable on a printed document. |
| **Allocate outside the transaction** | Reintroduces gaps on rollback and creates a window where a number exists with no record. |

## Enforcement

- **Concurrency test**: an integration test runs N parallel allocations for the same entity type and asserts N distinct, contiguous values.
- **Rollback test**: a transaction that allocates and then rolls back is asserted to leave the counter unchanged, and the next allocation returns the same value.
- **Migration lint** (ADR-0014): `CREATE SEQUENCE` used for a business-number column fails CI.
- **Uniqueness**: a unique index on `(organization_id, business_number)` per entity table, so even a logic error cannot persist a duplicate.
- **Coverage test**: every aggregate root exposes a business number; a structural test asserts each first-class entity table has the column and the index. Closes C15.
- **Late allocation**: a lint check flags counter allocation occurring before other significant work in a use-case, to keep the lock window short.
