# ADR-0039: ZATCA e-invoicing applicability

**Status:** Accepted
**Date:** 2026-08-02
**Accepted:** 2026-08-08 — open question answered: **yes**, Abak invoices entities inside Saudi Arabia. ZATCA e-invoicing applies.

## Context

Saudi Arabia's Zakat, Tax and Customs Authority (ZATCA) mandates e-invoicing (*Fatoorah*) for resident taxable persons. Phase 1 (generation) required structured electronic invoices with specific fields and a QR code. Phase 2 (integration) requires invoices to be cryptographically signed, formatted as XML (UBL 2.1), reported or cleared through ZATCA's platform, and to carry a compliant QR code.

Abak is an engineering consultancy operating in Saudi Arabia. If it invoices Saudi entities, this is not optional and it is not a late-stage feature.

**Why this must be answered before Finance is built:** ZATCA compliance shapes the invoice data model (additional mandatory fields: seller and buyer VAT registration numbers, commercial registration, invoice type codes, line-item tax categories, invoice counter value, previous invoice hash), the invoice numbering rules (ADR-0025), the cryptographic signing and archival requirements, and — critically — **the PDF worker's output contract** (ADR-0032), because the QR code and the compliant layout are part of the document, not decoration.

Retrofitting these fields into an invoice table that already holds issued invoices means either a migration of legally significant records or a parallel invoice model. Both are bad.

## Decision

ZATCA e-invoicing applies. We will therefore:

1. **Carry ZATCA-mandated fields in Finance's invoice aggregate from its first migration**, even though the signing and reporting integration ships later. The mandated set: seller and buyer VAT registration numbers, commercial registration, invoice type codes, line-item tax categories, invoice counter value (ICV), and previous-invoice hash (PIH).
2. **Treat signed UBL 2.1 XML generation and ZATCA platform integration as an Integrations anti-corruption layer** (ADR-0006) with its own adapter, scheduled at Phase 5. Nothing about ZATCA's API shape reaches the Finance domain.
3. **Carry a compliant TLV-encoded QR code and layout in the PDF worker's output contract from v1.** The document contract is owned here; the worker's runtime and its build-time and post-deploy checks are owned by ADR-0032.
4. **Align invoice retention with ADR-0042** (10 years, financial/tax class).

### Invoices carry two independent identifiers

This is the part that is easy to get wrong, so it is stated explicitly.

| Identifier | Purpose | Mechanism | Resets |
|---|---|---|---|
| Business number, e.g. `INV-2026-0042` | Human-facing reference on documents and in conversation | `platform.business_counters` (ADR-0025), unchanged | Yearly, per organisation |
| ZATCA ICV + PIH | Statutory invoice counter and hash chain | `finance.einvoice_counters`, owned by Finance | **Never** |

ADR-0025's counter **cannot** carry the ICV. Its primary key is `(organization_id, entity_type, year)` and ADR-0025:49 states numbering "restarts naturally each year" — but the ICV must never reset, including at year boundaries, and it is scoped per EGS unit rather than per entity type per year. Separately, a hash chain is cryptographic state and has no business living in an allocation counter.

```sql
CREATE TABLE finance.einvoice_counters (
  organization_id     uuid  NOT NULL,
  egs_unit_id         uuid  NOT NULL,   -- e-invoice generation solution unit
  last_icv            bigint NOT NULL,  -- monotonic, never reset
  last_invoice_hash   bytea,            -- PIH; NULL only for the first invoice in the chain
  PRIMARY KEY (organization_id, egs_unit_id)
);
```

The ICV is incremented and the PIH written **in the same transaction as invoice issuance**, following ADR-0025's row-lock and late-allocation discipline even though the table is separate.

## Consequences

**Positive**
- No migration of legally significant records. The chained fields exist before the first invoice is issued, which is the only point at which a hash chain can begin.
- The PDF contract is fixed before any document reaches a client, so no reissuing.
- ZATCA's platform shape stays behind an adapter, so its versioning and downtime are an integration concern, not a Finance concern.

**Negative / trade-offs**
- A wider invoice model and a more constrained PDF contract from day one, including fields that stay unused until Phase 5.
- Two counters on one entity is a genuine conceptual cost. Mitigated by the table above and by naming: `business_number` versus `icv`, never "invoice number" unqualified.
- The PIH chain means invoice issuance is strictly serial per EGS unit. At consultancy invoice volumes this is irrelevant; it is recorded as the revisit threshold.
- Phase 5 is a hard compliance deadline rather than a feature slot. Deferring the integration is safe; forgetting it is not.

## Rejected alternatives

| Alternative | Why rejected |
|---|---|
| **Build a generic invoice model and adapt later** | The additional fields are mandatory and some are cryptographically chained (invoice counter and previous-invoice hash). A chain cannot be retrofitted onto records issued before it existed. |
| **Use a third-party invoicing service for KSA compliance** | A legitimate option that should be evaluated *if* the answer is yes — it would sit behind an Integrations adapter. Not a reason to defer the data model decision. |
| **Assume it applies and build it regardless** | Moot — it does apply. Retained because it was a live alternative while this was blocked. |
| **Put the ICV in `platform.business_counters`** | The primary key includes `year` and the mechanism resets annually by design (ADR-0025:49). The ICV must never reset and is scoped per EGS unit. Overloading the table would either break yearly business numbering or break the statutory counter. |

## Enforcement

- **Contract tests**: every ZATCA-mandated field is asserted present and non-null on issued invoices. An invoice cannot reach `issued` with a null ICV.
- **Migration lint** (ADR-0014): the Finance invoice migration fails if the mandated columns are absent, so the fields cannot be omitted "for now" and added later.
- **Chain-integrity test**: issuing three invoices in sequence asserts `icv` increments by exactly one and each `last_invoice_hash` equals the hash of the prior invoice. A nightly job re-walks the chain per EGS unit and alerts on a break.
- **Never-reset assertion**: a test issues invoices either side of a simulated year boundary and asserts the ICV does **not** reset while the business number does. This is the check that keeps someone from later "helpfully" adding `year` to the counter key.
- **PDF golden-file test**: the QR code is present and decodes to the expected TLV payload. The post-deploy smoke test in ADR-0032 asserts the same on a real issued document.
- **Mining document**: `docs/mined/finance.md` records the field set and its ZATCA source, per ADR-0003.
