# ADR-0044: Explicit deny

**Status:** Accepted
**Date:** 2026-08-02
**Accepted:** 2026-08-08 — open question D answered: explicit deny is not required.

## Context

ADR-0021's model includes a fifth table, `user_permission_overrides`, carrying an `is_denial` flag. It allows a specific permission to be granted to, or **denied from**, an individual user regardless of their roles.

Explicit deny is a common request and is genuinely useful in one scenario: temporarily removing a capability from one person without disturbing a role that several others share. It is also a well-known source of complexity — it makes effective-permission calculation a two-pass operation (compute grants, then subtract denials), and it makes "why can't this user do X?" materially harder to answer.

It also interacts badly with the division of labour ADR-0049 establishes. Under ADR-0049 the resolver is a monotone single-pass union and monetary approval limits are evaluated separately, in the approval workflow engine. A denial pass reintroduces non-monotonicity into the one component that ADR-0049 deliberately keeps monotone, and it offers a second, weaker way to express "this person may not approve this" — competing with approval authority limits, which express it properly and with an amount attached.

No concrete requirement for explicit deny has been identified for Abak.

## Decision

We will **drop `user_permission_overrides`.** The table is not created.

- Individual exceptions are handled by creating a narrow role and assigning it, which keeps one mechanism instead of two.
- The table can be added later **without migration pain**: it is additive, and the resolver gains a subtraction pass. No existing data changes.
- If a concrete need appears, this ADR is superseded rather than amended.

If the answer is that explicit deny **is** required, the specification is: denial applies after grants, denial is never overridden by any grant, denial is always scoped to a single user and key, denial carries a mandatory reason and an optional expiry, and every denial is audited.

## Consequences

**Positive (of dropping)**
- One mechanism for authorization: roles grant, and that is all. "Why can this user do X?" is answered by listing their roles.
- The resolver stays a single pass, and monotone: adding a role can only add capability.
- Authorization has exactly two concepts, at two layers, with no overlap — permission keys in the resolver (ADR-0049), monetary limits in the approval workflow engine (ADR-0049). Denial would have been a third, straddling both.

**Negative / trade-offs**
- Removing one capability from one person requires creating a role, which is heavier than a single override row and can encourage role proliferation if it happens often.
- If the need turns out to be frequent, we will have deferred a feature that is then requested under time pressure. Mitigated by the change being purely additive.

## Rejected alternatives

| Alternative | Why rejected |
|---|---|
| **Implement explicit deny now** | No identified requirement. It adds a permanent third authorization concept and a two-pass resolver, and it overlaps with the approval authority limits of ADR-0049 — for a hypothetical. |
| **Deny at the role level rather than the user level** | Role-level denial makes role composition non-monotonic: adding a role could reduce access, which is the confusing behaviour ADR-0049 rejects when it settles on a most-permissive union. |
| **Use denial to cap financial approval authority** | This was the shape ADR-0043 originally reached for. It encodes a monetary control as an absence of permission, so the limit has no amount attached and cannot be expressed as "up to 500,000 SAR". ADR-0049 supersedes it with an explicit limit. |
| **Deactivate the user instead** | Far too blunt; the scenario is removing one capability, not all access. |
| **Keep the table but leave it unused** | An unused table invites accidental use without the resolver supporting it, producing a silently ignored denial — the worst outcome, because it looks like it worked. |

## Enforcement

- **The table is not created.** An unused table cannot be misused, and its absence makes the decision visible in the schema.
- **Resolver test**: the permission resolver has a test asserting a single-pass grant union with no denial concept, so adding denial later requires an explicit test change and therefore an explicit decision. This is the test that keeps the decision from being reversed silently.
- **Migration lint**: a table named `user_permission_overrides`, or any authorization table carrying an `is_denial`-style boolean, fails the migration lint (ADR-0014) with a pointer to this ADR.
- **Documentation**: `docs/mined/identity.md` records the individual-exception workaround (create a narrow role) so administrators have a documented path.
- If adopted later: the role-matrix suite (ADR-0009) gains denial cases including denial-versus-widest-grant precedence, and denials require a reason column that is `NOT NULL`.
