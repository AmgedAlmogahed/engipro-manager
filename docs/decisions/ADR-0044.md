# ADR-0044: Explicit deny

**Status:** Proposed — **BLOCKED** on open question D
**Date:** 2026-08-02

## Context

ADR-0021's model includes a fifth table, `user_permission_overrides`, carrying an `is_denial` flag. It allows a specific permission to be granted to, or **denied from**, an individual user regardless of their roles.

Explicit deny is a common request and is genuinely useful in one scenario: temporarily removing a capability from one person without disturbing a role that several others share. It is also a well-known source of complexity — it makes effective-permission calculation a two-pass operation (compute grants, then subtract denials), it interacts awkwardly with the multi-role resolution rule (ADR-0043), and it makes "why can't this user do X?" materially harder to answer.

No concrete requirement for explicit deny has been identified for Abak.

## Decision

**BLOCKED** on confirmation. Proposed: **drop `user_permission_overrides` initially.**

- Individual exceptions are handled by creating a narrow role and assigning it, which keeps one mechanism instead of two.
- The table can be added later **without migration pain**: it is additive, and the resolver gains a subtraction pass. No existing data changes.
- If a concrete need appears, this ADR is superseded rather than amended.

If the answer is that explicit deny **is** required, the specification is: denial applies after grants, denial is never overridden by any grant, denial is always scoped to a single user and key, denial carries a mandatory reason and an optional expiry, and every denial is audited.

## Consequences

**Positive (of dropping)**
- One mechanism for authorization: roles grant, and that is all. "Why can this user do X?" is answered by listing their roles.
- The resolver stays a single pass.
- No interaction to reason about between denial and the multi-role scope rule (ADR-0043).

**Negative / trade-offs**
- Removing one capability from one person requires creating a role, which is heavier than a single override row and can encourage role proliferation if it happens often.
- If the need turns out to be frequent, we will have deferred a feature that is then requested under time pressure. Mitigated by the change being purely additive.

## Rejected alternatives

| Alternative | Why rejected |
|---|---|
| **Implement explicit deny now** | No identified requirement. It adds a permanent second authorization concept, a two-pass resolver, and an interaction with ADR-0043 — for a hypothetical. |
| **Deny at the role level rather than the user level** | Role-level denial makes role composition non-monotonic: adding a role could reduce access, which is the confusing behaviour ADR-0043 rejects. |
| **Deactivate the user instead** | Far too blunt; the scenario is removing one capability, not all access. |
| **Keep the table but leave it unused** | An unused table invites accidental use without the resolver supporting it, producing a silently ignored denial — the worst outcome, because it looks like it worked. |

## Enforcement

- **While blocked / if dropped**: the table is **not created**. An unused table cannot be misused, and its absence makes the decision visible in the schema.
- **Resolver test**: the permission resolver has a test asserting a single-pass grant union with no denial concept, so adding denial later requires an explicit test change and therefore an explicit decision.
- **Documentation**: `docs/mined/identity.md` records the individual-exception workaround (create a narrow role) so administrators have a documented path.
- If adopted later: the role-matrix suite (ADR-0009) gains denial cases including denial-versus-widest-grant precedence, and denials require a reason column that is `NOT NULL`.
