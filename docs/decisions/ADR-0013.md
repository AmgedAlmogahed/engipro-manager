# ADR-0013: Schema per bounded context, no cross-schema foreign keys

**Status:** Proposed
**Date:** 2026-08-02

## Context

The predecessor kept every table in one PostgreSQL schema with a 2,700-line Prisma file. Its `Client` model had direct relations to leads, pipeline entries, quotes, RFQs, purchase orders, projects, invoices, and payments — making the client aggregate touch every context in the system. That is the coupling hub that made C5 and C18 possible and would make any future extraction a rewrite.

PostgreSQL schemas are described in its documentation as namespaces "analogous to operating system directories," explicitly intended for logical organisation and multi-user isolation.

## Decision

We will use **one PostgreSQL schema per bounded context**:

```
identity · access · org · crm · sales · delivery · finance · hr
notifications · integrations · reporting · audit · settings · platform
```

- **One owning module per table.** Only that module's repositories read or write it.
- **Foreign keys within a schema: yes.** Use them freely.
- **Foreign keys across schemas: deliberately omitted.** Store the identifier, no constraint. PostgreSQL permits schema-qualified `REFERENCES`; we choose not to use it. **The missing foreign key is the extraction seam.**
- `organization_id` is the sole exception and may be constrained everywhere — tenancy is infrastructure, not a domain relationship (ADR-0017).
- **`search_path` is set empty** in the application connection so every table reference must be schema-qualified, preventing name-resolution surprises and shadowing.
- Cross-context referential integrity becomes an application invariant, compensated by a **nightly consistency check** that reports orphaned identifiers.

## Consequences

**Positive**
- Boundary violations become visible in the schema itself, not just in import graphs.
- Per-schema `GRANT`/`REVOKE` allows database-enforced module ownership from Phase 4, which is stronger than lint.
- Extraction of a context later is `pg_dump --schema=finance` rather than a table-by-table archaeology exercise.
- Two modules may each have a `contacts` table without collision.

**Negative / trade-offs**
- **Referential integrity across contexts is weaker.** A bug can orphan a `clientId` in `sales` with no database error. The nightly check is the compensating control, and it detects rather than prevents.
- No cascade delete or cascade update across contexts; those become explicit application concerns.
- ER diagramming tools cannot draw cross-context relationships, so schema diagrams are incomplete by construction.
- Cross-context reporting cannot use a simple join; it goes through the reporting module (ADR-0030).
- Permission grants multiply by the number of schemas (14), enlarging the ACL surface.
- Drizzle's documentation on multi-schema edge cases is thin (ADR-0011) — validate migration ordering with a proof of concept.

## Rejected alternatives

| Alternative | Why rejected |
|---|---|
| **Single schema with naming conventions** | The predecessor's approach. Conventions are invisible to the database, so ownership cannot be enforced by grants and violations are only detectable by reading code. |
| **Database per context** | Loses cross-context transactions, which the core business flow needs (quote won → PO → project in one commit). Operationally disproportionate on one VM. |
| **Cross-schema foreign keys** | They work, and they would remove the orphan risk — but they are precisely what makes later extraction a data migration rather than a dump. Traded deliberately. |
| **Schema per tenant** | Different concern; ADR-0017 addresses tenancy with a column. Schema-per-tenant does not scale operationally past a small tenant count. |

## Enforcement

- **Database grants** (Phase 4): one role per schema; the application role receives `USAGE` on all schemas and table privileges only on the tables its modules own. A cross-module write then fails at the database, not in review.
- **`search_path=''`** in the connection string, forcing schema qualification.
- **Migration lint**: DDL adding a `REFERENCES` clause that crosses schemas fails, with `organization_id` allow-listed.
- **dependency-cruiser** rule `no-cross-module-internals` blocks the code path that would produce a cross-schema query.
- **Nightly consistency job**: for each declared cross-context reference, count rows whose target identifier no longer exists; non-zero raises an alert (ADR-0036).
