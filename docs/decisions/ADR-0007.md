# ADR-0007: Selective DDD by module tier

**Status:** Accepted
**Date:** 2026-08-02
**Accepted:** 2026-08-08 — ratified as wave W2 (architecture shape).

## Context

Applying full domain-driven design uniformly across an ERP produces well-documented harm on small teams: eight files for a simple GET route, a single reviewer becoming a bottleneck, and difficulty changing requirements once the model is fixed. One reported case delivered 30% of planned features in eight months under uniform DDD, versus 70% in four months after simplifying.

At the same time, this system has genuinely complex invariants that a thin service layer cannot protect: quotation approval chains with configurable thresholds, payment schedules that must total exactly 100%, licence-blocked project phases, and quote versioning. Those are precisely what DDD was designed for, and their absence in the predecessor produced C3, C4, C5, C12, and C16.

The literature's own conclusion is the resolution: choose DDD because it solves a problem you have right now, not as a default.

## Decision

We will apply DDD **selectively, by declared module tier**.

| Tier | Modules | Structure |
|---|---|---|
| **Rich** | Sales (RFQ, quotations, approvals), Finance, Delivery (projects, phases, licences), Access | Full: entities, value objects, policies, state machines, domain events, outbound ports, use-cases |
| **Medium** | CRM, Identity, Org, Notifications | Entities and a state machine where status exists; thin use-cases; ports for outbound I/O |
| **Thin** | Settings, service catalogue, regions, holidays, lookups | Service over the ORM. **No `domain/` folder at all.** |

Each module declares its tier in its `README.md`. Promotion from Thin to Medium/Rich is allowed and expected; demotion requires an ADR.

## Consequences

**Positive**
- Ceremony is spent where invariants exist. A regions lookup table does not get an aggregate.
- Because Thin modules have no `domain/` folder, ADR-0006 and ADR-0008 rules simply do not apply to them — no exemptions to configure, no lint suppressions.
- Velocity on the ~40% of the system that is genuinely CRUD is not taxed.

**Negative / trade-offs**
- Two styles coexist in one codebase; newcomers must learn both and must learn which applies where. Mitigated by the per-module tier declaration.
- Boundary cases require judgement — a module that starts Thin and grows invariants must be promoted, and that promotion is a refactor. The Rule of Three applies: tolerate the invariant in a service twice; promote on the third.
- Risk of tier inflation ("everything is Rich"). Mitigated by requiring the tier in the module README and reviewing it at PR time.

## Rejected alternatives

| Alternative | Why rejected |
|---|---|
| **Uniform full DDD** | Documented velocity destruction on small teams; 4–6× file multiplication on CRUD modules that have no invariants to protect. |
| **No DDD anywhere (services over ORM)** | This is the predecessor. Leaves no home for the 100%-schedule rule, the approval chain, or the licence-blocking rule, all of which then get enforced inconsistently per call site — literally C12. |
| **Decide per-module ad hoc without declaring a tier** | Produces inconsistency that cannot be reviewed or enforced, and makes the boundary lint rules ambiguous. |

## Enforcement

- **Module README**: each module has a `README.md` whose first line declares `Tier: Rich | Medium | Thin`. A CI script asserts every module directory contains one.
- **Structural consistency check**: CI asserts that a module declared Rich or Medium *has* a `domain/` folder, and that a module declared Thin does *not*. This makes tier drift visible instead of silent.
- **dependency-cruiser** rules key off the `domain/` and `application/` path segments, so Thin modules are naturally exempt without a suppression list.
- **Aggregate size**: no automated check. Reviewed at PR time against Vernon's guidance; the contention signal (needing a queue in front of an aggregate) is recorded here as the trigger for splitting.
